## 一、两条源码级铁律

### 铁律 1：章节按 URL 去重，同 URL 会被合并

```kotlin
// BookChapter.equals 只比较 url  →  LinkedHashSet 去重
```

**推论**：

- 多章共用一页（卷末页、付费提示页、"本书完"页）时，**必须给 URL 加 `#fragment` 保证唯一**；
- 反过来：**列表字段 `bookUrl` 取空 → 全部回退 baseUrl → "书籍总数:1"**，就是这条铁律在搜索/发现上的表现（不是污染，是污染的下游放大器）；
- `BookChapter.index` 是 **0-based**。

### 铁律 2：阅读按"出现顺序"接收章节，不排序

Legado **不会**替你按标题/编号排序，也不会校验顺序合理性。
→ **规则里给什么顺序，书架里就是什么顺序。** 所有顺序治理都必须发生在 `chapterList` 内部。

## 二、官方抓目录的两种模式（保序能力不同）

源码：`BookChapterList`（已核）

```
nextTocUrl 产出【单个 URL】 → while 链式循环        ← ★顺序天然保证
nextTocUrl 产出【多个 URL】  → flow.mapAsync 并发抓取 ← 按发射顺序 await = 保序
                              但"每页内部返回顺序"不保证等于 URL 升序 → 有错序风险
```

**实务结论**：

- 分页目录**优先用链式**（每页只产 1 个下一页 URL），最省心；
- 要并发（页数多、想快），必须满足第三节的判定条件，且**每页产出的页码要显式可控**。

**链式写法模板**（xuken 定型）：

```javascript
// nextTocUrl：有 select → 取 selected 的【下一个】option；无 select → 取 div.info_btn 的 /book_N/1.html
@js:
var doc = Packages.org.jsoup.Jsoup.parse(String(result));
var sel = doc.select('select[name=indexselect], div.page_num select').first();
if (sel) {
  var os = sel.select('option'); var hit = false;
  for (var i = 0; i < os.size(); i++) {
    if (hit) { return baseUrl.split('?')[0].replace(/1\.html$/, '') + os.get(i).attr('value'); }
    if (String(os.get(i).attr('selected')).length) { hit = true; }
  }
  return '';                       // 末页 → 空串 → Legado 终止
}
var a = doc.select('div.info_btn a').first();
return a ? a.attr('href') : '';
```

**⚠️ 空串终止的机制**：`nextTocUrl` 返回空 → Legado 解析为当前 URL → 被去重 → 抓取终止。**这是安全的停止信号，不要返回假 URL。**

## 三、★"并发抓全页"能不能用？判定条件

两条实战路径**结论相反**，差别在于**详情页有没有内联前 N 章**：

| 站点形态 | 做法 | 结果 |
|---|---|---|
| **63sg**：目录页 `/dir/{id}/?page=N&sort=asc`，**详情页不含章节列表** | `nextTocUrl = select#indexselect@option@value`（一次产全部页 URL） | ✅ 实测 **1699 章完整**，Legado 并发抓全部页并去重 |
| **xuken**：详情页内联前 100 章（正序主体）+ `select` 指向 `1.html`(101-200)… | 同样 select 全 option | ❌ **错序**：101-200 段的位置跑到最前面 |

**判定规则**：

```
详情页是否内联了部分章节？
├─ 否（目录页是独立入口）→ 可以并发抓全页（nextTocUrl 返回全部页 URL）
└─ 是（详情页 = 第 1 页）→ 必须链式，每页只返回【一个】下一页 URL
                            否则"详情页第 1 页"与"分页第 2 页"会错序
```

**折中方案**（想快又怕错序）：`nextTocUrl` 只返回第 2、3 页 URL（跳过与详情页重叠的部分），或统一在 `chapterList` 末尾**自己做排序**（见第五节）。

## 四、六类目录脏数据与对策

### 脏 1｜"最新章节"倒序区（最高频）

**形态**：详情页有**两个** `ul`/`dl`：第一个是"最新章节"12 条**倒序**，第二个才是全部章节列表。

```
63sg      ：第二个 <div class="book_last">（dt=「全部章节列表」）
lianaiya  ：同上"第二个 .book_last"
ggd66     ：dl.book.chapterlist 前 12 个 dd 是倒序区 → 用 #list-chapterAll 限定
xuken     ：class.ph_list 内混入"最新更新"（其他书推荐！）
35sw      ：两个 ul.p2，第一个是"最新章节"5 条倒序
book630   ：第 1 个 ul.chapter-list 是 12 条倒序，第 2 个才是主体
```

**三种正确写法**（按可靠度）：

```javascript
// A. 索引（最直接，但要确定结构不变）
"chapterList": "class.ph_list.0@class.br-b-1@tag.a"
// B. 用容器 id 限定（最稳）
"chapterList": "#list-chapterAll dd a"
// C. 用表头文本定位兄弟节点（35sw）
"chapterList": "@css:a[name=all]~ul.p2>li"
```

### 脏 2｜隐藏副本 / 页尾垃圾副本（xuken 的"三件套"）

```
目录页 ul.ph_list 里混：
 ① 页首 12 个 CSS display:none 的隐藏副本（<li> 无 class）
 ② 页尾 1~13 章垃圾副本（<li> 无 class）
 ③ 底部"最新更新"其他书推荐
★ 纯净章节的共同特征：<li class="br-b-1">（垃圾全无此 class）
```

→ **找"黄金特征 class"** 是最强的过滤器。xuken 实测 p1/p7 各 100/100 全对，p8 3/3 全对。

### 脏 3｜幽灵页 / 镜像陷阱页

- **xuken**：末尾 option "第801-802章" 页**根本不存在**（书 799 章完结）→ 靠官方去重 + `br-b-1` 自然消化。目录总数 803 = 799 正主 + 4 同标题 URL 变体；
- **ymxwx** ★更危险：末页 `ml36.html` 内容**实为第 1 页的镜像**（假末页）。→ 用 `select` 分页上限做**校验阻断**（拿到的页码超出 select 上限就停止），否则会无限拼接。

### 脏 4｜不存在的章（死链）

63sg：`/read/{id}/{卷}/0.html` 但标题写"第573章"，访问 302 回详情 → "内容为空"。
→ `chapterList` 里正则过滤章号 `0`，**并带"过滤后为空则回退原列表"保护**。

### 脏 5｜占位/结束项

- m.lzjxx：`href` 为空（"本页章节列表结束！"）、尾段非纯数字 → 白名单 `^[0-9]+[.]html$`；
- aaawz：目录标题是字体混淆乱码 → 先还原再判重（见[字体反爬篇](方法-字体反爬三代方案演进.md)）。

### 脏 6｜CDN 限频导致整页拿不到

rrssk：CDN 人人书云对 `loadChapterPage` 限频 403 →
**降级链**：`GET 首页自愈` → 梯度等待 5s/30s → 降级 `/chapter/{id}.html` 直读 → **按 URL 数字去重、升序保底 120 章**。

> 最后一步是关键：**宁可给一个"只有前 120 章但顺序对"的目录，也不要给空目录。**

## 五、排序：站点 ID 不等于章节序

**xuken 实测**：站点 `aID` 与章节号**不同步**（517~519 章 aID 乱序）。按 aID 排 → 519 排在 517 前面。

**排序键选择优先级**：

```
① 标题里的序号：/第(\d+)章/ 的 N        ← 最贴近用户认知
② 章节号字段（若有独立 chapter number）
③ 站点 aID / 数字后缀                   ← 兜底
④ 完全不排（信任站点给出顺序）           ← 单页站点常用，风险最低
```

**注意**：分页站点里"标题序号"可能带卷名/万字（`第100章`、`第1卷 第3章`），正则要容错；无法解析序号的行**保持原位**（稳定排序），不要把它们堆到一端。

**如果必须并发**（第三节允许的情况），在 `chapterList` 末尾显式排序后再返回：

```javascript
arr.sort(function(a, b){
  var na = num(a.name), nb = num(b.name);           // 抽标题序号
  if (na >= 0 && nb >= 0 && na !== nb) { return na - nb; }
  return 0;                                          // ★拿不到序号的保持原序（稳定）
});
```

## 六、虚拟章节（非真实章节）的正确造法

用途：把"外部链接/求书回复/功能入口"做成目录条目（zhaoshu「一键开书」、黑料网「在内置浏览器打开」）。

```javascript
// chapterList：为每个网址造一个虚拟 <div>，data-rid 承载真值，URL 加 fragment 保唯一
var rid = 'open-' + encodeURIComponent(u);
var el  = Packages.org.jsoup.Jsoup.parseBodyFragment('<div class="zs-open"></div>').select('div.zs-open').first();
el.attr('data-rid', rid);
// chapterUrl = baseUrl + '#reply-' + data-rid   ← ★fragment 不进 HTTP 请求，且天然唯一
```

三条约束：

1. **URL 必须唯一**（铁律 1）→ 用 `#` fragment；且 fragment **不会进 HTTP 请求**，所以同一物理页可以承载 N 个虚拟章；
2. 正文规则里判 `rid.indexOf('open-') === 0` → 还原网址 → `java.openUrl(深链)` → 返回说明文字；
3. ⚠️ **fragment 污染风险**：hlwf6 遇到过"debug 请求带 `#browser` 时，详情页 baseUrl 被污染 → 拼进章节 URL" → `chapterList`/`intro` 里统一 `split('#')[0]` 清洗。**加 fragment 要主动加，不能被上游意外带进来。**

## 七、tocUrl / nextTocUrl 的位置与写法约束

| 约束 | 事实 | 出处 |
|---|---|---|
| `tocUrl` 放哪 | **必须在 `ruleBookInfo` 内**；放 `ruleToc` 被反序列化**静默丢弃** | ppxsw |
| `tocUrl` 兜底 | **不支持 `\|\|` 兜底** | ppxsw |

| `chapterUrl` 的 JS | 纯 `@js:` 前缀**可执行**；`选择器@js:` 组合形式**不执行** → 改 `{{}}` 模板插值 | zhaoshu 推翻 aaawz 旧结论 |

| `bookUrlPattern` | **不能匹配目录/阅读页 URL**，否则点进去被当详情页 | 77shuku |

## 八、章内分页与串章防护

**规则**：`ruleContent.nextContentUrl` —— 发现分页按钮/下一页逻辑就**必须**考虑它（技能强约束），且**禁止** `prevContentUrl`。

但"下一章"链接会伪装成"下一页"，**串章是本节最大风险**。三种实测防护：

```javascript
// ① 只跟带下划线的分页 URL（fdxrz：短ID + _x.html；空返回→当当前 URL→去重终止，安全）
// ② 按页码正则判"是不是同章"（book630：按钮文案也叫"下章"=末页陷阱）
var m = baseUrl.match(/_([0-9]+)[.]html$/);        // 当前页码
// → "下章"链接若不含 _N 就不是同章分页 → 返回空
// ③ ★用 setNextChapterUrl 式校验（ymxwx：hhekgsv 末页指向下一章）
//    lastread.set(第二参 = 当前章节 id) 做同章校验，防误拼
```

**通用做法**：`nextContentUrl` 只跟**匹配同章分页形态**的链接，其余情况返回 `''`（空 → 终止，安全）。

**黄果/aaawz 式**：站点按固定字数硬切分页 → 会把 `&nbsp;` 切成 `&nb|sp;` 碎片，且孤立 `&` 被 jsoup 转义成 `&amp;` 躲过普通断言：

```
##&(?:amp;)?n(?:b(?:s(?:p;?)?)?)?|nbsp;?|sp;|(?<=>)(?:p;|;|bsp;)|&amp;(?![a-zA-Z#])|&(?![a-zA-Z#])##
```

经 10+ 组用例验证：碎片全清，且 `A&amp;B`、`&#123;`、`body`、`boss`、`b超` 不误伤。

**没有章内分页就干脆不设** `nextContentUrl`（77shuku/m.lzjxx 定型）。

## 九、验证方法：顺序 0 违规检查

目录抓完后，**别只看章数**，要验顺序：

```javascript
// eval_js 里，对抓到的章节名序列做单调性检查
function num(s){ var m = String(s).match(/第\s*([0-9一二三四五六七八九十百千]+)/); return m?1:-1; }
var bad = 0, prev = -1;
for (var i = 0; i < titles.length; i++) {
  var n = parseNo(titles[i]);           // 抽"第N章"的数字（中文数字要转）
  if (n < 0) { continue; }              // 无序号 → 跳过（不参与判序）
  if (n < prev) { bad++; java.log('乱序: ' + prev + ' -> ' + n + ' @' + titles[i]); }
  prev = n;
}
java.log('总' + titles.length + ' 乱序' + bad);
```

**四项验收标准**（xuken/63sg 交付口径）：

| 项 | 标准 |
|---|---|
| 章数 | 与站点页面显示"共 N 章"一致（± 幽灵页可解释） |
| 顺序 | 乱序计数 = 0 |
| 首末 | 第 1 章是"第1章/正文"，末章是"最终章/尾声" |
| 抽样可读 | 首、1/4、1/2、3/4、末 各抽 1 章跑正文（`--URL`） |

**⚠️ debug 连抓多页会触发封锁**（xuken 9 页、hanime1 8~10 req/min）→ 页间 ≥1.5s 或分次跑。
