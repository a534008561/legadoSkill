## 一、问题的形状：最误导人的失败态

绝大多数接口失败会给你错误码，你会立刻去查参数。但有一类站点**故意把拒绝伪装成"没有数据"**：

```json
{"code":0,"msg":"","data":{"search":[]}}
```

`code:0` 是成功码，`msg` 空，`data.search` 空数组——从契约上看完全合法。
于是排查会走偏：以为站点没收录这本书、以为参数名写错、以为 JSONPath 写错、以为 `bookList` 规则不对……
本案在这一态上卡了约 2 小时，试过换 UA、换 header、换 `Origin/Referer`、加 `X-Requested-With`、换 GET/POST、换 JSON body，
全部返回同一个空结果——**因为问题不在这些维度上**。

> 判断口诀：**`code:0` + 空数组 ≠ 站点没这条数据**。
> 先用"站点自己的 JS 能不能搜到"这一组实验把两种情况分开。

## 二、三组对照实验：唯一能定根因的排法

只做一两组会误判，三组缺一不可。

### 第 1 组 · 正向组：让站点自己的代码去发请求

```js
// 在 Legado 的 eval_js 里，用 webView 打开搜索页，hook 掉 $.post 抓真实请求体
var url = "https://m.dzrjk.com/user/search.html?q=" + encodeURIComponent("神箭遗恨");
var js = "(function(){"
 + "var cap=[];var op=$.post;"
 + "$.post=function(u,d,cb,t){"
 + "  try{var x=new XMLHttpRequest();x.open('POST',u,false);"
 + "  x.setRequestHeader('Content-Type','application/x-www-form-urlencoded; charset=UTF-8');"
 + "  x.setRequestHeader('X-Requested-With','XMLHttpRequest');"
 + "  var b=[];for(var k in d){b.push(k+'='+encodeURIComponent(d[k]));}"
 + "  x.send(b.join('&'));cap.push('ST'+x.status+'|'+String(x.responseText).substring(0,400));"
 + "  }catch(e){cap.push('ERR '+e.message);}return;};"
 + "var t=Date.now();while(Date.now()-t<7000){}"
 + "try{window.book.search();}catch(e){cap.push('THROW '+e.message);}"
 + "return cap.join(' ;; ');})()";
java.webView(null, url, js, false);
```

**结论**：站点自己发 → 有结果 ⇒ 接口是活的，问题在**我的请求**。
若站点自己也空 ⇒ 才轮到怀疑接口/账号/IP。

> 注意：`webView` 里的 `while` 空转是给页面脚本留加载时间的笨办法，能用就行，别指望 `setTimeout` 回调能返回到返回值里。

### 第 2 组 · 反向组：故意把签名改错

```js
// 真实 sign vs 全 0 sign，两次返回必须不同
post(pageUrl, pairs.concat(["sign=" + realSign, "q=" + q]));
wait(5000);
post(pageUrl, pairs.concat(["sign=00000000000000000000000000000000", "q=" + q]));
```

**关键判读**：
- 两次返回**不同**（错签名报"签名错误"或空、真签名有结果）→ 签名确实被校验，继续修签名
- 两次返回**完全相同**（都是空数组）→ 要么两个都被拒（签名之外还有别的因素），要么这个参数根本没参与校验。**本案属于后者：sign 校验通过，但 bgt 参与校验，改 sign 没用**

> 反向组的价值就在这：它否掉了"sign 是唯一门槛"这个假设，把注意力推向其他参数。

### 第 3 组 · 修复组：按假设改，必须出现结果

只改一个变量（本案：`bgt` 截断末位），其他全部不动，重测。

```
未截断 bgt → {"code":0,"data":{"search":[]}}   ← 空
截断末位 bgt → {"code":0,"data":{"search":[{"book_name":"神箭遗恨",...}]}}  ← 有
```

**只有这一组出现结果，才算定死根因。**

## 三、必读：发请求之前的预处理函数

这类 CMS（本家模板广泛用于多个"蕃茄/番茄"镜像站）的搜索逻辑是：

```js
search: function () {
    // 一堆 if ("" == vw) return; 的空值防御
    var keyword = decodeURIComponent(getQuery('q'));
    search_before();                    // ★ 关键：预处理
    var url = '/api/search';
    var params = {'q':keyword,'vw':vw,'abw':abw,...,'sign':sign};
    $.post(url, params, function (json) { ... }, 'json');
}
```

**必须读 `search_before()`**：

```js
function search_before() {
    if (document.cookie != "") {
        bgt = bgt.slice(0, bgt.length - 1);   // ★★ 有 cookie 就砍掉最后一个字符
    }
    $("#loading").css('display', 'block');
}
```

**为什么这一行是致命的**：
浏览器访问过站点必然带 `SID` cookie → 真实浏览器发出的 `bgt` **永远是截断过的** →
服务端拿"截断后的 bgt"参与签名计算 →
你用 `java.ajax` 抓页面拿到的 `bgt` 是**未截断的原始值** →
原样回传 ⇒ 签名对不上 ⇒ 服务端不报错，直接返回空数组。

> **通用教训**：抓到的"页面内联变量"不等于"真实请求里发送的值"。
> 一定要看**发请求前有没有被改写**（slice / replace / encode / 拼接 / 大小写转换 / 排序）。

### 常见的"发请求前改写"清单

| 改写方式 | 典型代码 | 影响 |
|---|---|---|
| 截断 | `x = x.slice(0, x.length-1)` | 末位校验失败 |
| 反转 | `x = x.split('').reverse().join('')` | 全串校验失败 |
| 拼接时间戳 | `x = x + Date.now()` | 时间窗口过期 |
| 二次编码 | `encodeURIComponent(encodeURIComponent(x))` | 服务端解码一次后不匹配 |
| 条件分支 | `if (document.cookie != "") {...}` | **有/无 cookie 两套参数**，最容易漏 |
| 大小写 | `x = x.toLowerCase()` | 大小写敏感校验失败 |

## 四、本案根因：bgt 要砍掉最后一个字符

```js
// 从搜索页抓 31 个变量
var names = 'vw abw ru jrt van fw cwl gpr uyoo tz euu tsn eju um fp dvm jpk deblkx ht azy sna wqx fpp rup jwj bgt qp yf cw wq'.split(' ');
var re = /var\s+([A-Za-z_]\w*)\s*=\s*"([^"]*)"/g;
var map = {}; var mm;
while ((mm = re.exec(html)) !== null) { map[mm[1]] = mm[2]; }

for (var i = 0; i < names.length; i++) {
    var n = names[i];
    var v = map[n];
    if (typeof v === 'undefined') continue;
    if (n === 'bgt' && v.length > 1) v = v.slice(0, v.length - 1);   // ★ 复刻站点预处理
    pairs.push(n + '=' + encodeURIComponent(v));
}
```

### 为什么用正则一次性抓全部变量，而不是逐个 `match`

```js
// ❌ 在书源 JSON 里写 31 次 match，转义层数容易错，且字符串里 \\s 会被吃
var m = html.match(new RegExp('var\\s+' + n + '\\s*=\\s*"([^"]*)"'));

// ✅ 正则字面量只写一次，转义层数固定
var re = /var\s+([A-Za-z_]\w*)\s*=\s*"([^"]*)"/g;
while ((mm = re.exec(html)) !== null) { map[mm[1]] = mm[2]; }
```

> 书源 JSON 里 `searchUrl` 的 `@js:` 部分是**单层字符串**，正则字面量 `/var\s+/` 直接写即可，不要写成 `/var\\\\s+/`（那是 JSON→Python→JS 多层转义留下的坏习惯）。

## 六、Legado 侧的连带坑

### 1. 空结果会生成"假书"，必须加 bookUrlPattern

`BookList.analyzeBookList` 源码：

```kotlin
if (collections.isEmpty() && bookSource.bookUrlPattern.isNullOrEmpty()) {
    Debug.log(bookSource.bookSourceUrl, "└列表为空,按详情页解析")
    getInfoItem(...)   // ← 把搜索 URL 本身当详情页，生成一本书
}
```

不加 `bookUrlPattern` 时，搜"斗破苍穹之无上之境"（0 结果）会得到一本书名叫空、`bookUrl=https://m.dzrjk.com/api/search` 的假书。
加：

```json
"bookUrlPattern": "https?://(m|www)\\.dzrjk\\.com/html(_wap)?/\\d+/?"
```

之后正常返回 0 本。副作用是好的：用户粘贴详情页 URL 搜索时，会直接按详情页解析。

### 2. `concurrentRate` 单位是毫秒（大坑）

```kotlin
// ConcurrentRateLimiter.kt
// 并发控制为 次数/毫秒 , 非并发实际为1/毫秒
val nextTime = fetchRecord.time + fetchRecord.interval.toLong()
```

`"1/2"` = 每 **2 毫秒** 最多 1 次 —— 这几乎没有限流作用！
要限成"每 2 秒 1 次"应写 **`"1/2000"`** 或 `"2000"`（单数字形式即 `1/毫秒`）。

> 站点限频是 3 秒，取 2~3 秒留余量。`"1/2"` 是常见误写，务必检查。

### 3. `java.ajax` 会走 AnalyzeUrl（带 cookie jar、带书源 header）

```kotlin
fun ajax(url: Any, callTimeout: Long?): String? {
    val analyzeUrl = AnalyzeUrl(urlStr, source = getSource(), ...)
    return analyzeUrl.getStrResponse().body
}
```

所以 `searchUrl` 里用 `java.ajax(页面)` 抓 token 页时，**会自动带 cookie**，这正是 `bgt` 需要截断的前提条件（有 cookie 才截断）。
不要用 `java.get`/`java.post`（那走 Jsoup，**不带 cookie jar**）。

## 七、避坑清单

1. **`code:0` + 空数组，先当"请求被拒"处理，别当"没数据"**
2. 三组对照（站点自己发 / 故意改错签名 / 修正后重测）缺一不可
3. **必读发请求前的预处理函数**，抓到的变量值 ≠ 发出的值
4. 正则抓内联变量用**字面量 `/.../g` 一次性建 map**，不要循环拼 `new RegExp`
5. `bgt`（本例）要 `slice(0, len-1)`；换站点时逐个参数检查有无类似改写
6. 加 `bookUrlPattern`，否则空结果会造出假书
7. `concurrentRate` 是 **次数/毫秒**，`"1/2"` ≈ 不限流，要写 `"1/2000"`
8. `java.ajax` 带 cookie jar，`java.get/post` 不带——抓 token 页要用 `java.ajax`
9. 沙盒 IP 与手机 IP 出口不同，一端被限频不代表另一端也失败，别用一端现象推另一端
10. 搜不到长书名时先试短关键词（分词匹配限制），再怀疑规则

## 九、附录：`ruleContent.replaceRegex` 的三条源码级铁律

本次清理正文残留文本时连踩三个坑，全部来自源码行为，记录下来避免重犯。

### 铁律 1：`replaceRegex` 必须以 `##` 开头，否则被当 CSS 选择器

`BookContent.kt`：

```kotlin
val replaceRegex = contentRule.replaceRegex
if (!replaceRegex.isNullOrEmpty()) {
    contentStr = contentStr.split(AppPattern.LFRegex).joinToString("\n") { it.trim() }
    contentStr = analyzeRule.getString(replaceRegex, contentStr)   // ← 走通用规则解析
}
```

它传给的是**通用 `getString`**，而通用规则里 `##` 是"正则替换"的专用分隔符。
所以：

| 写法 | 实际行为 | 结果 |
|---|---|---|
| `"##id.xxx.>##"` | `##正则##替换为空` | ✅ 正确删除 |
| `"<p>id.xxx.</p>"` | 当成 CSS 选择器 | ❌ 取不到 → **正文变空** |
| `"^id.xxx.$"` | 不带 `##`，当 CSS 选择器 | ❌ 正文变空 |

**正确格式**：`##要删除的正则##`（第二个 `##` 后为空 = 替换成空串）。

### 铁律 2：执行时机在 HTML 净化之后，正则里不能写标签

`BookContent.kt` 顺序是：先 `HtmlFormatter.formatKeepImg(content)` 把 `</?p|br|div>` 换成换行、剥掉所有标签，
**之后**才跑 `replaceRegex`。

所以 `##<p>\s*id"xxx">\s*</p>##` 永远匹配不到——`<p>` 已经变成换行了。
只能匹配**残留的可见文本**，例如 `##id.booktexts.>##`。

### 铁律 3：Java `String.replace` 不带 MULTILINE，`^...$` 只匹配整串首尾

`AnalyzeRule.kt`：

```kotlin
return result.replace(regex, replacement)   // Kotlin String.replace(Regex, String)
```

`^` / `$` 在未开 `Pattern.MULTILINE` 时只锚定整个字符串的开头和结尾。
正文有几十行，`^id.xxx.$` 匹配不到中间那一行。

**对策**：去掉锚点，直接匹配文本片段；或用 `(?m)` 内联标志（Rhino/Java 均支持）。

### 另外：MCP `save_source` 会吞掉含双引号的字段值

`id"booktexts">` 这种带双引号的字符串写进 JSON 后，MCP 侧解析失败，字段被**静默丢弃**（保存成功但值为空）。
对策：正则里用 `.` 代替 `"`（`id.booktexts.>`），或者用 `\x22`。
