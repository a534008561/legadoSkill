# 方法：书源内「自定义资源」上限放开与静默截断排查

> 蓝本：iwara 视频书源 v10（2026-09-20）。用户诉求原话：
> 「源现在限制了用户加入自定义播放域名的数量以及测试的数量，放开限制，
> 不然他们这些域名无法使用的时候，用户的自定义域名也可以用。」

## 0. 一句话总结

**书源里凡是写死的 `length<40` / `tried<3` / `slice(0,40)` / `i<14`，都是"用户资源被静默丢弃"的凶案现场。**
解法不是把数字改大，而是**抽出统一的可配置上限函数 + 保留硬护栏**。

## 1. 现象谱系：怎么发现这类问题

| 用户描述 | 真实原因 |
|---|---|
| "我加了自己的域名，但好像没用" | 池上限 `out.length<40` 把第 N 个起丢掉了 |
| "保存了 100 个，只剩 40 个" | `ok.slice(0,40)` 保存时截断 |
| "下拉框里找不到我加的域名" | 渲染层 `i<14` 只显示前 14 个 |
| "自带域名全挂了，我的域名也不顶用" | **复合**：候选队列 `order.length<5` + 探测 `tried<3`，用户域名排在候选之外，根本没被尝试 |
| "测速只测了 12 个" | `IWRMHPRIO(...,12)` |
| "测到一半就停了" | 时间预算 `>40000ms` 中断 |
| "测出来的延迟不刷新" | 缓存淘汰 `while(ord.length>40){ord.shift()}` 把老域名挤掉 |

**共同特征：不报错、不警告、静默失败。** 这是它难查的根本原因。

## 2. 排查方法：三遍扫描

### 第一遍：数字字面量扫描
```bash
grep -oE 'length *[<>]=? *[0-9]+|i *< *[0-9]+|tried *< *[0-9]+|slice\(0, *[0-9]+\)|>[0-9]{4,}' jsLib.js | sort | uniq -c
```
iwara 实扫结果：
```
1 i<14              <- 下拉渲染
1 length<40         <- 池上限
1 tried<3           <- 正文探测
1 order.length<5    <- 候选队列
1 >40000            <- 测试时间预算
1 slice(0,40)       <- 保存截断
1 while(ord.length>40)  <- 缓存淘汰
```

### 第二遍：逐个判定"是不是用户资源限制"
关键提问：**这个数字限制的是「站点固定结构」还是「用户可增删的资源」？**
- `i<14 && t[i].id` 取标签 → 站点结构，**不动**
- `hex.length<400` 图片 base64 长度校验 → 安全护栏，**不动**
- `out.length<40` 域名池 → **用户资源，要放开** ✓

### 第三遍：沿调用链确认影响面
以 iwara 为例，一个上限串起整条链路：
```
IWRMHSAVE(保存 40) → iwMH 落库
   ↓
IWRMHPOOL(池 40) → IWRMHOPT(下拉 14) / IWRMHPRIO(取样 12)
   ↓
IWRMHTEST(测试 12, 40秒)   IWRCOPick(候选 5, 探测 3)
```
上限是**链式**的：任一环截断，后面的都白搭。所以必须**全链一起放开**。

## 3. 解法：统一上限函数 + 硬护栏

```js
function IWRMAX(k,Sv){
  var d={pool:200,probe:12,test:60,save:200,lat:200,ui:40,
         budget:120000,order:40};
  var V={pool:'iwMaxPool',probe:'iwMaxProbe',test:'iwMaxTest',save:'iwMaxSave',
         lat:'iwMaxLat',ui:'iwMaxUi',budget:'iwMaxBudget',order:'iwMaxOrder'};
  var X=Sv||IWRSS();
  var n=parseInt(IWRG(X,V[k]||'',d[k]),10);
  if(n!=n||n<1){n=d[k];}                      // 非法值回退默认
  var cap=(k=='budget')?3600000:2000;          // ★ 毫秒预算单独放宽
  if(n>cap){n=cap;}
  return n;
}
```

### 三条设计原则

1. **单点定义**：8 项上限集中一处，不再散落全库 → 下次改不用再翻 70KB。
2. **书源变量可覆盖**：用户在书源变量里改 `iwMaxPool=500` 即可，**不用改 jsLib**。
   这是关键 —— 用户不会为了调个数字去读 7 万字符的脚本。
3. **保留硬护栏**：`cap` 防用户填 `99999999` 把 App 卡死。
   ⚠️ **护栏要分类**：条数类 2000 足够，**毫秒预算不能也用 2000**（否则 120 秒被钳成 2 秒，功能直接失效）。这是本方法最容易踩的坑，务必按单位给不同 cap。

## 4. 配套改进（让"放开"真正可用）

放开上限只是第一步，**数量一多必须给人可管理的手段**，否则 200 个域名反而是灾难：

### 4.1 自动排序（IWRMHSORT）
```js
function IWRMHSORT(Jv,Sv,force){
  // … 可先 force 触发一次全量测速（IWRCOPRB 走播放器同款通道）
  var lat=IWRG(X,'iwMLat','');var m={};/* 解析 h:ms|h:X 缓存 */
  var scored=[];
  for(var q=0;q<P.length;q++){
    var v=m[P[q]];
    var s=(v===undefined||v==='')?9e9:((v==='X'||v==='C')?1e9:parseInt(v,10));
    scored.push([P[q],s]);
  }
  scored.sort(function(p,q){return p[1]!=q[1]?p[1]-q[1]:(p[0]<q[0]?-1:1);});

```
排序权重：**通(ms 升序) → 不通 → 未测**，同级按域名稳定排序（避免每次刷新顺序乱跳）。

### 4.2 输入容错统一
- `IWRMHPOOL` 与 `IWRMHSAVE` 都要做「无点则补 `.iwara.tv`」，否则 `hime` 在保存时变成 `hime.iwara.tv`、在池里还是 `hime` → **同一个域名两份记录**，测速结果对不上。
- 非本站域名（`*.iwara.tv` 之外）应**直接放行**，不要套用站点黑名单：
  ```js
  if(x.indexOf('.iwara.tv')!=x.length-9){return true;}  // 外部域直接放行
  ```

### 4.3 枚举值语义统一（`auto` 陷阱）
把 `iwMHost` 设为 `'auto'` 后，要同步检查**所有读取点**：
```js
// ✔ 已处理
if(cur!=''&&cur!='off'&&cur!='auto'&&P.indexOf(cur)<0){...}  // 不进下拉
if(cur==''||cur=='off'||cur=='auto'){ /* 选中「不固定」*/ }   // 选中态
// ✔ 状态行
if(mh0=='auto'){mh0='自动选域';}
```
漏掉任一处的症状：下拉里多出 `auto · 未测` 这种假项、选中态错位。

### 4.4 文案同步
旧文案里的「下拉只显示前14个」「上限 40 个」必须一起改，否则**用户按旧文案理解，以为还有限制**。文案里要动态回显当前值：`'下拉显示上限 iwMaxUi='+IWRMAX('ui',Sv)`。

## 7. 迁移改动清单（套到别的源）

1. 扫数字字面量（§2 第一遍），挑出**限制用户资源**的
2. 加 `IWRMAX(k,Sv)`，把关键项搬进去（**含单位分类的 cap**）
3. 沿调用链把所有截断点替换为 `IWRMAX(...)`
4. 加自动排序 / 容错 / 枚举语义统一 / 文案同步
5. Node 仿真 10 项 + **负对照**
6. 大源走 dpaste + 深链导入

## 9. 通用结论

1. **硬编码数字 = 潜伏的静默失败**。凡是用户能增删的资源，都不要写死上限。
2. **放开 ≠ 改大数字**：要「可配置 + 硬护栏 + 管理手段（排序/筛选）」，三者缺一不可。
3. **上限是链式的**，必须全链一起放开，否则用户在最末端还是用不上。
4. **放开之后用户体验反而更差**（200 个域名没法挑）→ 必须配套自动排序。
5. **验证要带负对照**，否则"跑通了"可能只是"本来就没坏"。

## 10. ★追加（2026-09-20 实战）：上限放开后暴露的更深问题

放开域名数量限制后做回归，意外挖出一个**比上限更致命**的 bug —— 值得单独记：

### 10.1 探测函数必须走"能生效的那条通道"

`IWRCOPRB`（媒体域可用性探测）原本这样写：

```js
// ❌ 没带 dnsIp
J.ajax('https://'+h+path+','+IWRJ({headers:{Range:'bytes=0-1023'}}));
```

而这个源的用户环境里，**该域名被 DNS 污染到 IPv6 黑洞** ——
只有带 `dnsIp` 时才会去 Cronet 走 OkHttp 成功。

后果是灾难性的**静默连锁**：

```
探测不带 dnsIp → 全走 Cronet → 全部超时
   → 每个域名被标记为「Cronet不通」
   → 选域函数认为无域可用，保持原样
   → 播放器走 Cronet + 污染 DNS → 播放失败
   → 用户看到「书源测试全绿，视频就是播不动」
```

**教训**：**探测函数与使用函数必须走同一条通道**。
如果探测走 A 通道、实际使用走 B 通道，探测结果就是**系统性误导**，
比不做探测更糟（会把好域名标记成坏域名）。

```js
// ✔ 修复：探测时带上与实际使用一致的选项
var _op={headers:{Range:'bytes=0-1023'}};
var _ip=IWRHS(Sv);
if(_ip!=''){_op.dnsIp=_ip;}    // ← 与正文取流保持同一通道
```

### 10.2 状态标记要区分「环境问题」与「目标问题」

```js
if(/Cronet/i.test(s.substring(0,400))){Mark(h,'C');return -2;}   // 环境问题
if(/SocketTimeout|timed out|UnknownHost|ConnectException/i.test(s)){Mark(h,'X');return -1;}
//                                    ↑ 目标问题（域名本身不通）
```

原版把所有失败都记成 `C`（Cronet 不通），于是**一次环境抖动就永久污染整个域名池**。
区分后：`C` = 该关 Cronet；`X` = 换个域名。用户看到的处置指引因此完全不同。

### 10.3 验证方法论：对照实验锁定通道归属

同一请求、同一域名、同一网络，只切换"是否带 dnsIp"：

| 请求 | 通道 | 结果 |
|---|---|---|
| 不带 `dnsIp` | Cronet | ✘ 15335ms 超时 |
| 带 `dnsIp` | OkHttp | ✔ 1352ms 成功 |

**一次对照就能证明**：问题不在域名、不在网络，而在**通道选择**。
这类"测试全绿但功能不动"的错觉，几乎都可以用这个两行对照实验破掉。

| # | 坑 | 症状 |
|---|---|---|
