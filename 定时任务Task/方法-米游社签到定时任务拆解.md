## 1. 任务架构总览

米游社签到定时任务 = 三个独立作用域：

| 字段 | 作用域 | 说明 |
|------|--------|------|
| `script` | 定时任务主脚本 | cron 触发执行，每天 0 点跑全游戏签到 |
| `loginUrl` | 登录界面逻辑 | 独立作用域，**与 script 互不共享函数** |
| `loginUi` | 登录界面 UI 定义 | 按钮 action 是 JS 表达式，调用 **loginUrl 内顶层函数** |
| `loginCheckJs` | 登录状态判断 | 独立表达式，返回 true/false 决定登录界面显示状态 |

⚠️ **三大作用域独立编译**：jsLib 函数在 script 里看不到；script 函数在 loginUrl 里看不到；loginUrl 必须"自给自足"（所有辅助函数 md5/ds/auth/http/gameConfig/roles/signInfo/sign 全部内联）。

## 3. 修复案例：登录界面按钮无反应（v9d）

### 3.1 症状

- 定时任务后台运行正常（cron 签到成功 5/0）
- 登录界面：`保存登录` / `清除` 有反应；`验证登录状态` / `查询签到状态` / `立即签到` / `获取帮助` 点了没反应
- 把按钮名对齐后，出现明确报错：
  ```
  TypeError: 找不到函数 show。
  at function doHelp() ... java.show('【获取Token方法】' + ...)
  ```

### 3.2 根因（两个问题叠加）

**问题 1：loginUi 按钮 action 与 loginUrl 函数名不匹配**

```
loginUi action:        login() logout() checkLoginStatus() querySignStatus() doManualCheckin() showHelp()
loginUrl 实际定义:     login() logout() doCheckLogin()      doQueryStatus()    doManual()       doHelp()
```

按钮 action 是 JS 表达式，执行不存在的函数 → ReferenceError 被静默吞掉 → "无反应"。
**排查方法**：把 loginUi 的 action 列表与 loginUrl 的 `function\s+(\w+)` 正则提取结果做差集比对。

**问题 2：此 App 的 java 对象没有 `show` 方法**

```
TypeError: 找不到函数 show（JsExtensions 精简版，无 show/showDialog）
```

反射枚举 JsExtensions 全部 260 个属性：只有 `longToast` / `toast` / `copyText` / `getVerificationCode` 等，**无 show**。

### 3.3 修复方案

**① loginUi action 对齐**（4 处）：

| 旧 action | 新 action |
|-----------|-----------|
| checkLoginStatus() | doCheckLogin() |
| querySignStatus() | doQueryStatus() |
| doManualCheckin() | doManual() |
| showHelp() | doHelp() |

**② loginUrl 末尾追加 4 个别名函数**（双保险，兼容 App 端可能缓存旧 UI）：

```js
function checkLoginStatus() { return doCheckLogin(); }
function querySignStatus() { return doQueryStatus(); }
function doManualCheckin() { return doManual(); }
function showHelp() { return doHelp(); }
```

**③ `java.show` → 三级兜底 `__show`**（任何 App 版本都不会再炸）：

```js
function __show(text) {
    try { java.longToast(text); }
    catch(e) { try { java.toast(text); } catch(e2) { java.copyText(text); } }
}
```

- `doQueryStatus` / `doManual`：`java.show(results.join('\n'))` → `__show(results.join(String.fromCharCode(10)))`
- `doHelp`：帮助文本改 `java.copyText(helpText)` + `java.longToast('帮助已复制到剪贴板')`（避免超长 toast 显示不全）

**④ loginCheckJs 严格化**：

```js
// 旧：未配置也永远返回 true（登录界面误显示"已登录"）
var stoken = source.get('ltoken'); var stuid = source.get('ltuid'); if (stoken && stuid) { return true; } return true;
// 新：未配置返回 false（正确显示"未登录"）
var stoken = source.get('ltoken'); var stuid = source.get('ltuid'); if (stoken && stuid) { return true; } return false;
```

⚠️ loginCheckJs 只影响 UI 显示，**不影响 cron 定时执行**（script 走独立管线）。

### 3.4 验证清单（修复后）

1. `python3` json.load 校验 JSON 合法
2. `node --check` 校验 loginUrl / script 两个 JS 块语法（loginUi 是宽容解析器，勿用 node 检查）
3. `get_auto_task` 取回 App 端字段核对（确认落库，非本地幻觉）
4. `run_auto_task` 实测后台管线（确认 script 未受影响）
5. 用户在 App 登录界面逐个点 4 个按钮实测（最终裁决）

## 4. 排查方法论沉淀（可复用）

### 4.1 "按钮无反应" 三步定位法

1. **先取 loginUi 的 action 列表**，与 loginUrl 的顶层函数集合做差集——函数名不匹配是头号原因
2. **再点按钮看 App 日志**（get_app_logs）——执行到函数内部才会暴露 API 缺失类错误（如 java.show）
3. **反射枚举 java 对象可用方法**——确认 API 存在性，避免臆造：

```js
// eval_js 空白源裸跑（注意：此时 java 实际绑的是 BookSource 对象，getClass().getMethods() 返回 null）
var arr = [];
for (var k in java) { arr.push(k); }
arr.join(',')   // 枚举出全部可用属性名（260 个）
```

⚠️ 反射结论有边界：eval_js 环境 typeof 探测为 undefined 的 API，**不一定**在 loginUi 上下文不存在（如 java.getVerificationCode 先例）；但枚举出的方法名列表是可信的"存在集合"。**"不存在"的结论以真实调用报错为准**（本次 java.show 就是真实报错证实）。

### 4.2 loginUi 按钮 action 的调用链

```
用户点按钮 → App 用 initScriptEngine 加载 loginUrl（顶层函数注册）
         → 对 action 字符串 eval（login() 等表达式）
         → 函数内可用：java.* / source.* / Packages.* / 顶层函数 / 顶层 var
```

- action 直接写 `函数名()` 即可，无需 `@js:` 前缀
- 函数必须定义在 loginUrl（不能在 script / jsLib）
- 函数内 `return` 无意义（按钮不消费返回值），靠 toast/copyText 反馈

### 4.3 长文本展示的兼容策略

| 场景 | 推荐写法 |
|------|----------|
| 结果列表（5~10 行） | `__show(text)` 三级兜底（longToast→toast→copyText） |
| 帮助文档（超长） | `java.copyText(text)` + `java.longToast('已复制到剪贴板')` |
| 简短状态 | `java.toast('验证中...')` |
| 后台任务结果 | `java.log()`（进任务日志）+ `java.longToast()`（用户可见） |

## 5. 定时任务通用坑点（AutoTask）

1. **作用域独立**：script / loginUrl / jsLib / loginCheckJs 各自独立编译，函数不互通 → loginUrl 自给自足
2. **`java.ajax` 在 jsLib 作用域是 JavaPackage 对象**（非函数）→ 不用 jsLib，全部内联
3. **script 顶层不要 `return`**（run_auto_task 报"返回的值无效"）→ 最后表达式直接产出字符串
4. **`source.get('key')` / `source.put('key', val)`** 是跨执行持久化的正确姿势（CookieJar 之外的自定义状态）
5. **`save_auto_task` 覆盖保存会重置 lastRunAt/lastResult 为 0**——正常现象，不是故障
6. **大 JSON 任务推送**：唯一可靠流程 = Python 生成字节级完美成品（json.dumps ensure_ascii=False）→ save_auto_task 传字符串；shell 分块显示对反斜杠呈现不一致不可信
7. **loginCheckJs 与定时执行解耦**：loginCheckJs 只影响登录界面显示状态，不影响 cron 触发
8. **cron 表达式**：`0 0 * * *` = 每天 0 点

## 8. 【260904 官方 LegadoTeam 版适配 v9e】"登录状态失效，请重新登录"(-100) 根因与修复

### 8.1 现象

同一任务 JSON：
- legadoT（改版，MCP 连接的 App）：签到全通 ✓
- 官方 LegadoTeam 版（github.com/LegadoTeam/legado）：getUserGameRolesByCookie 返回 `{"data":null,"message":"登录状态失效，请重新登录","retcode":-100}`

### 8.2 排查过程（可复用的方法论）

1. **验证 DS 签名**：用日志里真实 t/r 复算 md5 → 与日志 DS 完全一致，时间戳对应 00:14:50 ✓ → 排除签名因素
2. **对比环境差异**：MCP `get_cookies(api-takumi.mihoyo.com)` → legadoT 该域 **CookieJar 为空**；官方版 HTTP 日志显示 `CookieJar: 1`（任务 enabledCookieJar=true）且请求带 Cookie 头仍 -100
3. **根因锁定**（OkHttp BridgeInterceptor 源码行为）：
```java
List<Cookie> cookies = cookieJar.loadForRequest(userRequest.url());
if (!cookies.isEmpty()) {
  requestBuilder.header("Cookie", cookieHeader(cookies)); // .header() = 覆盖，不是追加！
}
```
官方版走 OkHttp 栈：只要 CookieJar 里该域有任何残留 cookie（曾用 WebView 登录过米游社/其他米哈游书源写入过），就会**把脚本手动拼的正确 ltoken_v2 Cookie 头整体覆盖**成残留旧值 → 服务端读到失效 token → -100。legadoT 的 CookieJar 该域恰好为空，不触发覆盖，所以一切正常。

### 8.3 修复（一行字段 + 一处乱码）

1. **`enabledCookieJar: false`** —— 任务不启用 CookieJar，隔离掉全局残留 cookie 的覆盖干扰。本任务全靠手动 Cookie 头鉴权，无 WebView 需求，关掉零副作用。
2. **script 内 UA 乱码修复**：v9d 的 script 的 httpReq UA 是历史转录错误 `AppleWebSpec, see Misc.Spec) AppleWebKit/537.36`（loginUrl 里是正确的），一并改正为与 loginUrl 一致的标准 UA。
3. header 字段（concurrentRate 兜底 UA）保持不变。

### 8.4 实测验证

- v9e 推回 legadoT → run_auto_task 实测：5 角色全部正常（今日已签到=登录态识别正确，无 -100）✓ → **双版本通用版**
- 官方 LegadoTeam 版：用户导入 v9e 实测（预期：Cookie 头不再被覆盖，登录态恢复）

### 8.5 【260904b 深度修正】官方版-100 的三层真相（v9e/v9f 实验全记录）

前述"OkHttp CookieJar 覆盖"结论**只对了一部分**（第一层），后续对照实验揭示完整机制：

**官方版 HTTP 栈的真实结构（源码实锤）：**
1. OkHttp 的 `.cookieJar(...)` 在官方版 `HttpHelper.kt` 里被**注释掉了**（`//.cookieJar(cookieJar = cookieJar)`）——OkHttp 层根本不装 CookieJar
2. 真正的注入路径是 `NetworkInterceptor`：仅当请求头带 `CookieJar:1` 标记（=enabledCookieJar=true）时，`CookieManager.loadRequest()` 把数据库 cookie merge 进请求——**v9e 关掉这层是对的**（日志 `CookieJar:1` 消失证实）
3. **但 `AnalyzeUrl.setCookie()` 无条件执行**（不管 enabledCookieJar）：`CookieStore.getCookie(domain)`（数据库+会话）与手动 Cookie 头 merge，`mergeCookiesToMap` 的 reduce 语义=**后传入覆盖先传入**，调用序 `mergeCookies(dbCookie, manualCookie)` → 手动头键优先，但数据库里**手动头没有的键**（ltmid_v2/account_mid_v2 等）会补进来

**对照实验结果（legadoT，诊断桩逐步验证）：**
- v9f 清域（cookie.removeCookie）后**legadoT 也开始 -100**！说明库里 merge 进来的 `ltmid_v2=0cck94mty7_mhy` 等键是**服务端下发的会话标识，与 ltoken 配对才有效**，清域反而破坏配对
- 手动拼回相同 ltmid_v2 仍 -100 → **该 ltoken 已被服务端作废**（00:56 同一 token 还全通，01:41 后失效；期间用户在官方版反复触发 -100 约 9+ 次，触发米哈游风控吊销旧会话）

**最终因果链（官方版 -100 全解释）：**
1. 官方版 App 数据库 `api-takumi.mihoyo.com` 域存有**很久以前 WebView 登录的旧会话 cookie**（旧 ltmid_v2 等）
2. `AnalyzeUrl.setCookie()` 把旧 ltmid_v2 merge 进手动 Cookie 头 → 与新 ltoken 配对错乱 → 服务端 -100
3. 反复 -100 触发服务端风控 → **旧 ltoken 被吊销**（导致后来 legadoT 也失败）
4. 此时重新获取 token 才是正解（不是当初的"重获 token 治不好"——那是 v9e 之前的覆盖场景，v9e 后场景变了）

**最终正确做法（v9g 方向）：**
- enabledCookieJar=false（切断 NetworkInterceptor 注入路径）
- **不删除域 cookie**（ltmid_v2 是配对必需品），如需清理只精准删旧认证键（cookie.removeCookie(url, key) 单键删除），保留服务端下发的会话键
- 若仍 -100：token 已被服务端吊销 → 重新获取 token（配对会重新生成）

### 8.6 【260904c 最终修复 v9g】ltmid_v2 是必需配对键（A/B/C 对照实锤）

用户提供新完整 cookie 后的三组对照实验（legadoT，enabledCookieJar=false，干净环境）：
- A（ltoken_v2+ltuid_v2+account_id+account_id_v2 四基础键）→ **-100**
- B（A + ltmid_v2 + account_mid_v2 + _MHYUUID）→ **OK roles=1**
- C（完整 cookie 全量）→ **OK roles=1**

**结论：米哈游服务端校验 ltoken_v2 与 ltmid_v2 的配对关系，缺 ltmid_v2 必 -100。**

官方版失败的完整解释（比 8.5 更简明的最终版）：
- 官方版任务手动 Cookie 头只有 4 基础键（缺 ltmid_v2）
- `AnalyzeUrl.setCookie()` 无条件把官方 App 数据库 cookie merge 进来补键——官方库里的 ltmid_v2 是旧 WebView 会话的值（与新 ltoken 不配对）或根本没有
- → 配对断裂 → -100；legadoT 能成功纯因库里恰好存着与当前会话匹配的 ltmid_v2

**v9g 修复方案（双版本通用，legadoT 实测 5 角色全通过）：**
1. 登录 UI 改为单"Cookie"输入框：粘贴 F12 `document.cookie` 全量输出
2. `source.put('mhyCookie', raw)` 整段存储，请求时 `__cookie()` 直接全量发送
3. merge 语义上手动头含全部键 → 官方库旧值全被覆盖，不再依赖任何库内 cookie
4. login() 校验提示：缺 ltmid_v2 时警告"会话标识缺失可能仍失效"
5. 保留旧版 ltoken/ltuid 两个字段的 fallback 兼容路径

配套：App 内已存同版（id=miyoushe_checkin_task）

### 8.7 排查方法论总结（本次 -100 三阶段演进）

1. **v9e 阶段**：怀疑 OkHttp CookieJar 覆盖 → 关 enabledCookieJar（对，但只切断了一层）
2. **v9f 阶段**：怀疑库 cookie 是污染源 → 清域（**错**，反向实验证明它们是必需配对键，清域反而把 legadoT 也搞挂了）
3. **v9g 阶段**：A/B/C 对照实验锁定 ltmid_v2 必需性 → 完整 Cookie 全量发送（对）
教训：**同一现象（-100）在排查过程中根因会演变**（merge 污染 → token 吊销 → 缺配对键），每一步都要用对照实验实锤，不能停留在上一个假设。
