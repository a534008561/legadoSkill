# 方法：爱丽丝书屋全站改版重建与书源变量迁移（alicesw 261128）

> 案例：`®️爱丽丝书屋（路人二次修复搜索）` 从旧 PHP CMS 源重建为 Next.js + `/api/v1` 双版本（LT/E）书源。
> 本文只写**可复用**的结论与方法，站点细节见 `examples/爱丽丝书屋_alicesw_经验.md`。

---

## 0. 一句话结论

旧源"搜索 0 结果"不是搜索参数问题，而是**整站换架构 + 主域彻底不可达**；重建必须以真实 API 为准，
并额外处理三件以前没踩过的事：**覆盖同名源时 variable 不覆盖**、**`String(java.post(...))` 拿到的是对象不是响应体**、
**eval_js 调试通道对超大响应会截断**。

## 1. 改版识别（三步定位）

| 现象 | 判据 | 结论 |
|---|---|---|
| 旧 `search.html` 返回 404（nginx 页） | 域名能通但路径 404 | 不是封禁，是**路由/架构变了** |
| 首页 HTML 340KB、带 `self.__next_f.push` | Next.js App Router | 数据走 `/api/v1/*`，HTML 里没有列表 |
| 首页 `href` 出现 `/books/123`、`/search`、`/rankings` | SPA 路由 | 书源必须改打 API，不能再解析 HTML |

**反推端点最快的手法**（不抓包）：
1. 取首页 `<script src>` 全量 chunk；
2. 在 chunk 里 grep `"/api/v1`、`get("/books"`、`sort_by`、`uE.get(` 等特征；
3. 找到 axios 实例（`baseURL = origin + "/api/v1"`）后，端点通常写作 `get("/books/".concat(id,"/chapters"))` —— **路径是相对 baseURL 的片段**，
   直接 grep `"/api/v1/xxx"` 往往只命中 1 条（refresh），必须 grep 片段再拼。

**参数名同理从 chunk 反推**：排序映射、榜单周期、翻页参数都写在前端常量里，
例如 `{hot:"hot",popular:"view_count",...}`、`{hot:{periods:["day","week","month"],default:"week"}}`。

## 2. ★主域"假死亡"：IPv6 毒化导致整站不可达

本案第一坑：`www.alicesw.com` 有正常 A 记录（`202.160.128.14`），但手机 DNS 同时给出
`2001::67e4:823d`（Teredo 段）这类**不可路由 AAAA**。OkHttp 先连 IPv6 → 15s connect timeout →
整次请求失败，**表现和"站点跑路"一模一样**。

判据与绕法：
- `java.ajax` / `java.get` 报 `failed to connect to <host>/<ipv6> ... after 15000ms` 时，**不要下"站点已死"结论**；
- 用 **发布页 / 备用域名 / 另一条线路** 交叉验证：只要有一条通，就是 DNS/IPv6 问题；
- 书源侧无法改 DNS，正解是**把书源入口收敛到发布页解析出的可用线路**（本案线路全部 IPv4-only，直接可用）；
- 附带：`java.connect(url).timeout(ms)` **不存在**（报 `找不到函数 timeout`），别指望在规则里缩短探测超时。

## 3. 发布页三层链路解析（爱丽丝式）

```
发布页 xn--vcsx64d.asw4.cc
  ├─ <a href="javascript:jump('BASE64')">  → 永久地址 / 备用地址（base64 解出 URL）
  └─ 备用地址（als1007.space）
        └─ 2 秒跳转页：<a id="redirectButton" href="目标"> + const targetUrl="目标"
              └─ 选线页 alicesw1.quest
                    └─ var u1=r('semoh.5wsecila.www//:sptth')  ← 字符串反转，= https://www.alicesw5.homes
```

**通用抽取器要同时认这 4 类特征**（缺一类就漏线路）：

```js
/jump\(['"]([A-Za-z0-9+\/=]+)['"]\)/g      // base64 载荷
/=\s*r\(['"]([^'"]+)['"]\)/g               // r('...') → 反转还原
/(?:targetUrl|location(?:\.href)?)\s*=\s*["'](https?:\/\/[^"']+)["']/g
/href=["'](https?:\/\/[^"']+)["']/g        // 需按域名关键字过滤，别把 chrome/firefox 下载链接当线路
```

**中转页 vs 线路页要分开**：`asw4.cc` / `als1007` / `alicesw1.quest` 只是"跳板"，
必须继续跟进一层（BFS，深度 ≤3）；把跳板当线路存下来，用户点了就是空白。

**可用性验证用轻端点**：`/api/v1/config/public`（约 3KB），既能判活又能顺带测 ms；
不要用首页（340KB）验证，7 条候选就是 2MB 流量。

## 4. ★新坑：覆盖同名书源时 `variable` 不会覆盖（整源指向死域名）

**症状**：保存新源后，`searchUrl` 里 `{{ASW_ul(source)}}` 解析成**旧域名**，请求直接超时，
看起来像"新规则没生效"。

**根因**：`bookSourceUrl` 是主键；覆盖同名源时 `variable`（运行时变量）**保留旧值**，
即使 JSON 里带了新的 `"variable"` 字段也不生效（LAN `saveBookSource` 与 MCP 保存都一样）。
旧源把 `sourl` 存在 variable 里 = 新源一装上就被旧值劫持。

**正解（两条一起用）**：
1. **变量读取必须做结构校验**，结构不符就回退默认，绝不直接信任 `sourl`：

```js
function ASW_ul(sv) {
    var d = "https://www.alicesw5.homes";
    try {
        var o = JSON.parse(String(sv.getVariable() || ""));
        if (o && o.lines && o.lines.length) {          // ← 关键：必须存在 lines 结构
            var s = String(o.sourl || "");
            for (var i = 0; i < o.lines.length; i++)
                if (String(o.lines[i].u) === s) return s.replace(/\/+$/, "");
            return String(o.lines[0].u).replace(/\/+$/, "");
        }
    } catch (e) {}
    return d;                                           // 旧格式/损坏 → 默认线路
}
```
2. 升级路径：登录面板的 `ASW_cfg()` 发现无 `lines` 时重建默认结构并在用户首次操作时落盘（自然迁移）。

> 通用原则：**书源变量是"可能来自上一条命"的持久数据**，任何 `source.getVariable()` 都要当外部输入做校验。

## 5. ★新坑：`String(java.post(...))` 拿到的是 Response 对象，不是响应体

实测（LT，`java.post` 返回 jsoup `Connection.Response`）：

```
typeof r        = object
typeof r.body   = function
String(r).length      = 48     ← 类名/toString，不是 JSON
String(r.body()).length = 5799 ← 真响应体
```

所以登录/校验这类**把响应喂给 JSON.parse** 的代码，必须取 `.body()`；
写错时的症状极具欺骗性：`JSON.parse` 抛错 → 被 try/catch 吞 → 界面只报"登录失败"，
而 `java.ajax`（返回 String）在同一环境是正常的，容易误判成接口问题。

**双版本通用 helper**：

```js
function ASW_body(r) {
    try { if (r && typeof r.body === "function") return String(r.body()); } catch (e) {}
    return String(r);                    // 兼容返回 String 的实现
}
ASW_body(java.post(url, body, {"Content-Type":"application/json"}))
ASW_body(java.get(url, {"Authorization":"Bearer " + tok}))
```

> 另一个相关坑：`java.get` / `java.post` 在 **非 2xx 会直接抛 HttpStatusException**（读不到错误体）；
> 需要看错误 JSON 时改用 `java.ajax`（返回堆栈字符串，不抛）。

## 6. ★新坑：eval_js 调试通道对超大响应截断（≠ 站点截断）

`/api/v1/books/{id}/chapters` 对 6926 章的书返回约 1.8MB JSON。
在 **MCP `eval_js`** 里 `java.ajax` 拿到 **固定 1,802,436 字节**、末尾是半个 key（`"publis`），
换 `Accept-Encoding: identity` / 加 cache-buster / 加 limit 参数都一样 → 说明是**通道侧上限**；
同一 URL 走 `debug_source` 的规则链路却是 **完整 6926 条**。

结论：
- **不要用 eval_js 的大响应长度判断接口/站点是否截断**，要看真实规则链路（debug_source / LAN getChapterList）；
- TOC 仍建议加"截断修复"兜底（成本极低）：

```js
function ASW_fixJson(s) {
    try { return JSON.parse(s); } catch (e) {}
    var k = s.lastIndexOf('{"chapter_no"');       // 找最后一个完整对象起点
    if (k > 0) { try { return JSON.parse(s.substring(0, k).replace(/,\s*$/, "") + "]}"); } catch (e) {} }
    return null;
}
```

## 7. E 版（legado-E）实测补充

| 事项 | 结论（源码 + 真机） |

| `source.setLoginUi(x)` / `source.loginUi = x` | **不可用**：`NativeBaseSource.has/get` 屏蔽 `setXxx`（底层有同名 getter 时返回 NOT_FOUND），`put` 只放行 `variable` ⇒ **无法从 JS 改 loginUi**，动态按钮文案只能靠 `viewName` |

## 8. 登录：图片验证码型 API 的完整配方（已实测通过）

```
POST /api/v1/auth/captcha   body {}                    → {data:{captcha_id, image(data:image/png;base64,...), expires_in}}
POST /api/v1/auth/login     {email,password,captcha_id,captcha_answer} → {data:{tokens:{access_token,refresh_token}, user}}
GET  /api/v1/users/me       Authorization: Bearer <access_token>       → {data:{nickname,user_no,...}}
```

Legado 侧：
```js
var cj = JSON.parse(ASW_body(java.post(ul+"/api/v1/auth/captcha","{}",{"Content-Type":"application/json"})));
var code = String(java.getVerificationCode(String(cj.data.image)));   // data URI 直接可弹验证码框（<64KB 限制）
```
- `getVerificationCode` 要求**后台线程**：登录按钮 action 在 `lifecycleScope.launch(IO)`，满足；
- `expires_in` 300s，**调试时手工 OCR 要卡时间**；一次成功即证明字段名/大小写全部正确；
- 站点全站免费时，登录只是可选增强，但**契约必须验过**，否则用户点了必失败。

### 10.2 新踩到的接口坑

- **Legado 没有 `java.delete`**（`typeof java.delete === 'undefined'`，只有 get/post/head/ajax）。
  发 DELETE 只能 `Packages.org.jsoup.Jsoup.connect(url)` + `.method(Packages.org.jsoup.Connection.Method.DELETE)`
  + `.header("Authorization", ...)` + `.ignoreContentType(true)` + `.execute()`；★该分支未获登录态实测，需真机验证。
- `java.connect(url)` **不是** jsoup Connection（没有 `.method/.header`），它直接发 GET 并返回 `StrResponse`，别拿它改方法。
- 登录接口的 token 也能通过 `loginHeader` 影响**所有**源请求（含图片/发现页），所以登录后书架、阅读记录、评论都无需逐条拼头。

### 10.3 变量结构迁移

旧源变量是 `{z,s,co,urls[],sourl}`，新源用 `{sourl,pub,urls[],lines[{u,ms}],s,co,tags,tok,user}`。
`ASW_cfg()` 里做一次迁移：`lines` 缺失而 `urls` 存在 ⇒ 由 urls 生成 lines；
`ASW_ul()` 仍保留"无 lines 时信任 sourl"的兼容分支，但**显式排除已死的 `www.alicesw.com`**，
避免旧值把整源钉死在死域名上（这是首轮最大的坑）。

## 11. v2.1：书架为空的两个真根因（★重要，跨站通用）

用户报「登录后账号网络书架打开为空」。两个独立原因叠加，缺一不可：

### 11.1 `loginHeader` 不会附加到发现页/临场请求 → 401

`source.putLoginHeader({"Authorization":"Bearer ..."})` 后，`source.getLoginHeader()` 能读回，
但发现页条目（`exploreUrl` 里的绝对 URL）请求仍是 **401**（HTTP 日志实锤），
说明这些路径的 `AnalyzeUrl` 没走 `hasLoginHeader=true`。

★**正解：把 token 放进书源 `header` 的 `@js:` 动态表达式**，让**所有**请求都带：

```json
"header": "@js:var o={};try{o=JSON.parse(String(source.getVariable()||\"\"))||{}}catch(e){};var h={\"User-Agent\":\"...\",\"Accept-Language\":\"zh-CN,zh;q=0.9\"};if(o.tok){h[\"Authorization\"]=\"Bearer \"+o.tok;}JSON.stringify(h);"
```

- LT：`BaseSource.getHeaderMap` 用 `extractInlineJs(header)` + `evalJS` 求值；
- E：`startsWith("@js:", true)` → `evalJS(...)`；
  两版都支持，`source` 在 evalJS 里可用。
- 实测错误 token 对公开接口无影响（`/search/books`、`/books/{id}` 仍 200，服务端按匿名处理），
  所以"全站带 Authorization"是安全做法，不需要逐接口挑。
- `putLoginHeader` 保留也无害（同值覆盖），但**不能只靠它**。

### 11.2 书架/阅读记录是**扁平字段**，不是嵌套 `book{}`

`GET /api/v1/bookshelf?page=1&page_size=20` 返回：

```json
{"data":{"items":[{"book_id":35212,"book_title":"...","book_author":"...","book_cover_url":"/api/v1/media/...","chapter_count":13,"book_no":867041,"book_state":"active","id":4719019,"group_id":43872}],"pagination":{...}}}
```

- 只有 `book_id` 没有 `id` 的语义（`id` 是书架条目 id），也没有 `title/cover_url/synopsis`；
- `data` 里是 `pagination`，**不是** `total/total_pages`；
- 阅读记录 `GET /reading-history` 同构（`data.items[]`）。

★列表解析必须兼容三形态，否则列表静默为 0：

```js
var bk = b.book ? b.book : b;
var id = b.book_id ? b.book_id : (bk.id || 0);
var title = b.book_title ? b.book_title : bk.title;
var author = b.book_author ? b.book_author : (bk.author_name || ...);
var cover = b.book_cover_url ? b.book_cover_url : bk.cover_url;
```

判据指纹：**接口 200、日志正常、列表 0 条** ⇒ 先打印 `Object.keys(items[0])` 对字段，
不要怀疑接口或鉴权。

### 11.3 评论区脏数据

真实数据里存在 `user=null` + `content=""` + 有回复 的已删评论，以及 `is_anonymous=true`。
展示兜底：`is_anonymous→匿名用户`、无昵称→`已注销用户#user_no`、空内容→`（原评论已删除）`、
`created_at` 为空时不打印时间。否则会出现「👤用户 | 空行」这种破格式。

### 11.4 详情页 → 登录界面「书籍ID」预填（原版功能）

旧源在 `ruleBookInfo.init` 里把当前书 id 写进登录信息表；新站同样做法：

```js
var si = source.getLoginInfoMap();
var so = {};
var it = si.keySet().iterator();
while (it.hasNext()) { var k = String(it.next()); so[k] = String(si.get(k)); }
so["书籍ID"] = String(d.id);      // 用详情接口返回的真实 id（书号路由也已解析）
source.putLoginInfo(JSON.stringify(so));
```

★必须**手工组 JSON**：`JSON.stringify(java.util.Map)` 在 Rhino 下不可靠，要先遍历 `keySet()` 转成纯 JS 对象。
★实测：打开任意详情页后 `getLoginInfoMap()` 里 `书籍ID` 即为该书 id，且不会清掉用户已填的账号/标签等其他键。

### 11.5 E 版专有坑：header 里的 `ConsString` → ClassCastException

现象（用户报）：E 版「加入书架」失败，`Operation failed: JavaException: java.lang.ClassCastException:
org.mozilla.javascript.ConsString cannot be cast to java.lang.String`；LT 版同一份代码正常。

根因链：
1. E 的 `fun post(urlStr, body, headers: Map<String,String>)` / `get(...)` **只使用传入的 headers**，
   不合并 `source.header`（所以不能靠全局 header 兜底）；
2. Rhino 把 JS 对象字面量转成 Java `Map` 时**泛型擦除**，value 不做 `String` 强转；
3. `"Bearer " + o.tok` 在 Rhino 里是 `ConsString`（不是 `java.lang.String`），进 Map 后在
   jsoup `.headers(map)` 迭代取值时才炸。
4. LT 同位置是 `headers: Any?` + 自有 `parseJsRequestHeaders`，能容忍 → **LT 绿、E 红**。

判别指纹：headers 全是字面量时正常（所以登录能成功），**只要某个值含 `+` 拼接就 CCE**。

修法（两版通用，已验证）：
```js
function ASW_bearer2(tok) {                     // loginUrl 作用域
    var s = "Bearer " + tok;
    try { return java.bytesToStr(java.strToBytes(s)); } catch (e) { return s; }
}
// 规则 @js 作用域（jsLib 不能直接用 java，必须显式传）
function ASW_bearer(jv, tok) { ... jv.bytesToStr(jv.strToBytes(s)) ... }
```
`strToBytes/bytesToStr` 都是声明了具体类型的 Java 方法，ConsString 在调用边界被强制转成
`java.lang.String`，往返后就一定是真 String。实测 `.length` 返回 Java 方法、带真实 token 请求 200。

★排查顺序：E 报 CCE 时先看**该行有没有字符串拼接**，不要怀疑 JSON/接口；
`JSON.stringify({...})` 之后整体作为 `String` 参数传的（如 `putLoginHeader`）不受影响。
