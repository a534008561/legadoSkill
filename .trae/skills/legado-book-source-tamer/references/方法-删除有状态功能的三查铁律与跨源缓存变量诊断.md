# 方法：删除「有状态功能」的三查铁律 + 跨源 CacheManager 变量诊断（ExHentai 收藏夹 IP 限制彻查篇）

> 案例源：🅴ExHentai 订阅源 v6.7→v6.9（261114）
> 症状：LT 版收藏夹「收藏页获取失败 · IP 限频」，E 版同一手机同账号完全正常
> 成品：`/workspace/exhentai/exhentai_rss_v6_9.json`（双端口 LAN 落库，LT 回读 diff=0）

## 一、案例回顾（时间线）

| 版本 | 动作 | 后果 |
|---|---|---|
| v6.4~v6.6 | hosts IP 直连功能全量（面板 UI + 8 处 dnsIp 注入 + 18 IP 池） | 用户手机路径 TLS ClientHello 掐 SNI，直连不可行 |
| v6.7 | 用户裁定删直连 → **只删了面板 UI（loginUrl 4 函数 4 行）** | ruleContent/loginCheckJs/sortUrl/searchUrl 共 **8 处读取注入逻辑残留**；**CacheManager 里 273 字符 IP 池值残留** |
| v6.8 | 名单缓存上线，收藏夹开关默认关（header 一次性迁移 ehFavReset68） | 旧用户变量 `ehFavPanel=1` 被重置，但 `ehHostsIp` 原样躺着 |
| 故障 | 用户开收藏夹开关 → LT 每次请求 `favorites.php` 带 `dnsIp=IP池` → 直连共享 IP → 站方 banned 页 | favErr 判定「IP 限频」；E 版缓存库无残留走正常 DNS → 正常 ⇒ **同手机同账号两版行为分裂** |

## 二、根因定位方法论（双组对照实验）

用 MCP `eval_js`（绑任意书源）在 LT App 真机环境直接做对照实验：

```
A组（复现故障路径）：url + ,{"headers":{...},"dnsIp":"<残留IP池>"}
  → 239B "This IP address has been temporarily banned due to an
    excessive request rate... share the IP address with someone who does"

B组（正常路径）：url + ,{"headers":{...}}   # 不带 dnsIp
  → 96921B 正常收藏页（2.2s）
```

结论：出口 IP 根本没被 ban；被 ban 的是**共享直连 IP 池**。favErr 的「IP 限频」文案判定条件是响应体含
`temporarily banned`，与 LT 看到的现象一字不差 ⇒ 请求确实走了直连路径。

要点：
- **同手机同账号 ≠ 同路径**：两版 App 是独立进程/独立缓存库，任何「状态残留」类差异都会分裂行为。
- **favErr 文案是高价值指纹**：故障文案里的判定关键词（banned/Sad Panda/空白）直接指回响应体形态，
  先从代码里找「什么响应体会打出这句话」，再反向复现。

## 三、CacheManager 全局键空间（源码级新知）

```kotlin
// BaseSource（LT/E 同款）
fun put(key, value) { CacheManager.put("v_${getKey()}_$key", value) }
fun get(key)        = CacheManager.get("v_${getKey()}_$key") ?: ""
```

- 键 = `v_<源URL>_<变量名>`，**订阅源与书源 URL 相同时共享同一存储**。
- **MCP eval_js 绑任意书源即可 `cache.get/put` 读写其他源的变量**（跨源变量诊断/清理通道）：
  ```js
  // 诊断：读 ExHentai 源的全部面板变量真身
  cache.get('v_https://exhentai.org/_ehHostsIp')
  // 止血：当场清掉残留（无需等新版导入）
  cache.put('v_https://exhentai.org/_ehHostsIp', '')
  ```
- RssSource 落库的 `variable` 字段被 GSON 丢弃（LT/E 同）⇒ 面板变量唯一真身=CacheManager，
  `/getRssSources` 回读 variable 恒空属正常，别被它骗了。
- 旧结论「CacheManager 无 API 可删」错误——eval_js cache.put 空串即可清。

## 四、修法三层（v6.9 落地）

1. **8 处 dnsIp 注入逻辑全删**：
   - ruleContent 主 OPT：`var hip=...;var OPT=...,+(hip?dnsIp...)` → `var OPT=',{"headers":'+PAGE_HDR+'}'`
   - 页内脚本 hip() 函数 ×2 → 桩函数 `function hip(){return "";}`
   - 页内 POST `if(_hp){_o.dnsIp=_hp;}` 死代码删除
   - 懒加载 fetchOne 的 hip/dnsIp 拼接删除
   - loginCheckJs / sortUrl hostsVal+watched / searchUrl 的 hip 块删除
2. **header `<js>` 一次性迁移清残留**（对新老机器都生效）：
   ```js
   // ★新守卫：ehFavReset68 已被 LT 消费过，旧守卫不会再触发
   try { if (!g('ehFix69')) { source.put('ehHostsIp', ''); source.put('ehFix69', '1'); } } catch (eF69) { }
   ```
   - 迁移守卫每次都要用**新键**：旧守卫执行过一次就永久跳过，清不了新残留。
3. **MCP eval_js 当场清空存量**（导入新版前止血，用户立刻可用）。

配套：variableComment 里的旧功能说明同步删除（否则面板说明与行为不一致会误导排障）。

## 五、通用铁律：删除「有状态功能」必须三查

> 删功能 ≠ 删 UI。只删 UI 入口，等于把功能变成**幽灵功能**：代码还在读、库里还有值，就还在生效。

1. **查 UI 入口**：loginUi 行、loginUrl 里对应函数。
2. **查全部代码读取点**：对功能变量名在**所有字段**（ruleContent/loginCheckJs/sortUrl/searchUrl/
   ruleNextPage/ruleArticles/header/preloadJs/…）grep，一处不漏。
3. **查已落库变量残留值**：CacheManager 里的旧值不会随源删除/更新而消失；
   eval_js `cache.get('v_<URL>_<名>')` 排查，发现残留用 cache.put('') 清掉 + 新版 header 迁移兜底。

反面教材：v6.7 删直连只做了第 1 步 → v6.8 没查 → 用户报障 v6.9 才修。
正面流程：删 UI 的同一个 commit 里，把 2/3 一起做掉，并写迁移守卫。
