# 方法：封面解密跨版本差异与站点排序参数失效

> 沉淀日期：2026-11-27　｜　来源：2048ai2 / 麻豆短剧免VPN 书源（LT 版封面空白、E 版正常；发现页两个 tab 内容相同）
> 前置阅读：**[方法-图床AES加密图片解密](方法-图床AES加密图片解密.md)**（魔数探测、coverDecodeJs 双钩子、缓存中毒与 `?v=N` 自愈）；**[[双版本 E 版兼容]]**

## 一、症状与第一时间分流

同一个 `coverDecodeJs`，**E 版封面正常、LT 版封面空白**，搜索/详情/目录/正文/播放全绿。

- 历史经验多是反过来（E 版 API 缺失导致 E 挂、LT 正常，见双版本兼容专题），所以这次不能直接套旧结论。
- **第一刀永远是分版本对照**：先问清"哪版好哪版坏"。只要有一版能显示，就证明书源规则和解密算法本身是对的，不需要再怀疑算法、Referer、域名可达性。

## 二、Legado 封面解密链路（源码级，两版一致）

1. `BookList.analyzeBookList` → `getSearchItem`：`searchBook.origin = bookSource.bookSourceUrl`。
2. 发现页 adapter → `CoverImageView.load(searchBook)` → `load(..., searchBook.origin, ...)` → `RequestOptions.set(OkHttpModelLoader.sourceOriginOption, sourceOrigin)`。
3. `OkHttpStreamFetcher.loadData`：`source = SourceHelp.getSource(sourceUrl)`。
4. `onResponse`：`if (ImageUtils.skipDecode(source, isCover=true)) { 原样返回; }`，否则 `ImageUtils.decode(src, responseBody!!.byteStream(), true, source)`。
5. `ImageUtils.getRuleJs`：`is BookSource -> source.coverDecodeJs`；source 为 null 时返回 null → `skipDecode=true` → **原始加密字节直接进 Glide** → 图裂。

结论：发现页封面的 `coverDecodeJs` 是否执行，只取决于 `SourceHelp.getSource(searchBook.origin)` 能否命中书源；规则层能通过 `source.put/get` 写入变量来证明执行过。

## 三、本例逐项证伪（按此顺序做，别跳步）

| 假设 | 对照实验 | 结果 |
|---|---|---|
| 解密算法错 | App 内执行 XOR，把结果与原始密文分别喂 `BitmapFactory.decodeByteArray` | 解密后 600×900 可解码，原始密文 null → **算法正确** |
| 图床防盗链 Referer | 4 组 Referer（mdaiapi / 2048ai2 / 无 / 图床自身）下载同一 URL | 全 200、魔数全 `cde8cdd0` → **Referer 无关** |
| 站点有明文图 URL | 抓 SPA 主 JS，读 `Td/Pc/Db/Fb/Bb/Hb` | 前端自己 `fetch → 前100字节 XOR → data: URI`，**没有明文 URL**，只能靠 coverDecodeJs |
| 书源绑定错 | 源码链路确认 `origin=bookSourceUrl` 且 E 版同规则正常 | 命中正常，**非绑定问题** |
| **Glide 缓存了早期加密图** | 封面 URL 加版本参数 `?v=3` 使缓存 key 变化 | **LT 立即正常** → 根因确认 |

> ★关键认知：**重启 App 不会清 Glide 磁盘缓存**。早期（尚未写 coverDecodeJs 时）加载过的加密图被缓存，之后改规则也一直读旧缓存；E 版因首次加载时规则已完备，所以正常。症状就是"怎么重启都不变"。

## 四、正式修法（已真机双端验证）

1. **封面 URL 加版本参数**：
   ```js
   return u.split('madou.ymkizv84.work').join('acfan.ymkizv84.work')+'?v=3';
   ```
   `ruleSearch` / `ruleExplore` / `ruleBookInfo` 三处同时改；以后再改解密算法就把 `v` 递增。
2. **coverDecodeJs 加自包含下载兜底**：`result` 读不到内容时，用 `new Packages.java.net.URL(String(src||''))` 重新下载再解密。这样即便某版本传入的 `result` 形态不同也不影响。
3. **Rhino `typeof` 必须 try 包裹**（老坑复述）：`typeof result.read` 对 Java `byte[]` 会直接抛 `InternalError`，不是返回 undefined：
   ```js
   try{var t=typeof result.read;isStream=(t==='function');}catch(e){isStream=false;}
   ```
4. **失败兜底 `return result` 原字节**，绝不 `return null`；`ByteArrayOutputStream.write(int)` 逐字节写，不要给 `byte[]` 元素赋 255。

## 五、诊断桩：在不改 UI 的前提下证明 coverDecodeJs 跑没跑

把下面这行插进 coverDecodeJs 开头，保存后刷新发现页，再用 `eval_js` 读：

```js
try{source.put('md_cover_probe','START|'+Date.now()+'|'+String(src||''));}catch(e){}
```
```js
String(source.get('md_cover_probe')||'')
```

- 有值 → 解密链路执行过，问题在返回类型 / 图片解码 / 缓存。
- 空值 → `skipDecode` 跳过，去查 `SourceHelp.getSource(origin)` 与 `SearchBook.origin`。
- 注意：MCP 会话可能 `Session not found`，LAN 1122/1125 的 `/getBookSource` 仍可回读规则；诊断完务必换回正式版。

## 六、附带坑：站点 `sortBy` 被后端忽略 → 找 REST 子路径

发现页两个 tab 内容完全一样，对比原始 JSON：仅 3 条记录的 `heatCount` 实时 +2，ID 与顺序全同。

- 探测 `sortBy=heat|latest|newest|createdAt|publishedAt|id|hot|heatCount|views|viewCount`：只有 `heat` 和 `latest` 两个值被接受，但**返回同一顺序**；其他值返回空数组。
- 正解不是继续调参数，而是试 REST 子路径：`GET /short-dramas/latest?productId=1&page=1&size=12` 返回 `[349,307,310,311...]`，与热榜 `[89,95,143,218...]` 完全不同。
- 判据口诀：**两个 tab 内容全同 → 先 diff 原始 JSON；若仅实时计数字段不同 → 后端忽略 sort 参数 → 转向子路径/独立 endpoint 探测**。不要把这种站点缺陷误判为书源 `exploreUrl` 写错。

## 七、避坑清单

- 分版本差异先做"哪版好"的对照，不要默认旧经验方向。
- `Content-Type: image/jpeg` 不等于真 JPEG，**先查魔数**。
- 换域名、改 Referer 都不能替代"缓存 key 变化"这一招。
- 前端 JS 用 `data: URI` 显示图片 ⇒ 站点没有明文图可用，别在 `coverUrl` 上白费功夫。
- 改完解密逻辑必须递增 `?v=N`，否则用户看到的还是旧缓存，会误判"改动无效"。
