## 一、站点识别与域名形态

笔趣阁家族站点常有多个域名共享同一书库，但**模板可能不同**：
- wap.shoujixs.net —— UTF-8，hot_sale/articlecon 模板（主线路）
- open-ki.jishouzj.cc / open-ki.jisysxs.cc —— UTF-8，bookbox/chaptercontent 恰当模板
- www.shouj移动版.net —— GBK，bqg PC 模板（#content），结构与 WAP 系完全不同，**不可混用**

**铁律**：自定义网址功能必须校验/提示「GBK PC 模板不可填入」。GBK PC 站搜索编码是 GBK，与 UTF-8 WAP 站搜索 POST body 编码不同。

## 2.5 Cookie 键级搜索限频终版破解（四组对照实验定案）

**机制**：首次成功搜索 → 服务端下发 `Set-Cookie: ss_search_delay=1; Max-Age=120` → 此后 120 秒内请求 Cookie **带此键（无论值 1/0）** → 服务端查时间窗拒绝，返回 `<script>alert("搜索间隔: 120 秒")</script>`（200 伪装成功）。判据 = **键存在性**，不是值。

**四组对照**（App 内 eval_js 实测）：
| 方案 | 结果 |
|---|---|
| 窗口内普通搜索 | ❌ 被限 |
| 显式 `Cookie: ss_search_delay=0` 头 | ❌ 仍被限 |
| `removeCookie` + `setCookie('ss_search_delay=0')` 双保险 | ❌ 仍被限（setCookie 把键又写回去）|
| **纯 removeCookie（请求发起前）** | ✅ **破解成功** |

**唯一解**：searchUrl 的 URL 选项 `js` 里每次搜索前 `cookie.removeCookie(域名)`（服务端认不到键 = 新访客放行）。落在 Legado 里：
```
searchUrl: @js:(function(){var h=...读变量拼域名...;
  return h+'/search/,{\"js\":\"try{cookie.removeCookie('https://xxx/')}catch(e){}\",\"method\":\"POST\",\"body\":\"searchkey={{key}}&t=1\"}';
})()
```
注意：①选项 JSON 必须拼进 @js 返回串（@js: 贪婪吃满整串）②js 选项执行环境绑定 cookie=CookieStore ③**尾部多一个 `}` 会让 GSON 解析失败静默降级 GET**（现象：HTTP 日志出现 GET /search/）——生成后必须模拟求值并 `json.loads` 校验选项。

**配套**：concurrentRate="1,3000" 防轰炸；loginCheckJs 检测 `alert(` 极短页（<500B）→ 正则提取文案 → `new Packages.io.legado.app.help.http.StrResponse(baseUrl, tip)` 改写为可读提示（短词「关键字最少 10 个字符」=trim 后 ≥4 汉字，UTF-8 字节数判据，空格补位被 trim 无效）。

**排查陷阱**：MCP clear_cookies 后「立即成功」不是清 Cookie 生效，是 120s 窗口恰好自然过期——**时序对照实验必须含"清后立即重发"组**（本案清后立即重发仍被限，才暴露真机制）。# 手机小说 shoujixs.net 书源制作全记录（261030）

## 2. 限频破解（本次最大堵点）

站点写入 `ss_search_delay=1` Cookie 后 120 秒内搜索（任何关键词）返回：
```html
<script>alert("搜索间隔: 120 秒");window.history.go(-1);笔趣阁家族限频Cookie
```
- **与 IP 无关**（沙盒无 Cookie 客户端同时段正常）
- **与关键词无关**（新词同被限）⇒ 纯 Cookie 会话级
- **解除 = 清该 Cookie 立即恢复**（App 内清 Cookie 或等 120s）
- 书源对策：`concurrentRate="1,120000"` + 注释说明
- 排查判据：搜索 0 结果 + 响应体以 `<script>alert(` 开头 ⇒ Cookie 级限频页

**对照实验流程（值得复用）**：debug 0 结果 → 查 HTTP 日志响应体 → 发现 alert 限频页 → 沙盒 Python 无 Cookie 同时段正常（排除 IP）→ get_cookies 发现 ss_search_delay=1 → 清 Cookie → 立即恢复。全程零频率探测，全靠响应体判据。

## 3. 三模板统一规则设计

### 详情页（og meta 三模板统一）
```
name: meta[property=og:novel:book_name]@content||meta[property=og:title]@content
```
### 目录（锚点切割法 + 双容器分支）
- wap 模板：div.directoryArea **未闭合**（最新5章+全部章节同容器）→ `h2 ~ p a` 锚点切割
- open-ki：规范双容器 → `divs.get(1).select('p a')`
- 分页「下一页」与「上一页」同容器 ⇒ **用按钮文本「下一页」判据**（`:nth-of-type(2)` 也能用但文本判据更稳）
- 末页 javascript:void(0) → return null 干净终止
### 正文（三容器 + Ajax 兜底）
- #articlecon（wap）/#chaptercontent（open-ki）/#content（PC）

## 3.5 发现页分组布局优化（用户实测反馈：前缀太长显示不全）

**问题**：`周榜·玄幻奇幻` 这类「板块前缀+分类名」长标题在 4 列布局（flexBasisPercent 0.25）下显示不全。

**方案**：拆「分组标题行 + 短名子项」两级：
```
out.push({title:'🏆 周榜', url:'', style:{layout_flexBasisPercent:1.0, layout_wrapBefore:true}});  // 独占整行
out.push({title:'玄幻奇幻', url:h+'/top/week1_{{page}}.html', style:{layout_flexBasisPercent:0.25}});  // 短名4列
```
- 分组行 `url:''` 不产生书列表，只当节标题
- 子项全部短名（`玄幻奇幻`/`全部`），板块身份由分组行承担
- 新增子分类（月榜/总榜）必须逐一实测 URL（`/top/month1_1.html` 等）再上架
- exploreUrl 有 aCache 缓存，改后须发现页长按「刷新」

## 3.7 双版本（LT/E）兼容坑：java.post 的 null 参数

**症状指纹**：同一份 content Ajax 兜底规则，LT 版正文完整、E 版返回「内容正在加载中」加载页文本（异常被 try/catch 吞掉，无报错）。

**根因**：E 版 `JsExtensions.post(urlStr, body, headers: Map<String,String>)` 是 **Kotlin 非空参数**——JS 里 `java.post(url, body, null)` 抛 NPE；LT 版同位置可空。同族坑：hexDecodeToByteArray（E 版调用即炸）。

**修法**：`java.post(url, body, {})`——第三参一律传空 Map，双版本通吃。

**E 版调试利器：getBookContent 探针**（比 /image 探针简单）：
1. `POST /saveBook`（测试书，bookUrl 用目标书详情页）→ `GET /refreshToc` → `GET /getBookContent?url=&index=N`
2. 探针脚本把各步结果拼进返回串：result 类型（R1）/ typeof java.post（POST）/ baseUrl（BASE）/ 实际调用的返回长度（API），一次读出炸点
3. **双重缓存陷阱**：①改规则后必须删书重加（BookController 缓存 bookSource）②同 bookUrl 删书重加仍读**正文缓存**（BookHelp 按 bookUrl+chapter 存盘）——验证新脚本必须换**未取过的章节 index** 或换书

## 6. 本次新坑（通用经验）

1. **ruleSearch 字段是 lastChapter 不是 latestChapter**——GSON 未知字段静默忽略，save 后必须回读核对（本次字段直接消失）
2. **@js: URL 规则的选项 JSON 必须拼进返回串**：`@js:(...),{json}` 的 JSON 会成 JS 语法一部分；正确：`return h+'/search/,{\"method\":\"POST\"...}';`
3. **App jsoup 展开非法嵌套 p>p**：Python BeautifulSoup 保留嵌套、App jsoup 展开成扁平兄弟 p ⇒ Python 预演与 App 实测 DOM 不同，**规则以 App 实测为准**
4. **java.post(url, body, headers) 三参**，headers 可 null；java.connect 单参只有 GET
5. **307 重定向域名族**：open-ki.* → hua-8b.*（307），Legado 自动跟随，规则按重定向后域名工作
6. **searchUrl @js 里 {{key}} 在 JS 求值后才替换**（replaceKeyPageJs 在 analyzeJs 之后）
7. **debug_source key=章节URL 只走详情→目录**，正文调试靠全链路 debug 或 eval_js 单测
8. **check_source「搜索失效」可能是限频误报**：校验器与 debug 共享 CookieJar，命中限频窗口；App 内手动搜索正常 + HTTP 日志正常阅读流量 ⇒ 误报，间隔 130s+ 再校验
9. **MCP 工具长 JSON 参数易截断/损坏**：15KB JSON 手传 MCP 参数不可靠（本次两次损坏+一次会话过期），**走 LAN web 服务 /saveBookSource 投递**（x-legado-token 头）
10. **java.ajax GET /search/ 是空关键词搜索页**（正常无结果），别误判为解析失败
