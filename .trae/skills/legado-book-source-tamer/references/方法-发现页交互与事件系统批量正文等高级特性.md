## 一、发现页（主界面）的三个隐藏行为

### 1.1 搜索框不是"搜书"，是"筛书源"

这是**最容易被误解**的一点。发现页顶部的搜索框走的是这条 SQL（`BookSourceDao.flowExplore`）：

```sql
select * from book_sources_part
where enabledExplore = 1
  and hasExploreUrl = 1
  and (bookSourceGroup like '%' || :key || '%'
       or bookSourceName like '%' || :key || '%')
order by customOrder asc
```

**它匹配的是「书源分组名」和「书源名称」，不搜任何书籍内容。**

实测语义（4 个书源样本）：

| 输入 | 结果 |
|---|---|
| `趣书吧` | 命中「趣书吧手机版」（名称含）+「八叉书库」（分组含） |
| `39` | 命中同两个（分组 `39趣书吧` 含） |
| `番茄` | 只命中「番茄小说」 |
| `斗破` | **空** ← 证明不是搜书 |

另外还有两个前置条件，很多人不知道：
- `enabledExplore = 1` → 书源必须**开启发现**
- `hasExploreUrl = 1` → 必须**配置了 exploreUrl**

所以"发现页搜不到我的书源"，八成是这两个开关之一没开，而不是搜索词问题。

### 1.2 `group:` 前缀 = 精确按分组筛选

源码 `ExploreFragment.kt:48`：

```kotlin
private const val GROUP_QUERY_PREFIX = "group:"

internal fun exploreGroupFromQuery(query: CharSequence?): String? {
    return query?.toString()
        ?.takeIf { it.startsWith(GROUP_QUERY_PREFIX) }
        ?.removePrefix(GROUP_QUERY_PREFIX)
}
```

- 输入 `group:39趣书吧` → 精确按该分组过滤（走 `flowGroupExplore`，不是 like）
- 输入 `39趣书吧`（无前缀）→ 走 like 模糊匹配
- 从右上角分组菜单点选时，App 会自动把 `group:xxx` 填进搜索框

**实测解析表**：

| 输入 | exploreGroupFromQuery |
|---|---|
| `group:39趣书吧` | `"39趣书吧"` |
| `39趣书吧` | `null`（走模糊） |
| `""` | `null` |
| `null` | `null` |
| `group:` | `""`（空分组） |

### 1.3 收起/展开：同一时间只展开一个

```kotlin
private var exIndex: Int = -1      // 当前展开的行索引，单值！

fun compressExplore(): Boolean {
    return if (exIndex < 0) {
        false
    } else {
        val oldExIndex = exIndex
        exIndex = -1
        notifyItemChanged(oldExIndex)
        true
    }
}
```

- `exIndex` 是**单个 Int**，所以**全局只有一个书源处于展开状态**
- 点另一个书源会自动收起前一个（手风琴模式）
- 点标题左侧箭头：展开→加载 kinds；收起→`flexbox.gone()`
- 长按标题 → 弹出菜单（编辑/置顶/登录/搜索/刷新/删除）

**展开时的加载流程**：

```
点击 → exIndex = position → notifyItemChanged
     → sourceKinds[url] 有缓存？→ 直接渲染
     → 没有 → item.exploreKinds() → 缓存 + 渲染
     → rotateLoading 转圈 → 完成隐藏
```

**关键**：`exploreKinds()` 有**两级缓存**：
1. `sourceKinds`（内存 Map，`onPause` 时 `clear()`）
2. `aCache`（磁盘，`clearExploreKindsCache()` 才清）

所以**改了 exploreUrl 必须点菜单「刷新」**，否则看到的还是旧分类。

### 1.4 交互控件能刷新整个发现列表

`ExploreAdapter.kt:185`：

```kotlin
val sourceUiCallback = object : SourceLoginJsExtensions.Callback {
    override fun upUiData(data: Map<String, Any?>?) {}
    override fun reUiView(deltaUp: Boolean) {
        refreshExplore(item, exIndex, binding)   // ← 清缓存 + 重新加载 kinds
    }
}
val sourceJsExtensions by lazy {
    SourceLoginJsExtensions(context as? AppCompatActivity, source, callback = sourceUiCallback)
}
```

**这意味着**：在 select/toggle/button 的 `action` 里调 `java.reUiView(true)`，就能：
1. 清掉 `exploreKinds` 两级缓存
2. 重新求值 `exploreUrl`（此时 `infoMap` 里已是新选的值）
3. 整个分类列表重绘

**这是"下拉选项改变分类列表"的标准做法**：

```jsonc
{"title":"线路","type":"select","chars":["电信","联通","移动"],
 "action":"java.put('line', infoMap['线路']); java.reUiView(true)"}
```

> 注意：`refreshExplore` 内部是 `Coroutine.async(callBack.scope)`，在 IO 线程执行，安全。

### 2.3 双向分页（向上也能翻页！）

```kotlin
binding.recyclerView.addOnScrollListener(object : RecyclerView.OnScrollListener() {
    override fun onScrolled(recyclerView: RecyclerView, dx: Int, dy: Int) {
        if (!recyclerView.canScrollVertically(1)) {
            scrollToBottom()                       // 到底 → 下一页
        } else if (!recyclerView.canScrollVertically(-1) && dy < 0) {
            scrollToTop()                          // 到顶且在上滑 → 上一页
        }
    }
})

private fun scrollToTop(forceLoad: Boolean = false) {
    if ((oldPage > 1 && !loadMoreView.isLoading && !loadMoreViewTop.isLoading) || forceLoad) {
        loadMoreViewTop.hasMore()
        viewModel.explore(oldPage - 1)             // ← 加载上一页
    } else if (oldPage <= 1) {
        viewModel.showPage(1)
    }
}
```

**这是很少见的设计**：滑到顶部继续上滑会**加载第 N-1 页并插到列表前面**。

配套的列表头：`updateTopHeader(page)` 在 `page > 1` 时插入一个顶部 header（`loadMoreViewTop`）。

**注意**：这依赖 `{{page}}` 规则的正确性。如果站点的页码是 0 基或倒序，双向分页会出错。


```kotlin
var callBackJs: String? = null,     // 监听到事件后执行的回调js代码
```

### 3.3 执行机制

```kotlin
fun callBackBtn(activity, event, source, book, chapter, bookType, result, noCall) {
    if (source == null || !source.eventListener) { noCall?.invoke(); return }
    val jsStr = source.getContentRule().callBackJs
    if (jsStr.isNullOrEmpty()) { noCall?.invoke(); return }
    ...
    source.evalJS(jsStr) {
        put("event", event)        // ← 事件名字符串
        put("java", java)          // ← SourceLoginJsExtensions（含 customButtonKey）
        put("result", result)      // ← 事件附带的返回值
        put("book", book)
        put("chapter", chapter)
    }
    ...
    if (!result.isTrue()) { noCall?.invoke() }   // ← 返回假值则执行原动作
}
```

**关键语义**：
- 返回 **truthy** → **拦截**原动作（`noCall` 不执行）
- 返回 **falsy** → **放行**原动作

这是"自定义点击行为"的核心：你可以拦截"点击作者"，改成打开自己的界面。

### 3.4 完整示例

```jsonc
{
  "eventListener": true,
  "ruleContent": {
    "callBackJs": "@js:(function(){\n  if (event === 'clickAuthor') {\n    java.longToast('作者: ' + book.author);\n    java.startBrowser('https://site.com/author?name=' + encodeURIComponent(book.author), '作者主页');\n    return true;   // 拦截原动作\n  }\n  if (event === 'clickCustomButton') {\n    java.longToast('自定义按钮被点');\n    return false;  // 放行\n  }\n  return false;\n})()"
  }
}
```

### 3.5 配套：`customButton`

```kotlin

```

开启后，详情页/阅读菜单会出现一个**书源可控的按钮**，点击触发 `clickCustomButton` 事件。

配合 `java.customButtonKey`（`SourceCallBack.kt:92`）可以做"同一个按钮在不同书源下做不同事"。

## 四、`contentBatch`：批量正文（下载提速关键）

### 4.1 是什么

传统模式下，缓存整本书要**逐章串行请求**（N 章 = N 次往返）。
`contentBatch` 让书源**一次拿多章**，把 N 次往返压成 1 次或几次。

### 4.2 三个字段（ContentRule）

```kotlin
var contentBatch: String? = null,   // 批量正文规则，支持 JS
var maxBatchSize: Int? = null       // 最大批量数量，默认 null 表示不支持
```

### 4.3 启用条件（BookSource.kt:248）

```kotlin
fun supportContentBatch(): Boolean {
    val rule = getContentRule()
    if ((rule.maxBatchSize ?: 0) <= 1) return false      // ← 必须 > 1
    return isJsSource() || !rule.contentBatch.isNullOrBlank()
}

fun contentBatchSize(): Int {
    if (!supportContentBatch()) return 1
    return (ruleContent?.maxBatchSize ?: 1).coerceIn(1, MAX_CONTENT_BATCH_SIZE)
}

const val MAX_CONTENT_BATCH_SIZE = 50     // ← 硬上限 50 章/批
```

**三个条件同时满足**：
1. `maxBatchSize > 1`
2. 有 `contentBatch` 规则（或 JS 源有 `getContentBatch` 函数）
3. 实际批量 = `min(maxBatchSize, 50)`

### 4.4 执行流程（BookContent.analyzeContentBatch）

```kotlin
val batchContext = BatchContentContext(bookSource, book, chapters, ...)
val analyzeRule = AnalyzeRule(book, bookSource)
analyzeRule.setChapter(chapters.first())
analyzeRule.setBatchContext(batchContext)
analyzeRule.setBaseUrl(book.tocUrl.ifBlank { bookSource.bookSourceUrl })

Debug.log(..., "≡开始批量下载,本批${chapters.size}章")

try {
    val script = contentBatch.trim()
    if (script.startsWith("<js>", true) || script.startsWith("@js:", true)) {
        for (rule in analyzeRule.splitSourceRule(script)) {
            if (rule.mode != AnalyzeRule.Mode.Js) {
                throw NoStackTraceException("批量正文规则只能包含 JavaScript")
            }
            analyzeRule.evalJS(rule.rule, chapters)     // ← chapters 数组作为 result
        }
    } else {
        analyzeRule.evalJS(script, chapters)             // 裸 JS 也当 JS 执行
    }
} finally {
    batchContext.close()
}

val missing = batchContext.missingChapters()
Debug.log(..., "≡批量下载完成,成功${savedCount()}章,未回存${missing.size}章")
return missing      // ← 未回存的章节交给普通单章流程兜底
```

**要点**：
- `contentBatch` **只能是 JS**（`<js>` / `@js:` / 裸 JS 都行，但不能是 CSS/XPath）
- 脚本里 `result` = **本章批次的 `List<BookChapter>`**
- 每处理完一章必须调 `java.cacheContent(chapter, content)` 主动回存
- **没回存的章节会自动回落到普通单章流程**（不会丢）

### 4.5 `java.cacheContent` 的正确用法

```kotlin
fun saveContent(identifier: Any?, content: String): Boolean = synchronized(lock) {
    val chapter = resolveChapter(identifier)
        ?: throw NoStackTraceException("java.cacheContent 未唯一匹配到本批次章节,重复 URL 请传章节对象: $identifier")
    val replaced = applyContentReplace(chapter, content)
    if (replaced.isBlank()) return false
    val saved = BookHelp.saveContent(bookSource, book, chapter, replaced, token)
    if (saved) savedIndexes.add(chapter.index)
    saved
}
```

**三条硬规矩**：

1. **章节身份按 `index` 判定，不按 url**
   > 源码注释：`目录允许多章共用同一 url（靠序号/标题/tag 区分），缓存文件名也是按 index + 标题生成的。按 url 认章会把正文写到错误章节，并让同 url 的其余章节被误判为已完成。`

2. **重复 URL 时必须传章节对象**，不能传 url 字符串
   > `throw NoStackTraceException("java.cacheContent 未唯一匹配到本批次章节,重复 URL 请传章节对象: $identifier")`

3. **会自动套用 `replaceRegex`**（与单章流程一致），所以批量拿到的正文**不需要自己清洗**

### 4.6 完整示例

```jsonc
{
  "ruleContent": {
    "content": "#text p@text",
    "contentBatch": "@js:(function(){\n  var list = result;\n  var base = baseUrl.replace(/\\/[^\\/]*$/, '/');\n  for (var i = 0; i < list.length; i++) {\n    var ch = list[i];\n    try {\n      var html = java.ajax(ch.url);\n      var doc = Packages.org.jsoup.Jsoup.parse(String(html));\n      var txt = doc.select('#text p').text();\n      if (txt) { java.cacheContent(ch, txt); }\n    } catch (e) {}\n  }\n  return true;\n})()",
    "maxBatchSize": 20
  }
}
```

**更好的做法**：如果站点有"一次返回多章"的接口，直接一个请求拿全部：

```javascript
var list = result;
var ids = [];
for (var i = 0; i < list.length; i++) ids.push(list[i].url.replace(/\D/g, ''));
var resp = java.post('https://site.com/api/batch', 'ids=' + ids.join(','), {...});
var jo = JSON.parse(String(resp.body()));
for (var i = 0; i < list.length; i++) {
  var c = jo.data[i];
  if (c && c.content) java.cacheContent(list[i], c.content);
}
```

### 4.7 性能对比（理论）

| 方式 | 100 章请求数 | 说明 |
|---|---|---|
| 单章 | 100 次 | 每次 1 往返 |
| `contentBatch`（无批量接口） | 100 次 | 但可并发，实际更快 |
| `contentBatch`（有批量接口） | **1~5 次** | 数量级提升 |
