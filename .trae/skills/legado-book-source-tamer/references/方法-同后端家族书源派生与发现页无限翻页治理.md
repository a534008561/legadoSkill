# 方法：同后端家族书源派生 与 发现页无限翻页治理

> 来源：261116 追书大全（com.zshuall.fread，yutinglu.com 后端）书源制作全过程实锤。
> 适用：①给「与已有源共用同一后端的套壳 App」做新源；②列表类发现页出现「上滑永远加载同一批内容」；
> ③需要在**不主动压测站点**的前提下判断搜索/接口限频；④在 Legado 里做规则级 A/B 实验。

## 0. 一句话结论速查

| 问题 | 结论 |
|---|---|
| 同后端套壳 App 要做新源 | 算法层可整体复用，**必须换的只有 4 样**：header 身份、UA、bookSourceUrl、状态键名前缀 |
| 要不要复制 App 的 sign/time/stamp | 先做三组对照实验。**yutinglu 系不校验** ⇒ 不要复制固定值（固定签名必然过期，是隐患不是保险） |
| 想知道站点有没有搜索间隔，又不想压测 | **读站点自己的 conf 接口**，不要试探请求频率（见 §2） |
| 发现页翻不到头 | 该后端**越界页重复末页**且响应体**没有 has_next/total** ⇒ 只能用「页码前进 + 本页 id 集合与上一页全等」内容级判据（见 §5） |
| 改了规则但 App 行为没变 | **BookSource 按 origin 缓存在内存**，同一 origin 反复覆盖推送 ⇒ A/B 实验全部失真（见 §6，本次最大坑） |
| 跨页/跨调用状态放哪 | 放**规则层**（source.put/get），不要放 jsLib（共享 scope 没有 source/baseUrl）（见 §7） |

## 1. 同后端家族识别（先确认值不值得复用）

判据（任一命中即高度疑似同后端）：
- ProxyPin 抓包出现同一组业务域（本例 s/d/book/catalog/chapter/conf/c-res/my.yutinglu.com）。
- 反编译看到同一套 Retrofit 短域头写法：@Headers("Domain-Name: s") + retrofiturlmanager
  （me.jessyan.retrofiturlmanager）+ me.jessyan.art 基础库、Base64Bean/BaseModel 实体。
- SearchService 路径模板一致：GET /{api_version}/1/lists.api?keyword=&form=。
- 业务 dex **未加固可直接 xref**（本包 com.amgcyo.cuttadon.* 直接可见，源码文件名为真名 SearchService.java）。

> 关键提醒：**包名 ≠ 代码命名空间**。com.zshuall.fread 只是应用包名，内部代码在 com.amgcyo.cuttadon。
> 按包名去 dex 里找类必然空手，应直接搜接口路径字符串（lists.api）反查。

## 2. ★用站点自己的 conf 接口替代「压测探测」（免风控取证法）

用户明确要求：**不要主动探测搜索访问频率**。正确做法不是"猜一个保守值"，而是**问站点要**：

    GET https://conf.yutinglu.com/v4/android/{package_name}/{channel}

APK 里 ConfigService 直接给出该模板：v4/android/{package_name}/{channel}，Domain-Name: conf；
另有一个 /a_package.html——**别被名字骗**，它返回的是 Xposed/Magisk 等 root 框架包名检测名单，不是配置。

响应用主协议 D() 解密后 JSON.parse('{"' + raw) 可整体解析（首个 16B 被 IV 覆盖，恰好落在 {" 位置）。
本次从中直接取到：

| 字段 | 值/含义 | 用途 |
|---|---|---|
| urls.domain | yutinglu.com | 确认唯一根域，无需猜镜像 |
| urls.website_url | https://xsxsapp.com/zsdq/ | **真实发布页**（zsdq=追书大全） |
| secondary_domain | 15 个键**全空** | 无备用域线路池 ⇒ 线路池就是官方子域 |
| force.invalid_request_min | 5 | 站点自定义"无效请求最小间隔"线索 |
| force.search_read / search_start_up | 400 / 100 | 搜索侧节流线索 |
| chapter.read_ad_lock.interval_min | 45 | 阅读侧节流线索 |
| stamp | SFczM01HTlQxWjI4TUFDM... | **App 的 stamp 头来自这里**（说明它是服务端发的固定串） |
| notify.notify_url | 同发布页 | 交叉验证发布页 |

**方法论**：套壳 App 家族的"站点自身信号"（限频、备用域、发布页、开关）几乎都写在配置接口里。
先解密配置接口，比做 N 组频率试探又快又安全。**本次全程只做了 2 次真实关键词搜索**（都是 App 内实测必须的那次）。

## 3. 三组对照实验定"签名字段是否被校验"（含反向验证）

现象：抓包里追书大全比全民小说多带 sign/time/stamp 三个头。要不要在书源里复现签名？

| 组 | 请求头 | 结果 |
|---|---|---|
| 正组 | 真实身份头，**省略 sign/time/stamp** | 200 + code:1 + 正常密文（119889B） |
| 反向验证组 | 身份头 + sign/stamp/time **全填假值** | 200 + 响应**与正组逐字节相同** |
| 极端组 | **只有 Accept: */***（裸请求，无任何身份头） | 200 + 正常密文 |

⇒ 结论：**服务端不校验这三个头**（"填假值也过"是判据核心——只测"省略"会漏掉"字段存在但内容不校验"这种情况）。
⇒ 行动：书源只保留身份头与 UA，**不复制固定 sign**（固定串会随版本/时间失效，制造"某天突然全挂"的隐患）。

> 对照实验设计要点（沿用既有方法论）：必须包含"反向验证组"（假值/破坏性输入），
> 否则无法区分「字段被忽略」与「字段被校验但恰好我的假值通过」。

## 4. 发布页三态与面板诚实反馈

| 形态 | 例子 | 面板"一键获取线路"应做 |
|---|---|---|
| A 线路清单页 | 搜书吧/黑料网/麻豆类 | 解析 URL 作为线路池主体 |
| B **App 下载落地页** | **本次 xsxsapp.com/zsdq/**（页面里只有 hm.baidu.com 统计与 App Store 链接） | 抓不到接口线路 ⇒ **明确 Toast"发布页为下载落地页，未发现小说接口线路（已保留官方子域池）"**，同时把内置官方子域池填上 |
| C 广告/开关控制页 | 全民小说的 bqm.125ks.cn/jc/*.php | 识别为"非小说 API"，不要当线路 |

两个具体实现纪律：
1. **不要把落地页根域塞进线路池**。本例第一版把 xsxsapp.com/zsdq 插进 6 个位置里，直接挤掉了真正有用的
   conf.yutinglu.com，测速时它还贡献了一个无意义的 2365ms。线路池应只放**有功能职能的域**。
2. **测速探针必须逐域配"能真返回内容的端点"**，不要用 /。第一版对 s/ d/ catalog/ 用 p='/'，
   三行结果全是"空响应 4776ms / 284ms / 1907ms"——这类"看起来在工作其实是噪声"的输出必须当 bug 修：

       book    → /book_city/v7/index/1/0/1.html
       conf    → /a_package.html
       d       → /book/details/v4/889/889551.html
       catalog → /qu/79/aa/94/358.html
       chapter → /qu/79/aa/94/358/1399.html
       s       → /v4/1/keyword.api?data_conf=5&package=...

   （keyword.api 是热词接口，不是 lists.api 搜索接口 —— 测速绝不打搜索端点。）

## 5. ★★发现页"无限翻页"的根因与内容级终止（本方法核心新增）

### 5.1 根因（实测数据）

    book_city/v7/index/1/0  →  p1: 69 本   p2: 60 本   p3: 60 本   p4: 60 本   p5: 60 本
                                p2..p5 书籍 id 集合完全相同（首本都是同一本）

- 该后端**越界页不返回空，而是持续重复末页内容**；
- 解密明文顶层字段只有 list / icon / data（rank 页是裸数组），**没有 total/page_count/has_next**
  ⇒ **不存在可直接使用的站点级"下一页"信号**；
- 所以旧结论「超界页去重后本页 0 条 ⇒ 自然终止」**在这族站上不成立**（全民小说/猫眼沿用该假设，
  表现为发现页可以无限上滑）。

### 5.2 判据（满足"跟随站点自身信号、不写死页码上限"）

    终止条件 = 页码严格向前推进(newPg > oldPg)  且  本页书籍 id 集合与上一页完全相同

三条刻意设计（都被实测纠正过，缺一即错）：
1. **必须"页码变大"**：只要求"页码不同"会把**回看/跳页（3→2）**误判为到底。实测第一版就因此让
   p3 之后的 p2 直接返回 0 本。
2. **同页重复请求不算重复**：下拉刷新同一页时 newPg === oldPg ⇒ 不终止 ⇒ 不会出现"刷新后分类变空"。
3. **不写死页数**：站点以后加书 ⇒ 末页内容变 ⇒ 指纹变 ⇒ 自动恢复继续翻页，**无需回来改规则**。

### 5.3 页码必须按端点 URL 形状分别解析（易错点）

{{page}} 在各端点位置不同，用一个通用正则一定会漏：

| 端点形状 | 页码位置 | 备注 |
|---|---|---|
| book_city/v7/index/{a}/{b}/{page}.html | 第 **2** 个数字 | index 锚点 |
| rank_lists/v7/details/{a}/{b}/{c}/{page}.html | 第 **3** 个数字 | details 锚点 |
| classify/v4/all/{sex}/{ltype}/{stype}/{end}/{score}/{page}.html | 第 **5** 个数字 | all 锚点，**第一版漏掉它** ⇒ 分类页永不终止 |
| book_city/v7/1/rank2tag/{rank}/0.html | **无页码位** | 取不到页码 ⇒ 保守地**不终止**（宁可多显示，不可误判到底） |

实现（jsLib 纯函数，零宿主依赖）：

    function EXD(jv,res,prevSig,prevPg,bu){
     var L=EX(jv,res); var st={sig:'',pg:''};

      var pg=''; var s=String(bu||''); var mm;
      if((mm=/(?:^|\/)index\/(-?\d+)\/(-?\d+)\/(\d+)(?:_reload)?\.html$/.exec(s))) pg=mm[3];
      else if((mm=/(?:^|\/)details\/(-?\d+)\/(-?\d+)\/(-?\d+)\/(\d+)(?:_reload)?\.html$/.exec(s))) pg=mm[4];
      if(!pg){ mm=/(?:^|\/)all\/(-?\d+)\/(-?\d+)\/(-?\d+)\/(-?\d+)\/(-?\d+)\/(\d+)(?:_reload)?\.html$/.exec(s); if(mm) pg=mm[6]; }

      var fP=parseInt(pg,10), oP=parseInt(String(prevPg||''),10);

     }catch(e9){ st.sig=prevSig||''; st.pg=prevPg||''; }

## 6. ★★★ BookSource 按 origin 内存缓存 —— 规则级 A/B 实验的头号杀手

症状（本次踩了整整一轮）：
- 把 ruleToc.chapterList 换成"纯硬编码 1 章"、把 jsLib 换成空壳桩，**报错一字不变**；
- 同一份源、同一批规则：A 书正常，B/C/D/E 书稳定报错；换个 bookSourceUrl 后**全部正常**。

根因：App 侧（LT 与 E 都有）把 BookSource 对象缓存在内存（BookController/checkBookSourceAndBook），
**通过同一 origin 覆盖推送不会让缓存的旧规则失效**；于是所有"我改了规则再看效果"的实验都在测旧规则。

正确姿势（本次实测有效）：

    每次实验换一个 origin（如 https://t<TAG>-<用例名>.book.yutinglu.com）
    + 用该 origin 重新 saveBook（书架记录与 origin 绑定）
    + 再 refreshToc / getBookContent

或让用户重启 App 清缓存。

推论与教训：
1. **A/B 结论"改动不改变现象"时，第一反应应是"我的改动生效了吗"，而不是"所以与它无关"。**
2. 交付前用**全新 origin** 做一遍 E 版整源验证，可排除缓存假象（本次 5/5 书全通，才敢下 E 兼容结论）。
3. 清理临时源时，LAN 服务**没有"列出全部源"路由**，可用已知时间戳 TAG 反查 origin：
   GET /getBookSource?url=<候选> 命中的即存在（本次实测 ~59 次/秒，扫 4500 候选仅 203s），
   命中后把整份对象回读再 POST /deleteBookSources [对象] 删除。

## 7. 规则作用域 vs jsLib 作用域（新增两条绑定实测）

在 E 版规则作用域内（借 /getBookContent 执行 ruleContent.content 探针实测）：

    baseUrlType=string
    baseUrl=https://chapter.yutinglu.com/qu/221/b4/28/657/2167.html   ← 是"本页完整地址"
    srcputType=function  srcgetType=function
    roundtrip=ECH_V        ← source.put → source.get 可往返
    javaget=1              ← java.put/get 同样可用

在 LT 版 ruleExplore.bookList 作用域实测：

    BU=https://book.yutinglu.com/book_city/v7/index/1/0/3.html   ← baseUrl = 本页地址（可取页码）
    VIA=source，计数 0 → 1 递增                                    ← 跨页状态通道成立

边界（老定式的补强）：
- **jsLib 共享 scope 里没有 source、没有 baseUrl**（"共享 scope 铁律"的第三个实例）。
  ⇒ 需要跨调用状态/页码时，**读写放规则层，jsLib 只做纯算法**（EXD 即按此拆分）。
- **探针写入若写在 jsLib 里会被 try{}catch{} 静默吞掉**，回读恒空 ⇒ 极易误判成"通道不可用"。
  本次就因此差点得出错误结论；把写入移到规则层立刻看到 0→1 递增。
- eval_js(MCP) 里 **source.evalJS(...) 不可调用**（InternalError: 找不到方法 evalJS(string)），
  但 **jsLib 的函数是直接绑定的，可直接调用**；验证 loginUi 的 viewName 表达式用 eval(expr) 即可。

## 8. Rhino 语法纪律（老坑，本次再次误触两次）

- **顶层 return 非法** ⇒ EvaluatorException: 返回的值无效。规则 JS 必须包成 (function(){...})()。
  （本次 E 版 A/B 有 3 个探针因此报废，白白多跑一轮。）
- 经 JSON 传规则时**双层转义**会吃掉引号 ⇒ 表现为 SyntaxError: Unexpected token，别误判为站点问题。
- 别在规则里写 :contains() / :first-child（Legado 不支持），沿用索引/@js: 写法。

## 9. 同家族派生的"身份隔离清单"

派生新源时，除 header/UA 外**必须逐项改名**，否则与已装兄弟源互相污染（App 的 source 级
SharedPreferences 是**按 key 全局**的，两源会读写同一格）：

| 项 | 本例（追书大全） | 兄弟源（全民小说） |
|---|---|---|
| 函数前缀 | ZD_* | QM_* |
| 状态键前缀 | zd_line* / zd_sp* / zd_exp* | qm_line* / qm_sp* |
| 发布页默认 | https://xsxsapp.com/zsdq/ | bqm.125ks.cn/jc/v.php |
| version 头 | 5.0.2 | 5.0.5 |
| channel 头 | baidu_tg104 | new2025 |
| 包名/UA 尾段 | com.zshuall.fread（微信 iOS UA 壳） | com.qmxsppa.novelreader（三星 Android UA 壳） |
| bookSourceUrl | https://book.yutinglu.com | 同域（**注意：同后端家族若共用同一 origin，会互相触发 §6 的缓存污染**） |

自检脚本思路（本次实际用上的）：派生后对成品做**残留扫描**——
['全民','qmxsppa','QM_','qm_','125ks','new2025','app.maoyankanshu'] 出现次数必须为 0，
并断言目标 UA/包名/发布页确实存在。残留大多藏在**注释**里，注释也是交付物。

## 12. 补录：短 book_id 死链（本次交付前最后一刻抓到的真 bug）

### 12.1 现象

发现页 `book_city/v7/index/1/0/2.html` 里第一条《大唐第一败家子》解析成
`https://d.yutinglu.com/book/details/v4//396.html`（**双斜杠**），详情/目录全空、`TocEmptyException`。
服务端对该 URL 明确回 `code:0 书籍ID错误！`。

### 12.2 根因

模板沿用 `id.slice(0,-3) + '/' + id` 拼路径，对 ≥4 位 id 正确，但 **id ≤3 位时 slice 得空串** ⇒ 少一段。
本源书城某页 42 本里 **11 本是 3~4 位 id**，即四分之一是死链——而它们在最常测的关键词/榜单里恰好不出现，
所以一直活到交付前才被"随手换一页"抓到。

### 12.3 正确形态（实测）

| id 位数 | 前缀 | 实测 |
|---|---|---|
| ≥5 位 | `id.slice(0,-3)` | `28/28539`、`889/889551`、`1043/1043368` ✓（抓包实锤） |
| 4 位 | 首位数字 | `3/3057` ✓ code:1 |
| ≤3 位 | **补 `0`** | `0/396` ✓ code:1，解出书名；`//396` ✗ 书籍ID错误；`396.html`（无前缀）✗ 404 |

### 12.4 修法（单一出口 + 脏值即丢）

```js
function DPRE(id){ var s=String(id===undefined||id===null?'':id);
 if(!/^\d+$/.test(s))return ''; return s.length>3?s.slice(0,-3):'0'; }
function DPATH(id){ var s=String(id===undefined||id===null?'':id);
 if(DPRE(s)===''&&!/^\d+$/.test(s))return ''; return 'v4/'+DPRE(s)+'/'+s+'.html'; }
```
所有 `details` / `source` URL 一律走 `DPATH()`（jsLib 的 EX、ruleSearch.bookList、ruleBookInfo.init 三处），
`EX()` 同时改成 `if(!/^\d+$/.test(id))continue;` —— **宁可少一条，也不产出死链条目**。

### 12.5 验证

- 单测 13 个长度样本：`≥4 位`与旧写法**逐字节相同**（搜索链路零回归），仅 `≤3 位`的 4 例由死链变活。
- 全量扫 4 个发现页收集全部短 id：12 本 × (详情+线路) = **12/12 双通**，且 `bookUrlPattern` 违规 URL = 0。
- 真实管线回归：`::book_city/…/2.html` → 详情 9 线路 → 目录 775 章 → 正文正常。

> 通用结论：**凡是 `id.slice(0,-3)`/`id.slice(0,-N)` 这类「按 id 位数切前缀」的 URL 构造，必须显式处理
> `len(id) <= N` 的边界**，并对非纯数字 id 直接丢条目。同类隐患存在于所有由该模板派生的源
> （全民小说 / 猫眼看书 / 顶点小说 的 `slice(0,-3)` 段同样中招），本次只按用户要求改了追书大全，
> 其余源**未擅自改动**，如需修复要单独确认。

## 13. 补录：把「偶发」误判成「确定性」的排查教训（本次最大时间黑洞）

现象回顾：E 版对短 id 书稳定报 `SyntaxError: Unexpected token: <随机汉字>`，长 id 书稳定通过，
连跑 4 次都一样 ⇒ 我据此判定"E 版对该书有确定性 bug"，做了 5 轮二分（换 jsLib、换 toc、硬编码 init、
外传诊断、逐步骤 trace），最后把真实规则原样在全新 origin 上**连跑 3 次全过**，才证明它是**偶发**。

三条纪律：
1. **"同一本书每次都不行"不等于"与书有关"**——同一时间窗内的偶发上游异常（边缘节点错误页/超时）会被
   复现成看似稳定的规律。判"确定性"之前，至少要**跨时间**复测一次（本次隔了几分钟后就自愈）。
2. **"把规则改掉就好了"要警惕**：我试的三种互不相干的改法（加外层 try／`.map` 改 for／换三元正则）**全部生效**
   ⇒ 改动内容与症状无关，说明病因在改动之外。这一步是决定性信号，比继续二分更早指向"偶发"。
3. **诊断脚本自身也会制造 bug**：本轮三次假信号都来自探针写法——①顶层 `return`（Rhino 非法，报"返回的值无效"）；
   ②在 `jsLib` 里 `source.put` 被 `try/catch` 静默吞掉（共享 scope 无 source）；
   ③Python 字符串里写 `\\d` 经多层转义后正则失效，让**我的诊断代码**先出了 `bid=''`，
   差点得出"服务端字段坏了"的错误结论。**每次下结论前先自问：这个失败会不会是我的探针本身造成的？**
