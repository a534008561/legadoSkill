# 方法：CDN 短时频控 与「假 UA 敏感」误判

> 2026-10-18 花都动漫（hd.huadudm.com）视频书源实战提炼

## 0 一句话

**「带某个 header 就 404、去掉就 200」几乎不是 UA 敏感，而是短时频控。**  
判定方法：**基线请求必须在实验中间穿插重复**——如果"无头"的基线在第 5 次也挂了，那就不是 header 的事。

---

## 1 现象：一个把人骗进沟里的假象

排查 CDN 分片/清单时，得到了这样的"规律"：

```
1 无头        => 200 len=18213
2 带UA        => HTTP 404
3 空headers   => HTTP 404
4 仅Referer   => HTTP 404
5 无头again   => 200 len=18213      ← 看起来"规律"成立
```

如果就此收工，会得出**极其错误的结论**：

> "该 CDN 拒绝一切显式请求头，必须完全不设 header 才能取流。"

进而写出：书源 `header` 留空、所有请求剥离 UA、在正文规则里警告用户"别设 UA"……  
**全部是错的**，而且会给后续维护者埋下大坑（用户一旦在 App 设置里配了 UA，整个源就"坏"了）。

---

## 2 正确的实验设计：基线穿插法

**关键动作**：不要"跑完 A 组再跑 B 组"，而是 **A/B/A/B/A/B 交替**。

```js
// 错误的实验（顺序执行，会被频控骗）
t('无头'); t('带UA'); t('仅Referer');

// 正确的实验（基线穿插，能暴露频控）
t('基线1', null);
t('带UA', {UA:...});
t('基线2', null);       // ← 如果这里也挂了，说明是频控不是 header
t('仅Referer', {Ref:...});
t('基线3', null);       // ← 恢复了吗？恢复了就是频控窗口
t('带UA2', {UA:...});   // ← 第二次带 UA 还挂吗？
```

实测结果（同一 CDN，同一分片，间隔数秒）：

| 序 | 请求 | 结果 |
|---|---|---|
| 1 | 基线（无头） | 200, 957156 B |
| 2 | 带 UA | 404 |
| 3 | 基线 | 200, 957156 B |
| 4 | 仅 Referer | 404 |
| 5 | 基线 | 200, 957156 B |
| 6 | 仅 Accept | 404 |

——到这里仍然像"header 敏感"。**继续跑第二轮**：

| 序 | 请求 | 结果 |
|---|---|---|
| 1 | 带 UA | **200, 957156 B** ← 反例出现 |
| 2 | 带 UA | **200, 957156 B** |
| 3 | 基线 | 200 |
| 4 | 带 UA | **200** |
| 5 | 基线 | 200 |
| 6 | 带 UA | **200** |

**同一个请求、同一个 header，前一轮 404、后一轮 200** ⇒ 与 header 无关，是**时间维度**的频控/抖动。

再用 `java.ajax` 通道验证（与 ExoPlayer 同栈 OkHttp）：

```
ajax 纯URL        => OK 503370
ajax +UA          => OK 503370
ajax 纯URL again  => OK 503370
ajax +UA again    => OK 503370
```
连续 4 次全 200（此时频控窗口已过）⇒ **结论翻转：CDN 对 UA 完全不敏感。**

## 3 频控的三种典型表现（都长得像"规则错"）

| 表现 | 误判成 | 真相 |
|---|---|---|
| 同一 URL 短时反复请求 → 404 | "URL 拼错了 / 分片名不对" | 短时频控 |
| 同一 URL 短时反复请求 → 连接超时 | "DNS 污染 / 被墙 / 节点不通" | 短时频控或冷启动 |
| 换 UA 后第一次 404、第二次 200 | "UA 敏感 / 需要特定 UA" | 频控窗口恰好跨越了实验 |

**共同点**：**同一个 (URL, header) 组合在不同时刻结果不同**。  
只要观察到"不可复现"，就必须先怀疑频控，而不是继续在 header 上做文章。

---

## 4 判定流程（可直接照做）

```
① 拿一个「基线」请求（最简形式），记下结果
② 做一次「变量」请求（改 header / 改 UA / 改 Referer）
③ 立刻重复一次「基线」
   ├─ 基线仍 200 → 变量可能就是原因，进入 ④
   └─ 基线也挂了 → 是频控，跳到 ⑤
④ 把「变量」请求重复 2~3 次（中间穿插基线）
   ├─ 变量稳定失败、基线稳定成功 → 真·变量敏感
   └─ 变量有时成功有时失败 → 仍是频控/抖动
⑤ 静默等待 60~120 秒，重跑 ②③
   ├─ 变量成功 → 确认频控，与 header 无关
   └─ 变量仍失败 → 才考虑真·敏感
```

**核心判据**：`同一输入不同时刻不同结果` = 时间维度问题，不是参数维度问题。

## 5 频控窗口的量级（实测）

| 站点/资源 | 窗口 | 备注 |
|---|---|---|
| `cdn5.huabf.com` / `t1.121126.com`（本案例） | 约 10~60 秒 | 同一分片连打 5+ 次触发，静默 1~2 分钟恢复 |
| `hd.huadudm.com` 主站 | **无**（连搜 6+ 次全正常） | 搜索框写"间隔10秒"是**装饰** |

> ⚠️ **不要主动压测来"测量"窗口**——压测本身就是触发条件。  
> 用户明确要求"不要主动探测搜索访问频率"时，用**最少 1~2 次**验证"是否真的会拦"，不要做频率扫描。

## 6 写进书源时怎么处理

### 6.1 不要为了"躲频控"而阉割 header
```jsonc
// ❌ 错误：以为 CDN 拒绝 header，于是留空
"header": ""

// ✅ 正确：正常带 UA（站点 UA 不敏感时随便给浏览器 UA）
"header": "{\"User-Agent\": \"Mozilla/5.0 ...\"}"
```

### 6.2 用 `concurrentRate` 兜住（而不是靠删 header）
```jsonc
"concurrentRate": "1/800"   // 每 800ms 最多 1 次请求
```
对**列表/详情**页面做节流即可；视频分片由播放器顺序拉流，不会触发频控。

### 6.3 错误提示要写"等一会儿"，不要写"规则坏了"
```js
// loginCheckJs 里
if (b.length < 1200 && b.indexOf('频繁') >= 0) {
  throw new Error('⏱ 站点限制访问频率，请等 10 秒后再试');
}
```
**用户看到的文案决定他会不会去改书源**。写"等 1~2 分钟"→ 用户等；写"解析失败"→ 用户以为源废了。

### 6.4 注释里记录真实结论，别记录误判
```jsonc
// ✅ "视频CDN有短时频控：同一分片短时间内反复请求会返回404或超时，等1~2分钟恢复
//     （实测正常播放不受影响，ExoPlayer 顺序拉流不会触发）"
// ❌ "CDN 拒绝一切显式请求头，必须留空 header"
```

---

## 7 为什么这个坑特别贵

1. **误判的结论会写进规则**，而规则会被"看起来合理"地实现出来 → 真正的故障点被掩盖。
2. **误判会传染**：一旦认定"CDN 不吃 header"，后续所有播放问题都会被错误归因（播放器黑屏 → "是不是又带 header 了？"）。
3. **不可复现**：下次换个人排查，跑第一次就 200，会直接推翻注释、又改回去，来回震荡。

---

## 8 避坑清单

- **K1** 出现"某 header 导致失败"时，**先穿插基线**，再下结论。
- **K2** 同一 (URL, header) 在不同时刻结果不同 ⇒ **时间维度**问题。
- **K3** 不要用"连打 10 次统计成功率"来测 CDN —— 那是在**制造**频控。
- **K4** 频控窗口通常 10 秒~2 分钟，**静默等待**是最快的验证。
- **K5** 不要为了躲频控而删 header / 清 UA，那是把功能阉割当修复。
- **K6** 用 `concurrentRate` 节流列表请求，比"优化 header"更对路。
- **K7** 错误文案必须给"等待"的出路，不能只说"失败"。
- **K8** 注释要写**实测结论**（含反例），不要写推测。
- **K9** `java.ajax` 与 `java.get` 走的是**不同栈**（OkHttp vs jsoup），对照实验可以区分"网络层问题"与"jsoup 层问题"。
- **K10** 分片可用 `Range: bytes=0-1023` 只取头部验证（但要记得这本身也是一次请求，会参与频控计数）。

## 9 本次实战的完整对照记录（可复用模板）

```js
// 在 eval_js 里跑（App 内真机网络）
var base='https://t1.121126.com/videos/.../index0.ts';
var UA='Mozilla/5.0 (Linux; Android 14; Pixel 8) ...';
var out=[];
function t(label,hdr){
  var s='';
  try{ var r=java.get(base, hdr, 12000); s='OK '+String(r.body()).length; }
  catch(e){ var m=String(e).match(/Status=(\d+)/); s=(m?('HTTP '+m[1]):String(e).slice(0,40)); }
  out.push(label+' => '+s);
}
t('基线1', null);
t('变量(UA)', JSON.stringify({'User-Agent':UA}));
t('基线2', null);          // ← 关键
t('变量(UA)2', JSON.stringify({'User-Agent':UA}));
t('基线3', null);
out.join('\n');
```

若 `基线2` 挂 ⇒ 立刻停止 header 实验，改为等待后重测。

## 10 同族陷阱：**畸形 URL 也返回 200**，让分页 bug 隐身

> 与频控同属「**看起来正常、其实错了**」家族，一起记在这里。

### 10.1 现象

发现页第一版这样拼分页：

```js
// ❌ 把 {{page}} 拼在 .html 后面
add('人气榜','/vodshow/1--hits---------.html{{page}}',cell);
```

实际请求变成：

```
GET https://hd.huadudm.com/vodshow/1--hits---------.html1   -> 200
```

站点对 `...html1` 这种畸形 URL **返回 200 + 完整正常页面**（内容是第 1 页）。

后果：
- `debug_source` 全绿（列表 40 条、字段全非空）
- `check_source` **通过 1/1**
- 但**翻页永远停在第 1 页**（用户滑到底加载"第 2 页"，拿回来还是第 1 页内容）

### 10.2 怎么发现的

不是靠 debug，是靠 **`get_http_logs`**：

```
#174 ... GET https://hd.huadudm.com/vodshow/1--hits---------.html1 -> 200 417ms
```

**URL 尾巴上那个孤零零的 `1`** 一眼就是错的。

### 10.3 为什么常规手段抓不到

| 手段 | 为什么失效 |
|---|---|
| `debug_source` | 只看字段有没有值，不看 URL 是否"符合站点规范" |
| `check_source` | 只验证"能拿到数据"，畸形 URL 也能拿到 |
| 页面内容校验 | 返回的是真实第 1 页，内容完全合法 |
| 肉眼读规则 | `'...html{{page}}'` 看起来天经地义 |

**唯一可靠的抓法**：看 **HTTP 日志里的实际请求 URL**，或**用站点的真实分页 href 反推模板**。

### 10.4 通用解法：从站点的分页 href 反推，而不是凭直觉拼

```python
# 1) 抓列表页，把站点自己生成的分页链接全捞出来
hrefs = re.findall(r'href="(/vodshow/[^"]+)"', html)
# ['/vodshow/15-----------.html',      # p1（省略页码段）
#  '/vodshow/15--------2---.html',     # p2
#  '/vodshow/15--------21---.html']    # 末页

# 2) 按 - 切段，找出「哪一段随页码变化」
for h in hrefs:
    parts = h[:-5].split('-')
    print(len(parts), parts)
# 12 ['15','','','','','','','','2','','','']   ← 第 8 段（index 8）是页码
```

然后按段位拼：

```js
function pgUrl(type,order){
  var o=order?('--'+order):'--';
  return '/vodshow/'+type+o+'------{{page}}---.html';
}
```

### 10.5 验证三件套（必须全做）

1. **URL 逐字符比对**：`pgUrl(15,'',2)` 的输出必须**严格等于**站点分页 href 里的 `/vodshow/15--------2---.html`
2. **第 1 页 vs 第 2 页内容不同**：抓两页比首条书名（本次：`仙子的修行4下` vs `慕名雪的私人拍摄`）
3. **`{{page}}=1` 与站点省略页码段形式返回同一页**：确认边界不会翻车

### 10.6 通用教训

- **K11** 分页 URL 模板必须**从站点真实 href 反推**，不能凭"字符串拼接直觉"。
- **K12** 站点对畸形 URL 返回 200 是**常态**（PHP 路由宽松匹配），别把 200 当"正确"。
- **K13** `check_source` 通过 ≠ 分页正确。**分页必须单独验证"第2页内容 ≠ 第1页"**。
- **K14** **HTTP 日志是发现"URL 形态错误"的唯一可靠手段** —— 内容对、状态码对，只有 URL 本身不对。
- **K15** 段位型 URL（`a-b-c-d-...`）先数段数，再用 index 定位；`vodshow` 与 `vodsearch` 段数**不同**。
