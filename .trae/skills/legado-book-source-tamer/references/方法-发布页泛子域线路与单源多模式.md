## 2. getElements 对 @js 返回值类型硬要求（本次首见源码级定案）

`AnalyzeRule.getElements` 尾部只接受 `List<*>`/`Array<*>`/`NativeArray`，**@js 返回 JSON 字符串 → 落到 `return ArrayList()` 静默空**（不报错）。

- 症状指纹：debug 日志 `┌获取目录列表 └列表大小:0`，但同 HTML 用同正则手动 exec 命中 103
- 判定正反例：
  - ❌ `@js: return JSON.stringify(L)` → getElements 空列表 → TocEmptyException
  - ✅ `@js: return L`（JS 数组，Rhino NativeArray→List 映射）
- 适用范围：**chapterList / bookList / 一切列表类 @js**（之前只对 bookList 有此经验，本次实锤对 chapterList 同样适用；E 版 getElements 无 NativeArray 分支，返回 Java ArrayList 通用）
- 配套：列表 @js 返回数组时，字段规则写**键值直取**（`title`/`url`），不是 CSS

## 2b. book.type 在 chapterList @js 里重设的时机（X夜社范式的时机修正）

X夜社经验说「book.type 必须在 ruleToc.chapterList 里动态设置」；本次源码级确认**时机细节**：

- `WebBook.getBookInfoAwait` 与 `getChapterListAwait` **每次都 removeAllBookType() → addType(source.getBookType())**（每次刷详情/目录都重置 type）
- 所以 chapterList @js 里 `book.type=N` **每次刷目录都会执行**，正确且必要；但**搜索列表阶段**（BookList.kt:173/212）type=书源静态类型，搜索结果卡片类型显示按 bookSourceType
- bookSourceType=0 的三模式源，视频书书架图标/播放 UI 依赖 chapterList 重设的 type=4
- E 版 book.setType(N) 存在（E 版 API 存在性清单已记），`book.type=N` 属性写法两版通用

## 3. debug_source 环境变量隔离（本次首见，重要诊断纪律）

**debug_source 跑在检查进程，与 App 主进程 CacheManager 键空间隔离**：
- eval_js 里 `source.put('jmMode','小说')` 后，debug_source 的 searchUrl @js 里 `source.get('jmMode')` **读到空**（probe URL `debug_mode=&debug_var=` 实锤）
- **probe1 实锤机制本身正确**：probe searchUrl 直接返回 novel URL → debug 日志显示真实请求了 novel URL（模式字符串→URL 构造链路正确）
- ⇒ **变量驱动的模式切换在 debug 里永远测不了**，必须真机点面板按钮后真机搜索验证
- 诊断纪律：debug 里变量读到空 ≠ 规则错误；先分「实例隔离」vs「规则错误」（probe URL 把变量值打进 URL 是最直接的实锤法）

## 7. 图片链路加固（2601031b 用户报障修复实录）

**现象**：三模式封面不显示 + 漫画正文图不显示。

**排查链**（对照实验定根因）：
1. HTTP 日志：图床 `xi.dzuxta.cn` 请求全部 200（160KB 真图）→ 网络/图床无问题
2. **auth_key 完全不校验**：无/空/假签名都返回 46544B 真图（CDN 公开桶）→ 签名非问题
3. 三种封面源测速：`/social-cover/` 代理 **1921ms** vs 图床直链 **177ms**（差 10 倍）→ **慢代理超 Glide 超时 = 封面不显示根因**
4. `expose.eisees.com`（LD-JSON image 域）返回 0B 空响应 → 排除

**修复三板斧**：
- **coverUrl 统一图床直链**：详情页 data-src 优先（三模式都有）、og:image 仅兜底
- **正文 img 追加 URL 选项**：`<img src="URL,{"headers":{"User-Agent":"..."},"retry":2}">`——AnalyzeUrl 解析剥选项 → getGlideUrl 带书源 UA + retry:2 抗 CDN 间歇 RST
- **novel 详情 LD-JSON 是 `Book` 型**（非 ComicStory/VideoObject）→ name 正则三型兼容

**源码级机制**（本次实锤）：
- Glide 图片链 = `OkHttpStreamFetcher → AnalyzeUrl(url, source).getGlideUrl()` → **书源 header 的 UA 自动附加**（BaseSource.getHeaderMap）
- URL 选项 headers 在 AnalyzeUrl.kt 构造期覆盖合并（line ~275）→ 图片 URL 带 `,{"headers":...}` 合法且生效
- **debug_source 正文输出里 img 带选项串是正常的**（debug 显示规则原始产出，AnalyzeUrl 层在真实加载时剥掉）

**通用结论**：
- 慢封面代理（>1.5s）在移动网络下必超时，**封面一律用图床/CDN 直链，站方代理只做兜底**
- 图片 URL 的 URL 选项（headers/retry/timeout）是图床防盗链/间歇故障的标准加固手段
- 同站多形态详情页的 LD-JSON @type 可能不同（ComicStory/Book/VideoObject），字段正则要枚举兼容

## 8. ★★★ 图片域名网络分层实锤（2601031c 二次报障的最终答案）

**演化链**：直链不显示（v1）→ 改图床直链+URL选项（v2）→ **用户：「详情页图原来显示的（social-cover），改直链后反而不显示了」** → 决定性反转。

**根因**：**同一 App 内文本请求栈（ajax/Cronet）与图片加载栈（Glide/OkHttp）网络路径可不同**——MCP eval_js 走文本栈测图床全 200，但用户手机 Glide 栈下图床域名不可达；主站域名两栈都可达。

**铁律**：
1. **跨域图片选路前，先问用户「原来哪个域名能显示」**——用户实测过的可达性 > 一切测速数据（可达性 > 速度：1921ms 能显示的代理 > 177ms 不可达的直链）
2. 站方图片代理若存在（如 `/social-cover/{base64(路径)}.{ext}`），优先把所有跨域图统一改造成代理形态——代理域名与正文同域，必然可达
3. 修复后必须让用户真机复验——debug 绿 ≠ 用户网络绿（不同栈）

**social-cover 代理构造法**（本站通用，其他站可类比）：
```
图床URL: https://xi.dzuxta.cn/upload/upload/xxx.png?auth_key=...
提取路径: /upload/upload/xxx.png
base64:   java.base64Encode(path)
代理URL:  {主站}/social-cover/{base64}.{ext}
```
实测对正文图（/upload、/upload_01）、列表封面全部有效，100KB~274KB 真图返回。

**连带 bug 教训**：coverUrl 的 @js 正则 `(/upload[^"]+)` 初版写成 `)[^"]*")`（多一个引号）→ Rhino 报 `SyntaxError: 只有一个")"在正则表达式中`——**JSON 内嵌的 @js 正则必须单独 `new Function(code)` 验证**，`node --check` 整文件抓不到这种内嵌错误。
