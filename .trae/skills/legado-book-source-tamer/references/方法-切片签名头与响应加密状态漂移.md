# 方法-切片签名头与响应加密状态漂移

> 来源：ACFAN(acfan.com) v15 抓包重写（2026-10-06）。站点在 2026-10 升级了防爬体系：
> 新增「切片式签名头」（t+s），且同一接口的响应加密状态会随**登录态**在「明文/密文」间漂移。
> 本文提炼两类跨站可复用的新问题：①缺头静默失败（HTTP 200 + content-length:0）
> ②响应包裹形态三态化（同一接口三种返回结构）。含对照实验定位法与完整适配模板。

---

## 0 一句话总结

**站点悄悄加了请求头校验时，表现是「HTTP 200 但 content-length: 0」——没有任何报错。
唯一可靠的定位法是「对照实验」：控制单一变量（有无该头）跑 A/B/C/D 四组。
另：同一接口的响应加密状态可能随登录态变化（匿名明文 / 登录密文），
解析器必须写「encData 存在则解密、否则明文」的双兼容，不能假设固定形态。**

## 1 现象谱系

### 1.1 缺头静默失败（本次头号堵点）

| 表现 | 说明 |
|---|---|
| HTTP 200 + `content-length: 0` | 无任何错误信息，规则侧只看到「空响应」 |
| 搜索/详情/发现 全部空 | 看起来像「网站挂了」或「规则写错了」 |
| 老规则昨天还好、今天全挂 | 站点单方面升级，规则零改动 |

★ 关键鉴别点：**同一 URL 在浏览器（Via/Chrome）里正常，在 App 里空**。
如果浏览器请求带的头比 App 多，优先怀疑「站点校验了某个你没发的头」。

### 1.2 响应加密状态漂移

同一个接口，**匿名访问返回明文 JSON，登录访问返回 encData（AES 密文）**：
- `classTypeListPc`：匿名 → 明文 `{code,msg,data}`；登录 → `{code,msg,encData}`
- 实测同一天同一接口两种形态都出现过（取决于请求头里有没有 `aut`）

★ 教训：**「这个接口是明文」这个结论有时效性**。写规则时直接上双兼容，
不要赌「它现在是明文所以以后也是明文」。

## 2 定位法：对照实验（决定性）

### 2.1 四组对照（本次实际用的）

控制单一变量：`t/s` 头的有无 × 版本号新旧。

```
A 旧版号 无 t/s  → len=0     （复刻 App 当前源的请求）
B 新版号 无 t/s  → len=0
C 旧版号 有 t/s  → len=12801  ← 成功
D 新版号 有 t/s  → len=12801  ← 成功
```

结论：**版本号无关，t/s 才是关键**。

★ 若只跑 A/B 两组会得出「版本号没用」的错误结论；跑满四组才能锁定唯一变量。

### 2.2 对照实验代码模板（eval_js 真机跑）

```js
function req(tag, hdrs){
  try{
    var u = 'https://<host>/<path>?_t=' + Date.now();
    var r = String(java.ajax(u + ',' + JSON.stringify({headers:hdrs, timeout:20000})));
    out.push(tag + ': len=' + r.length + ' head=' + r.substring(0,60));
  }catch(e){ out.push(tag + ': ERR ' + e.message); }
}
// 四组逐一测：旧版号无ts / 新版号无ts / 旧版号有ts / 新版号有ts
```

### 2.3 判断「哪个头是关键」的通用清单

依次怀疑（按出现频率）：
1. **时间戳+签名对**（`t`+`s`、`ts`+`sign`、`timestamp`+`nonce`+`signature`）
2. 设备指纹（`device_fingerprint`、`deviceId`）
3. 版本号（`appVersion`、`sdkVersion`、`hr`、`fp_version`）
4. 渠道/来源（`source`、`chcode`、`clientType`）
5. 会话（`aut`、`Authorization`、`sid`）

★ 注意大小写：**同一个头在抓包里可能大小写混用**（`sdkVersion` 与 `sdkversion`），
必须照抄抓包原文，HTTP 头名大小写不敏感但**服务器可能做了区分**（本次实测新版必须用 `sdkVersion` 驼峰）。

## 3 切片式签名算法（本站实战）

### 3.1 算法定义

```
t = 当前毫秒时间戳（字符串）
s = md5( t 的第 4~8 位字符 )   // JS: t.substring(3,8)，即取下标 3,4,5,6,7 共 5 个字符
```

实测样例（可用于回归验证）：

| t | t[3:8] | s |
|---|---|---|
| 1791301673546 | 13016 | 6fb993285d56e6927284ff9b11ac6851 |
| 1791301595232 | 13015 | 9990b876c04ba1532bf63a8944989828 |
| 1791301802800 | 13018 | b79daeb88b395cd98299ae2a75ba77e5 |

★ 这种「切片式」签名（而非全串哈希）是**防逆向的轻量手段**——直接 md5(整个 t) 会失败。
逆向时必须**逐位试切**（起点/长度），本次实测是 `substring(3,8)`（起点 3、长度 5）。

### 3.2 逆向切片位置的方法

```js
// 已知 t 与 s，暴力试所有切片组合
function md5hex(s){var m=Packages.java.security.MessageDigest.getInstance('MD5');
  var b=m.digest(new Packages.java.lang.String(s).getBytes('UTF-8'));var r='';
  for(var i=0;i<b.length;i++){var h=(b[i]&255).toString(16);if(h.length<2)h='0'+h;r+=h;}return r;}
var t='1791301673546', expect='6fb993285d56e6927284ff9b11ac6851';
for(var start=0;start<8;start++){
  for(var len=4;len<=10;len++){
    if(md5hex(t.substring(start,start+len))===expect){console.log('start='+start+' len='+len);}
  }
}
// 输出：start=3 len=5
```

### 3.3 生产级实现（jsLib）

```js
function AC_ts(){ return '' + Date.now(); }
function AC_md5(s){var m=Packages.java.security.MessageDigest.getInstance('MD5');
  return AC_hex(m.digest(AC_u8(s)));}
function AC_H(sv){
  var t = AC_ts();
  var o = {
    sdkVersion:'1.1.9', sdk_version:'1.1.9', appVersion:'1.9.9', fp_version:'3.0.1',
    t: t, s: AC_md5(t.substring(3,8)), hr:'ver=1.9.9',
    deviceId: AC_dev(sv), device:'Android', clientType:'android',
    device_fingerprint: AC_FP,
    'User-Mark':'xhp', 'X-Requested-With':'mark.via',
    'Accept':'*/*', 'Accept-Language':'zh-CN,zh;q=0.9',
    'User-Agent':'...'
  };
  var tk = AC_g(sv,'acToken'); if(tk) o.aut = tk;
  var uid = AC_g(sv,'acUid'); if(uid) o.sid = uid;
  return o;
}
```

★ **每次请求都要重新生成 t/s**（时间戳必须新鲜）。因此 header 不能写静态值，
必须走「URL 选项里带 headers」或 `header` 字段的 `<js>` 动态生成。

## 4 敏感接口签名（登录等写操作）

本站登录/游客登录等敏感接口需要 5 个额外头：

| 头 | 值 |
|---|---|
| `X-Sensitive-Action` | `1` |
| `X-Request-Timestamp` | 毫秒时间戳（字符串） |
| `X-Request-Nonce` | UUID（任意随机即可，服务端不校验格式） |
| `X-Request-Body-SHA256` | **body 的 sha256**（见下方排序规则） |
| `X-Request-Signature` | `sha256([METHOD, path, ts, nonce, bodySha, SECRET].join('\n'))` |

### 4.1 bodySha 的排序规则（实测钉死）

**必须用「键名升序的紧凑 JSON」**，不能直接用原始 body 串：

```python
# 抓包验证：原始 body 顺序是 encryptedKey, iv, encryptedData（长度 530）
# 但 bodySha 实际是「字母序重排后」的哈希
body2 = json.dumps({"encryptedData":ed,"encryptedKey":ek,"iv":iv},
                   separators=(',',':'), sort_keys=True)
sha256(body2) == 抓包中的 X-Request-Body-SHA256   # MATCH
```

### 4.2 Rhino 实现

```js
function AC_stable(o){
  if(o===null||o===undefined||typeof o!=='object')return JSON.stringify(o===undefined?'':o);
  if(Object.prototype.toString.call(o)==='[object Array]'){
    var a=[];for(var i=0;i<o.length;i++)a.push(AC_stable(o[i]));return '['+a.join(',')+']';}
  var ks=[];for(var k in o){if(o.hasOwnProperty(k))ks.push(k);}
  ks.sort();var p=[];
  for(var j=0;j<ks.length;j++)p.push(JSON.stringify(ks[j])+':'+AC_stable(o[ks[j]]));
  return '{'+p.join(',')+'}';
}
function AC_SIG(m,path,body){
  var ts=AC_ts(); var nonce=AC_rhex(32);
  var bs = (typeof body==='string') ? AC_sha(body) : AC_sha(AC_stable(body===undefined?'':body));
  var sg = AC_sha([String(m).toUpperCase(), String(path), ts, nonce, bs, AC_SEC].join(AC_NL));
  return {'X-Sensitive-Action':'1','X-Request-Timestamp':ts,'X-Request-Nonce':nonce,
          'X-Request-Body-SHA256':bs,'X-Request-Signature':sg};
}
```

★ `AC_stable` 在 node 里验证输出 `{"account":"a","password":"p"}`（字母序），与抓包一致。

### 4.3 签名逆向验证法

拿到抓包里的 5 个头 + 原始 body，用 Python 离线复算：

```python
sig = hashlib.sha256('\n'.join(['POST', path, ts, nonce, body_sha, SECRET]).encode()).hexdigest()
# 与抓包 X-Request-Signature 比对
```

本次实测 **MATCH**，直接确认了 SECRET（`aB3!k9$zL2@mQ8#xV5^nY7*pW1(jH4&`）与拼接格式。

## 5 响应包裹形态三态化（第二个堵点）

**同一站点、同一接口家族、不同接口的返回结构完全不同**：

| 形态 | 样例 | 解析要点 |
|---|---|---|
| A. data 包裹 | `{code,msg,data:{...}}` | `resp.data` |
| B. 顶层直出 | `{domain,fictionId,fictionTitle,...}` | **resp 本身就是对象** |
| C. 数组包裹 | `{data:[...], domain, total}` | `resp.data` 是数组 |

★ 踩坑实录：fiction 详情接口返回的是形态 B（顶层直出），
而代码写的是 `AC_get(...).data` → `.data` 是 undefined → `fd.chapters` 报
`TypeError: 无法读取 undefined 的属性 "chapters"`。

### 5.1 三态兼容解析器

```js
// 统一取「业务数据」的辅助函数
function AC_unwrap(r){
  if(!r) return null;
  if(r.data!==undefined && r.data!==null){
    // 形态 A/C：data 包裹（data 可能是对象或数组）
    var d = r.data;
    // 形态 C 的变体：{data:{data:[...],total}} 双包裹
    if(d && d.data!==undefined && !Array.isArray(d)) return d;
    return d;
  }
  return r;  // 形态 B：顶层直出
}
```

### 5.2 encData 双兼容（必写）

```js
function AC_parse(sv, resp){
  var s = String(resp==null?'':resp);
  var o = null; try{ o = JSON.parse(s); }catch(e){ return null; }
  if(o && o.encData!==undefined && o.encData!==null){
    var tk = ''; try{ tk = AC_g(sv,'acToken'); }catch(e3){ tk=''; }
    if(!tk) tk = AC_TOK;         // 兜底：上次 AC_H 记录的 token
    if(!tk) return null;
    try{ return JSON.parse(AC_dec(String(o.encData), tk)); }
    catch(e2){ return null; }
  }
  return o;
}
function AC_dec(enc, tk){
  var key = String(tk).substring(2,18);   // ★ 本站规则：key=token 的第 3~18 位
  var raw = Packages.android.util.Base64.decode(String(enc),2);
  var k = new Packages.javax.crypto.spec.SecretKeySpec(
            new Packages.java.lang.String(key).getBytes('UTF-8'),'AES');
  var iv = new Packages.javax.crypto.spec.IvParameterSpec(
            new Packages.java.lang.String(key).getBytes('UTF-8'));   // IV=key
  var c = Packages.javax.crypto.Cipher.getInstance('AES/CBC/PKCS5Padding');
  c.init(2, k, iv);
  return String(new Packages.java.lang.String(c.doFinal(raw),'UTF-8'));
}
```

★ `Base64.decode(enc, 2)`：第二参 2 = `NO_WRAP`（base64 里可能含 `+` `/` `=`，
用 0 或默认值在部分实现下会报 `bad base-64`）。

★ 顺带记：本次遇到 `bad base-64` 报错的两次都是**瞬时问题**（同一段代码重跑即过），
不要急着改代码——先重跑一次再判断。

## 6 登录态检查的权威接口

本站新增了 `POST /api/user/base/info`（body `{"userId":<uid>}`）作为登录态探针：

| 返回 | 含义 |
|---|---|
| `{code:200, ...用户对象}` | 登录有效 |
| `{code:301,msg:"刷新token"}` | token 过期（需重登） |
| `{code:1001,msg:"token解析错误"}` | token 无效/未登录 |

★ 比「首页是否含某元素」可靠得多（不依赖页面结构）。写进登录界面按钮：

```js
function AC_CKLOGIN(sv,jv){
  var tk = AC_g(sv,'acToken');
  if(!tk) return {ok:false,code:'-',msg:'未登录（未保存 token）'};
  try{
    var op = {method:'POST', body:'{}', headers:AC_H(sv), timeout:20000};
    op.headers['Content-Type'] = 'application/json;charset=UTF-8';
    var r = String(jv.ajax(AC_hostfix(sv,jv)+'/api/user/base/info,'+JSON.stringify(op)));
    var o = null; try{ o = JSON.parse(r); }catch(e0){ o=null; }
    if(!o) return {ok:false,code:'-',msg:'无响应（线路不通）'};
    var c = Number(o.code);
    if(c===200){
      var d = o.encData ? AC_parse(sv,r) : o.data;
      var nm = (d&&(d.nickName||d.userName)) ? String(d.nickName||d.userName) : AC_g(sv,'acNick');
      return {ok:true, code:'200', msg:'登录有效', nick:nm, uid:String((d&&d.userId)||AC_g(sv,'acUid'))};
    }
    return {ok:false, code:String(o.code), msg:String(o.msg||('错误码'+o.code))};
  }catch(e){ return {ok:false, code:'-', msg:String(e.message||e)}; }
}
```

★ 注意：`code=200` 时响应体也可能是 encData（本接口实测两种都出现过）——
所以 200 分支也要走 `o.encData ? AC_parse(...) : o.data`。

## 7 工程纪律（本次新踩）

### 7.1 带连字符的 HTTP 头键名必须加引号

```js
// ✘ 语法错误（node --check 直接抓）
var o = { User-Mark:'xhp' };
// ✔
var o = { 'User-Mark':'xhp', 'X-Requested-With':'mark.via' };
```

★ 构建脚本里的 `node --check` 是唯一能提前抓到这类错误的手段——**必须每个 JS 块都过一遍**。

### 7.2 新增内容形态时要同步改 4 处

本站新增 fiction（小说）形态后，要同步改：

| 位置 | 改动 |
|---|---|
| `AC_id` | URL 正则加 `/f/(\d+)` 分支 |
| `AC_url` | 拼 URL 时加 `f` 前缀 |
| `ruleBookInfo.init` | 加 fiction 分支（详情字段映射） |
| `ruleToc.chapterList` | 加 fiction 分支（章节列表 + book.type） |
| `ruleContent.content` | 加 fiction 分支（文字正文/音频 URL） |
| `bookUrlPattern` | 加 `f` 前缀 |

★ 漏改任一处 = 该形态在对应环节静默失败。

### 7.3 book.type 位掩码（小说=8 / 有声=32）

```js
try{ book.type = (id.type==='fiction') ? (book.type||8) : ((id.type==='comic')?64:4); }catch(e){}
```

★ 文字小说=8（text），有声小说=32（audio）。
有声小说的正文规则直接返回 mp3 URL 纯文本（音频通道要求纯 URL，不能包 HTML）。

### 7.4 「提示型虚拟条目」的 URL 必须能被 AC_id 识别

发现页某分区需要登录时，不能直接抛异常（会中断整个列表），
应返回一条**提示条目**；但该条目的 URL 也必须能被 `AC_id` 友好处理，否则用户点击时报错。

```js
// AC_id 里加提示识别
if(u.indexOf('x?j=n:')>=0) throw new Error('小说分区需要登录：请到 书源菜单→登录 ...');
```

## 8 开箱模板：动态签名头书源的完整骨架

```js
// ===== 常量 =====
var SEC = '<从抓包 X-Request-Signature 逆向出的 SECRET>';
var FP  = '<设备指纹（固定值，从抓包抄）>';

// ===== 基础工具 =====
function hex(b){var s='';for(var i=0;i<b.length;i++){var h=(b[i]&255).toString(16);
  if(h.length<2)h='0'+h;s+=h;}return s;}
function u8(s){return new Packages.java.lang.String(String(s)).getBytes('UTF-8');}
function md5(s){var m=Packages.java.security.MessageDigest.getInstance('MD5');
  return hex(m.digest(u8(s)));}
function sha(s){var m=Packages.java.security.MessageDigest.getInstance('SHA-256');
  return hex(m.digest(u8(s)));}

// ===== 动态头（每次调用重新生成时间戳）=====
function HDR(sv){
  var t = ''+Date.now();
  var o = {
    'sdkVersion':'1.1.9','appVersion':'1.9.9','fp_version':'3.0.1',
    t:t, s:md5(t.substring(3,8)),   // ★ 切片位置靠暴力试出
    'User-Mark':'xhp','X-Requested-With':'mark.via',
    'User-Agent':'<手机 UA>',
    device_fingerprint: FP,
    deviceId: dev(sv)
  };
  var tk=sv.get('token'); if(tk) o.aut = String(tk);
  return o;
}
function OPT(sv){ return ',' + JSON.stringify({headers:HDR(sv), timeout:45000}); }

// ===== 请求 =====
function GET(sv,jv,path,qs){
  var u = host(sv)+path+(qs?('?'+qs):'');
  return parse(sv, jv.ajax(u+OPT(sv)));
}
```

| 站点 | 签名类型 | 缺头表现 | 备注 |
|---|---|---|---|
| acfan.com（本次） | t+s 切片（md5(t[3:8])）+ 敏感 5 头 | 200 + content-length:0 | 响应明密文随登录态漂移 |
| （对照）ppxsw.cc | search_time Cookie 标记 | 拒答页 | 见《Cookie标记型限频破解》 |
| （对照）sangtacviet | 无签名，但会话铸 key | 无 | 见《对照实验驱动的接口逆向》 |

★ 与已有方法论的边界：
- 「Cookie 标记型限频」= 服务端查**Cookie 键存在性**；
- 「切片签名头」（本篇）= 服务端查**请求头的哈希正确性**；
- 两者都用「对照实验」定位，但修复手段完全不同（前者删 Cookie，后者算哈希）。
