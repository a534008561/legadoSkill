## 适用场景

遇到以下任一任务，直接按本文档流程执行：

- 书源需要**账号登录**才能搜索/阅读（302 到登录页、返回占位数据等）
- 需要**注册功能**（书源内完成开户，含手机号字段）
- 站点有**图形验证码**（`/code.jpg` 类端点）
- 搜索被**限频**（提示"请稍后再试"、倒计时、返回推荐书占位列表）

## 0. 三十秒速查表

| 问题 | 一句话结论 |
|---|---|
| 验证码怎么弹？ | `code = java.getVerificationCode(图片URL+"?"+Math.random())` **一行搞定**：自动弹窗看图→用户输入→返回所填值（ppxsw 登录/注册双函数实测用法） |
| `java.getVerification` | ✅ **存在**：弹图+输入框一体返回所填值（官方 JsExtensions 标准方法）。⚠️ eval_js 独立环境 typeof 探测为 undefined 属上下文受限，勿据此判不存在 |
| UI 值怎么取 | `source.getLoginInfoMap()` 返回 Java Map，`res.get("帐号")` 逐键取 |
| 密码加密 | 抠站点 JS 进 eval_js 实跑比对；多数为标准 MD5 hex 小写→直接 `java.md5Encode(pwd)` |
| POST 怎么发 | `java.ajax(url+","+JSON.stringify({body, method:"POST", headers: JSON.stringify(headers)}))` |
| 结果怎么反馈 | `java.longToast(html)` 服务端原文直接弹出（`1\|`=成功，`0\|文案`=失败原因），配 `Thread.sleep(3000)` 留展示时间 |
| 延迟等待 | 此 App **没有 java.sleep**！只能 `Packages.java.lang.Thread.sleep(ms)` |
| 改单个 Cookie 键 | `cookie.setCookie(url,str)` 是**整体替换**！必须"取全文→正则改→回写全文" |
| 限频怎么破 | 四组对照实验定位校验依据；若只查 Cookie 存在性→请求前置 JS **删键即破** |
| 注册接口参数 | 与登录**不同名**（name/pass/pass2/mobile/code），别照抄登录的 user_* |
| tocUrl 写在哪 | **ruleBookInfo 内**（放 ruleToc 被静默丢弃）；且不支持 `\|\|` 兜底 |
| 手动 OK 但 App 失效 | 头号嫌疑 **UA 双模板**，用 `get_http_log` 看 App 实际收到的响应再定规则 |
| 目录乱序 | 阅读**只按出现顺序去重、不排序**；用 li 的 class 特征过滤"最新章节倒序区" |

## 1. 登录接口分析三步法

1. **抓登录页 HTML**：找 `<form>` 和按钮 onclick 绑定的 JS 函数名
2. **下载对应 common*.js**：提取该函数，拿到真实端点、参数名、成功判定标记
   ```js
   // 典型形态
   jq.post('/qs_login_go.php', {user_name, user_pass, user_code}, function(data){
       data.split("|")[0] == "1"   // ← '1|xxx' = 成功, '0|文案' = 失败原因
   })
   ```
3. **逆向加密函数**：站点加密 JS 整体抠进 eval_js 实跑，与 Python 标准算法比对：
   ```js
   qsskel("a7894563") === "fd26f013d2c05c33c6ab53e654b8bf97"  // true → 标准 MD5 hex 小写
   ```
   一致就直接用 `java.md5Encode(pwd)`，无需内联。
   > 识别特征：`function xxx(o){... return (G(T)+G(S)+G(R)+G(Q)).toLowerCase()}` 结构 = Paul Johnston 风 JS-MD5。

探测技巧："故意填错验证码"逐项触发服务端校验，记录各错误文案（如"非法访问/验证码错误/密码错误"），摸清校验环节先后顺序，书源内的错误提示才有依据。

## 2. 登录/注册 UI 蓝本（ppxsw 双函数范式）

### loginUi：一个界面同时承载登录与注册

```json
"loginUi": "[{\"name\":\"帐号\",\"type\":\"text\"},{\"name\":\"密码\",\"type\":\"password\"},{\"name\":\"手机\",\"type\":\"text\"},{\"name\":\"登录\",\"type\":\"button\",\"action\":\"dl()\"},{\"name\":\"注册\",\"type\":\"button\",\"action\":\"zc()\"}]"
```

- 字段名随意（中文即可），按钮 action **直接写函数调用名**
- 注册需要的额外字段（手机）与登录共用同一 UI，多放一个 text 框而已，不必另开界面

### loginUrl：顶层具名函数集（不加 @js: 前缀）

```js
function dl() {                                   // 登录按钮 action 调 dl()
    java.log("模拟登录请求");                       // 日志留痕便于排查
    cookie.removeCookie(source.key);              // ★ 清旧会话,保证验证码图与新会话同源
    res = source.getLoginInfoMap();               // ★ UI取值:Java Map风格
    use = res.get("帐号");
    pwd = res.get("密码");

    code = java.getVerificationCode("https://www.ppxsw.cc//code.jpg?" + Math.random());  // ★ 弹验证码

    body = `user_name=${use}&user_pass=${java.md5Encode(pwd)}&user_code=${code}`;

    html = java.ajax("https://www.ppxsw.cc//qs_login_go.php," + JSON.stringify({
        "body": body,
        "method": "POST",
        "headers": JSON.stringify(headers)
    }));

    java.longToast(html);                         // ★ 服务端原文直接反馈('1|'=成功)
    Packages.java.lang.Thread.sleep(3000);        // 给 toast 留展示时间(无java.sleep!)
}
```

**headers 标配模板**（ppxsw 实测可用，XHR 类接口通用）：

```js
headers = {
    "accept": "*/*",
    "accept-language": "zh-CN,zh;q=0.9",
    "cache-control": "no-cache",
    "content-type": "application/x-www-form-urlencoded; charset=UTF-8",
    "pragma": "no-cache",
    "x-requested-with": "XMLHttpRequest",
    "Referer": "https://www.ppxsw.cc/",
    "Referrer-Policy": "strict-origin-when-cross-origin",
    "User-Agent": "Mozilla/5.0 (Linux; Android 15; K) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/133.0.0.9 Mobile Safari/537.36"
}
```

五个要点：
1. `cookie.removeCookie(source.key)` 先清会话再取码——验证码与会话绑定，旧会话残留会导致"码明明对的却报错"
2. `source.getLoginInfoMap()` 是 Java Map，用 `.get(key)` 取值（另一种风格是 `login(b)` 函数内直接用 `result` map，二选一勿混用）
3. `java.ajax(url+","+JSON.stringify({body, method, headers}))` 是 lyc 版 POST 标准姿势，注意 headers 要二次 stringify
4. `java.longToast(html)` 把服务端原文（含失败原因文案）直接呈现给用户，最省事最透明
5. 可选加固：成功分支补 `source.putLoginHeader(java.getCookie(host))` 持久化登录头，CookieJar 会话意外丢失时兜底

## 3. 验证码接入：一行取码

```js
code = java.getVerificationCode("https://www.ppxsw.cc//code.jpg?" + Math.random());
```

调用后自动弹出验证码窗口 → 用户看图输入 → 函数返回所填值 → 拼进 body 提交。**这就是 ppxsw 登录（dl）与注册（zc）双函数的实测用法。**

配套认知：

| API | lyc 版状态 |
|---|---|
| `java.getVerificationCode(imgUrl)` | ✅ 存在，弹窗取码（本文主线） |
| `java.startBrowser(imgUrl,'验证码')` | ✅ 备选：内置浏览器看图 + loginUi 验证码 text 框手填 |
| `java.getVerification(imgUrl)` | ✅ **存在**：弹图+输入框一体，返回所填值 |
| `java.getVerificationCode(imgUrl)` | ✅ **存在**（签名 `String getVerificationCode(String)`）：ppxsw 登录/注册双函数实测主线 |

原理与排错：
- `/code.jpg?rand` 的响应同时返回图片字节和 `Set-Cookie` 会话——**提交时必须携带同一会话**，服务端才能把你输的码和发给你的图对上号。所以取码前先 `cookie.removeCookie(source.key)` 重置，取码与 POST 之间不要再发其他请求
- URL 加 `?"+Math.random()` 防缓存，确保每次拿新图新码
- 若个别 App 版本上点击按钮无反应（弹窗未出现），退回 startBrowser 方案即可
- ⚠️ **方法论教训：API 存在性必须在真实调用上下文里验证**——eval_js 独立环境 `typeof java.getVerification` 返回 undefined 只是该环境能力受限（同先例：jsLib 作用域 ajax/connect 也受限），不代表 API 在 loginUrl/loginUi 上下文不存在。判断依据优先级：书源实跑 > 官方源码 > 单一环境探测
- 抓包验证会话：取码后立刻 `java.log(cookie.getCookie(host))`，确认出现了新 session 键

## 4. 注册流程接入（qs_register_go.php）

注册与登录是**两套参数名体系**，且多一个手机号字段：

| 字段 | 登录 `/qs_login_go.php` | 注册 `/qs_register_go.php` |
|---|---|---|
| 账号 | `user_name` | `name` |
| 密码 | `user_pass`（MD5 小写） | `pass` **和** `pass2`（两次均 MD5） |
| 验证码 | `user_code` | `code` |
| 手机号 | 无 | `mobile` |
| 成功判定 | `1\|` 前缀 | 文案不定 → longToast 原文 |

```js
function zc() {                                   // 注册按钮 action 调 zc()
    java.log("模拟注册请求");
    cookie.removeCookie(source.key);              // ① 重置会话再取码
    res = source.getLoginInfoMap();
    use = res.get("帐号");
    pwd = res.get("密码");
    sj  = res.get("手机");
    code = java.getVerificationCode("https://www.ppxsw.cc//code.jpg?" + Math.random());
    body = `name=${use}&mobile=${sj}&pass=${java.md5Encode(pwd)}&pass2=${java.md5Encode(pwd)}&code=${code}`;
    html = java.ajax("https://www.ppxsw.cc//qs_register_go.php," + JSON.stringify({
        "body": body, "method": "POST", "headers": JSON.stringify(headers)
    }));
    java.longToast(html);                         // ② 结果文案各异,原文展示最稳
    Packages.java.lang.Thread.sleep(3000);
}
```

注意：
- 注册成功**不必**持久化登录头（站点一般不自动登录），toast 提示用户"用刚注册的账号走一次登录"
- `pass2` 漏传/不一致时部分站只回"非法访问"；先浏览器手动注册一遍记录各分支正常文案做基准
- 完整双函数实现样本：examples/`皮皮小说网ppxsw_注册版参考.json`

## 5. Cookie 三大铁律

### 铁律一：setCookie 是整体替换，不是合并

```js
// ✗ 这一句会把该域名全部 Cookie 清空只剩一个 → 登录态被抹、全体302
cookie.setCookie(u, "search_time=123");

// ✓ 取全文 → 正则删/改键 → 回写全文
var c = String(cookie.getCookie(u)).replace(/search_time=\d+/, "");
cookie.setCookie(u, c);
```

### 铁律二：验证码绑定会话

取码前 `cookie.removeCookie(source.key)` 重置；取码与提交之间不发无关请求（见第 3 节）。

### 铁律三：限频先做对照实验，可能"删键即破"

ppxsw 实测：服务端**只检查请求是否携带 search_time Cookie**——带就拒（回12条推荐书+倒计时），不带就当首次放行；且**每次失败的尝试都会重置倒计时**（干等无效，实测 P1=122s→等26s→P2=122s）。

四组对照实验定位机制：
1. 立即连发两次 → 观察提示变化（是否重置计时）
2. 静默等待后单发 → 排除纯时间因素
3. 改 Cookie 值再发 → 判断是否看值
4. 删键再发 → 判断是否只查存在性

确认为"只查存在性"后，把删键放进**请求前置 JS**（每次搜索前自动执行）：

```xml
<js>
var U="https://www.ppxsw.cc/";
var c=String(cookie.getCookie(U)).replace(/search_time=\d+/,"");
cookie.setCookie(U,c);
"/search.html,{\"method\":\"POST\",\"body\":\"s=\"+encodeURIComponent(key)+\"\"}"
</js>
```

放在 searchUrl 或 ruleSearch.bookList 开头均可，效果等同。

## 6. 高频陷阱速查

| 陷阱 | 症状 | 解法 |
|---|---|---|
| **UA 双模板** | 工具里规则命中N条，App里0条 | 分类页/目录页按UA返回两套DOM。开HTTP日志→`get_http_log(id)`看App实际收到的体→按它写规则。eval_js取移动版页面须显式带移动UA（裸java.ajax走桌面UA） |
| **tocUrl 位置** | 日志"获取目录链接"永远是详情页本身 | tocUrl 属于 **ruleBookInfo**；放 ruleToc 被反序列化静默丢弃。且**不支持`\|\|`兜底**（整串被当URL发出） |
| **目录乱序** | 前14章是最新章节、后面才从第1章开始 | 移动版目录=最新14章倒序区(li无class)+正序区(li.br-b-1)+推荐区(第二个ul)。修复：`class.ph_list.0@class.br-b-1@tag.a`。跨分页各页同样滤掉最新区→天然有序 |
| **base64 动态对象名** | 正文空白或乱码 | 加密对象名每本书随机(rgr.owes/vypflhij.atyffy…)。恒定特征`var (\w+)=\{_keyStr`动态提名字再全局解码；简化替代：直匹配`/PHA\+[A-Za-z0-9+/]+={0,2}/g`（PHA+=`<p>`编码头）逐段 `java.base64Decode` |
| **分页变量随机名** | 只拿到第1页 | 匹配**赋值形态**而非变量名：`/'(\/[a-z]+\/[a-z]+_[0-9]+\.html)'/`。末页变量指向下一章不含_N.html→自动不匹配 |
| **延迟函数** | 报"找不到函数sleep"，整个规则炸 | 无java.sleep！用`Packages.java.lang.Thread.sleep(ms)` |
| **文字匹配省略号** | `text.查看更多章节` 匹配失败 | 页面实际是"查看更多章节..."；改模糊匹配或 href 定位 |
| **respondTime 过小** | 校验器误报失效 | 慢站设大（如180000），否则批量校验超时连坐 |

## 7. MCP 调试速查

| 场景 | 手法 |
|---|---|
| 规则手动OK但App失效 | `set_http_log_recording(true)` → 触发请求 → `get_http_log(id)` 看**App实际收到的响应体**（双模板/CDN缓存一锤定音） |
| debug_source 超时 | 含 sleep/长链路改用 `eval_js` 分段模拟；MCP客户端约120s上限 |
| 校验误报失效 | 连续快速请求触发限频所致；先破限频再校验 |
| 确认API存在性 | eval_js 里 `typeof java.xxx` 先探，再 try-catch 实调 |
| 探测登录校验环节 | 固定session+故意错码，按返回文案区分校验先后 |
| 验证限频是否重置计时 | probe→sleep→probe 对比倒计时读数：递减≈间隔则不重置；不变则每次尝试都重置 |
