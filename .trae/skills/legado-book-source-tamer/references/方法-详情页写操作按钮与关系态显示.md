## 一、现象谱系

用户报"详情页不刷新"时，**别急着怀疑刷新**。同一句抱怨下面有三种完全不同的病：

| 用户说法 | 真因 | 定位关键 |
|---|---|---|
| "下拉刷新不会刷新 useweb" | 刷新**确实**重跑了规则、重绘了面板，但面板数据的来源（带 TTL 的缓存）**没有任何写入方** | 顺着缓存键找 setter，找不到就是这句提示是空头支票 |
| "点了关注没反应" | 写请求成功了，但 √ 的判据不存在（关系态没读对）→ 画面无变化 | 点完立刻 GET 一次业务对象，看服务端关系字段有没有翻转 |
| "只能关注不能取消" | 本 App HTTP 层**根本没有 DELETE 动词**，URL 选项里写 `method:"DELETE"` 会**静默降级成 GET** | 读 `RequestMethod` 枚举，不用试 |

三者共同的深层病灶是同一个：**"改服务端状态"和"把状态显示回来"是两件事，必须各自有通路**。
只做了 POST 没做读态，用户看到的就是"没反应"；只做了读态没做写操作入口，用户看到的就是"刷不出来"。

## 二、源码级依据

以下均为 LegadoTeam 版源码逐行确认（`/workspace/legado_src`，2026-09-11 快照）。

### 2.1 ★ 动词白名单：DELETE 被静默降级

```kotlin
// model/analyzeRule/AnalyzeUrl.kt:268
option.getMethod()?.let {
    method = when (it.uppercase()) {
        "POST" -> RequestMethod.POST
        "HEAD" -> RequestMethod.HEAD
        else   -> RequestMethod.GET          // ← DELETE / PUT 全部落到这里
    }
}
// help/http/RequestMethod.kt:3
enum class RequestMethod { GET, POST, HEAD }   // ← 枚举里压根没有 DELETE
```

**三个推论（写源前先看，能省一整天）**：

1. 书源里写 `{"method":"DELETE"}` 不报错、不提示，**发出去是 GET**。
   GET 打到"删除"端点通常返回该资源的**读取结果或幂等写结果**，于是表现成
   "点了取消，啥也没发生"——iwara 取消关注就是典型：`DELETE /user/{id}/followers`
   退化成 GET，而该站 `POST /user/{id}/followers` 幂等（重复关注返回**同一行 id** `{"id":59252845"}`），
   所以连报错都没有，纯粹是空气。
2. 同理 **PUT 也不可用**。凡 RESTful 站点的 `PATCH/PUT/DELETE`（改昵称、取消收藏、移出列表、删评论）
   在书源侧一律按"做不了"设计，不要浪费时间试 URL 写法。
3. 唯一例外通道：站点自己提供 **POST 语义的兜底路由**
   （形如 `POST /xxx?_method=DELETE`、`{"_method":"DELETE"}`、`X-HTTP-Method-Override` 头），
   这属于**站点行为**，必须实测，见第五章。

### 2.2 关系态是随业务响应一起下发的（√ 零成本）

`loginHeader` 由 `BaseSource.getHeaderMap(true)` 在**同域请求**上自动附加，
所以只要书源登录时写过 `putLoginHeader({"Authorization":"Bearer xxx"})`，
书源规则里那些**不带任何 headers 的普通请求就已经是登录态**。

于是站点常在业务对象里内嵌"我与它的关系"字段，直接拿来当 √ 判据：

```jsonc
// iwara GET /video/{id}（带 loginHeader）响应节选
{ "id":"czrvd0EzH2fq7h", "liked": true,          // ← 我是否收藏了它
  "user": { "id":"6012a7b9-…", "username":"ppo2024",
            "following": true,                    // ← 我是否关注了该作者
            "followedBy": false, "friend": false } }
```

真机实证：关注前后同一请求，`user.following` 由 `false → true`，`followedBy` 始终 `false`
（`followedBy` 是"TA 关注了我")。**这类字段是 √ 的最优解：不加请求、不建账本、永不失真。**

### 2.3 详情"下拉刷新"到底会不会重跑规则

```kotlin
// ui/book/info/BookInfoActivity.kt:1173
refreshLayout?.setOnRefreshListener { refreshLayout.isRefreshing = false; refreshBook() }
// :482 → BookInfoViewModel.refreshBook(book):194 → onFinally { loadBookInfo(book, false) }
// :231 → WebBook.getBookInfo(...)  → model/webBook/BookInfo.kt:42 执行 ruleBookInfo.init
//                                    → :123 intro，<usehtml>/<useweb>/<md> 开头则原样存 book.intro
```

`WebBook/BookInfo` 里**没有任何详情页结果缓存**（grep `ACache|upCache` 零命中）——
所以"下拉刷新不刷新"**几乎不可能是刷新链路的锅**，一定是**规则产出的内容本身没变**。
排查顺序：①数据源是否 TTL 缓存 ②缓存有没有写入方 ③写的那个分支是否真有人触发（哨兵变量！）。

按钮改完状态要**立刻**重绘，靠的是 `java.refreshBookInfo()`（`EventBus.REFRESH_BOOK_INFO` →
`BookInfoActivity:460 observeEvent → refreshBook()`），语法见按钮选型树篇，本文只强调：
**凡是写操作的按钮，收尾必须有它**，否则用户就要手动下拉，于是引出第六章那一串坑。

## 三、端点发现：从站点自己的 JS bundle 里读 API 表

写"关注/取消/收藏/点赞"这类按钮，最费时间的从来不是实现，而是**猜端点和动词**。
不要撞路径，直接把站点前端打包出来的 API 定义表 grep 出来——**一次拿到「路径 + 动词 + 幂等性 + 文案」**。

```bash
# 1) 抓页面，拿到 bundle 地址（Nuxt/webpack 站通常一个 main.*.js）
curl -A "$UA" https://www.iwara.tv/users/someone -o page.html
grep -o 'src="[^"]*\.js"' page.html

# 2) 抓 bundle（记得带 UA 和 gzip 解码）
curl -A "$UA" --compressed https://www.iwara.tv/main.838884031a28ff0e346d.js -o main.js
```

然后在 bundle 里搜**动作名词**（`Follow`/`Like`/`Favorite`/`Subscribe`），
前端一般都有一个集中定义请求的 API 模块，形如：

```js
// iwara main.js 实测片段（压缩后仍可读）
createFollow:  function(e,t){ return A(e, "/user/"+t+"/followers", {...f, method:"POST"}) },
destroyFollow: function(e,t){ return A(e, "/user/"+t+"/followers", {...f, method:"DELETE"}) },
fetchFollowers:function(e,t){ return A(null,"user/"+e+"/followers", {...f, query:t}) },
fetchFollowing:function(e,t){ return A(null,"user/"+e+"/following", {...f, query:t}) },
destroyComment:function(e,t){ return A(e,"comment/"+t,           {...f, method:"DELETE"}) },
```

**读这张表一次性得到四件事**：

| 得到 | 例子 | 用途 |
|---|---|---|
| 真实路径与参数位 | `/user/{t}/followers`，t 是**用户 UUID 不是用户名**（`/user/ppo2024` 返回 `errors.notFound`） | 不用猜 |
| HTTP 动词 | 关注 POST / 取关 DELETE | 立刻知道取关做不了（见 2.1） |
| 幂等/返回体 | POST 返回 `{"id":行id}`，重复返回同一行 | 决定成功判据（别只判 200） |
| 关系字段名 | 同表附近 grep `following\|followedBy` 或 i18n `followButton.*` | √ 的判据 |

顺手 grep i18n 文案表能拿到官方中文措辞，直接照抄到按钮上，比自造词专业：

```js
"followButton.follow":"关注", "followButton.follow.success":"已关注 {name}",
"followButton.unfollow":"取消关注", "profile.sidebar.followers":"粉丝"
```

> **配套取证**：写操作端点确认后，用 `mcp eval_js` 真机跑一次读接口看字段翻转，
> 再跑一次写接口看返回体——**两端都对上才开始写规则**（第九章）。沙盒能连 API 但**没有登录态**，
> 关系态类字段只能在真机验。

## 四、关系态显示：四层阶梯 + 三态 UI

√ 从哪来？按"越上层越可信、越下层越兜底"排：

| 层 | 判据 | 成本 | 失效场景 |
|---|---|---|---|
| **L1 业务响应内嵌字段** | `user.following === true` | 0（详情那一次请求就带上） | loginHeader 掉线 → 恒 false |
| **L2 专用关系接口** | `GET /video/{id}` 的 `liked` | 1 请求 | 同上 |
| **L3 本机账本** | `iwFol="uid:ts;…"`，10 分钟窗 | 0 网络 | 用户在网页改了 → 本机不知道（所以必须短 TTL） |
| **L4 显式核对按钮** | 扫服务端回写账本 | N 请求 | 需要用户主动点 |

**推荐组合：L1 为主 + L3 填空窗**。
为什么还要 L3？因为点完关注到"详情重拉回来"之间存在一次重绘的空窗
（`refreshBookInfo()` 走的是异步刷新，且若 token 刚好在刷新中被换成匿名响应，L1 会退回 false），
账本能保证**点下去 √ 就一定出现**，而 10 分钟 TTL 又让它不至于把"用户在网页取关了"这件事记成一辈子。

### 三态 UI（自己的内容要单独一档）

```
未关注：  👤 作者 ppo2024   [＋ 关注作者 ppo2024]  [🏠 作者主页]
已关注：  👤 作者 ppo2024   [√ 已关注 ppo2024]     [🏠 作者主页]
是自己：  ✍ 这是你自己的视频                       [🏠 我的主页]
未登录：  整行不出现（别放按钮，点了只能报错，纯噪音）
```

三条硬规矩（都是被真机打脸回来的）：

1. **未登录不要显示关注按钮**。关系态在匿名响应里恒 false，按钮点下去只能返回 🔒，
   用户会以为源坏了。用 `if(IWRG(Sv,'iwTk','')==''){return L;}` 整行跳过。
2. **作者 id == 自己 uid 时不要给关注按钮**（iwara 会返回 `errors.notFound`，很怪），改成"我的主页"。
3. **显示名与 onclick 参数要分开清洗**：
   显示走 HTML 转义（`&`→`&amp;`、`<`→`&lt;`），onclick 参数走**删除**（`&`→`和`、去掉 `' < > "`），
   两者混用就会要么显示成 `&amp;` 要么把 onclick 截断。参照 `IWRPLADD` 的 `lab` / `safe` 双变量写法。

## 五、取消/删除类动作：降级决策树

```
需要"取消关注 / 取消收藏 / 移出列表 / 删除"？
│
├─ 1. 站点 API 是不是 DELETE/PUT？（bundle 里 destroyXxx 的 method）
│    ├─ 否（有 POST 版切换接口）→ 直接做，按钮做成 toggle
│    └─ 是 → 本 App 发不出 DELETE（§2.1）→ 继续 2
│
├─ 2. 站点是否支持 POST 语义覆盖？（实测，不要猜）
│    ├─ POST /xxx?_method=DELETE
│    ├─ POST /xxx  + 头 X-HTTP-Method-Override: DELETE
│    ├─ POST /xxx  + body {"_method":"DELETE"}
│    └─ 判据：调用后**再读一次关系字段**。iwara 三种全部返回 {"id":59252845}
│        （同一行 id）且 following 依旧 true → 只是幂等重放关注，全部作废
│
├─ 3. 绕开 java.ajax 自己发？（**别投入，本文已替你试过**）
│    原始 TLS 套接字手写 HTTP/1.1：SSLSocketFactory.getDefault().createSocket()
│    → connect(ip,443) → createSocket(plain,'api.iwara.tv',443,true)（保 SNI 与证书校验）
│    → 手写 "DELETE /user/{id}/followers HTTP/1.1" + Host + Authorization + Connection: close
│    → 逐字节读（Rhino 里 java.lang.reflect.Array 被 JavaClass-shutter 封，newInstance 报
│       "无法读取 undefined 的属性 Byte"）+ 手工解 chunked
│    结果：Cloudflare 对该 TLS 指纹 **Read timed out**（GET 也一样超时，说明握手通、CF 不给响应）。
│    这条路只在"直连源站 IP、非 CF 前端"的站点有戏（对照 pixiv 东京源站成功案例）。
│
└─ 4. 降级交付（默认终点）：
     · 按钮不假装能取消，点下去给一句**说清楚为什么**的长文案
     · 顺手 java.startBrowser(对象主页, 标题) 把用户送到"能取消的地方"
     · 文案模板：「🌐 已打开 X 的主页：本App的 java.ajax 不支持 DELETE 请求，
        取消关注请在主页点「已关注」」
     · 书源注释与面板帮助里同步写明该限制（用户会反复来问"是不是坏了"）
```

> **关键姿势**：把"做不到"写成一条**带原因、有下一步动作**的提示，而不是静默失败或误导文案。
> 这一条能挡掉绝大多数"点了没反应"的报障。

## 六、面板刷新出口：TTL 缓存三件套

### 6.1 本轮真实事故：哨兵变量的"空头支票"

面板写了一句 **"下拉刷新详情页即可载入你的列表"**，实现却是：

```js
// IWRINIT（详情初始化规则）
if (IWRG(Sv,'iwMyPlNeed','')!='' && IWRG(Sv,'iwTk','')!='') { Sv.put('iwMyPlNeed',''); IWRMYPL(...); }
//                        ↑ 全源码 grep 'iwMyPlNeed' 只有这一处“读”，没有任何一处“写”
```

于是：**永远没有第二次请求，缓存永远为空，面板永远停在那句提示上**，
用户看到的就是"下拉刷新没刷新 useweb"（而刷新链路其实完全正常，§2.3）。

> **检查动作（30 秒，建议固化进验收）**：凡是"条件触发型"分支（哨兵变量、need 标志、
> `xxx==1` 才执行），**grep 那个键名，确认存在写入方**；写入方不存在的分支就是死代码，
> 要么补写入方，要么把依赖它的用户提示删掉。

### 6.2 三件套

带 TTL 的缓存面板（关注列表、播放列表、收藏数、线路延迟…）必须同时具备：

| 件 | 做法 | 本轮实现 |
|---|---|---|
| **① 自愈补拉** | 渲染函数发现缓存缺失/过期 → **自己补一次**再渲染，不等外部触发 | `IWRINTR` 里 `arr==null && 已登录 && 单视频` → `IWRMYPL()` |
| **② 冷却** | 补拉前**先**写时间戳，60 秒内不再试（失败也要冷却） | `iwPlTry`；写在请求**前**，所以"0 个列表"的账号不会每次进详情白等一个 RT |
| **③ 显式刷新按钮** | 清缓存 → 强拉 → `java.refreshBookInfo()` | 「🔄 刷新收藏夹」→ `IWRPLRF()`（TTL 语义救不了"用户刚在网页新建了列表"，只有这个能） |

**加一条收尾**：所有"扫描/核对"型按钮（`🔎`）跑完顺手**回写缓存 + `refreshBookInfo()`**，
把"再下拉刷新一次就能看到"这类话从产品里消灭掉。

### 6.3 列表型按钮组的数量上限要对齐真实数据

`for(i=0;i<arr.length&&i<12;i++)` —— 真机账号有 **14 个播放列表**，用户视角就是"少两个、怎么刷都不出来"。
定上限的规矩：**先拿真实账号看一眼实际数量**（或按最大公约数 16/20），超出时**显式提示**
`另有 N 个未列出`，不要静默截断。

## 七、开箱模板

## 八、避坑清单

1. **`method:"DELETE"` 在本 App 里是 GET**（`RequestMethod` 枚举只有 GET/POST/HEAD）。PUT 同理。别再试第二遍。
2. **幂等 POST 会伪装成成功**：iwara 重复关注返回同一行 id，用"有没有报错"当成功判据必错；
   要判**返回体里的行 id / count**，或事后**读一次关系字段**确认。
3. **关系字段别猜语义**：`following` 是"我关注 TA"，`followedBy` 是"TA 关注我"——用关注前后的
   同请求对照确定，猜反了 √ 就永远不动。
4. **√ 依赖 loginHeader 自动附加**：书源没走 `putLoginHeader`（只把 token 存在变量里）时，
   匿名响应的 `following` 恒 false，此时必须显式加 `Authorization` 头或退回 L3 账本。
5. **未登录别渲染写操作按钮**；**自己的内容要单独一档**，否则点了只报错。
6. **提示语里的操作必须有实现**（`iwMyPlNeed` 空头支票）。grep 哨兵键确认有写入方，否则删文案。
7. **TTL 缓存三件套**：自愈补拉 + 冷却 + 显式刷新按钮，缺一件就有"刷不出来"的报障。
8. **冷却时间戳写在发请求之前**，失败也要冷却；否则 0 数据的账号每次进详情都白等一个 RT。
9. **列表型按钮上限按真实账号数据定**，超出要显式提示"另有 N 个未列出"，不要静默截断
   （真机 14 个列表 vs 旧上限 12 = "少了两个"疑案）。
10. **写操作按钮收尾必带 `java.refreshBookInfo()`**，否则 √/计数变化要用户手动下拉，观感等同坏掉。
11. **`<usehtml>` 截断陷阱**：简介取 `substring(9, lastIndexOf('<'))`，所以所有用户文本（标题/作者名/
    列表名）都要转义，`</usehtml>` 必须是最后一个 `<`；onclick 串内不得出现裸 `<` 与 `&&`。
12. **显示名与 onclick 参数两套清洗**：一个转义（`&→&amp;`），一个删除（`&→和`、去掉 `' < > "`）。
13. **原始 TLS 套接字绕 DELETE**：握手能过但 CF 不给响应（Read timed out）；且 Rhino 里
    `java.lang.reflect.Array` 被 JavaClass-shutter 封（`newInstance` 报"无法读取 undefined 的属性 Byte"），
    只能逐字节读 + 手工解 chunked——**成本高、收益零，别做**。
14. **bundle 里的路径参数是 UUID 不是用户名**：`/user/ppo2024` → `errors.notFound`，
    `/user/6012a7b9-…/followers` 才对。函数名（`createFollow(e,t)`）看不出 t 是什么，必须实测。
15. **搜索/发现结果里常常已经带关系字段**（`user.following`、`liked`），能省一次详情请求；
    但**别在列表页为每条各发一次请求**（并发一高就是限频）。
16. **改 jsLib 后必须先导入再测**（`eval_js` 里同名函数重新声明不会覆盖已加载的旧绑定）。
17. **MCP 调用严禁并行**（`Session not found`）；`check_source` 偶发 CF 抖动误报，重跑即过。
18. **`eval_js` 顶层不能 `return`**（"返回的值无效"），要写成最后一个表达式。

## 九、验证方法

### 9.1 新断言必须先"红"再"绿"（负对照）

给旧版加测试时，最容易自欺的是"断言写得根本不会失败"。规矩：
**新写的每条断言，先拿改动前的旧 JSON 跑一遍，必须报错/失败**，再拿新版跑必须通过。

```bash
node jscheck_v8/harness_v8.js iwara_v8.json   # ✅ 全过
node jscheck_v8/harness_v8.js iwara_v7.json   # 必须 ❌（旧版没有 IWRFAROW / IWRPLRF）
```

本轮负对照当场抓到一条假断言（正则写宽了，旧版也能过）。

### 9.2 双作用域 node 仿真（沙盒，零网络）

用 `vm` 把 jsLib 装进"假 java + 假 source"的盒子里，桩必须**复刻真机行为**
（本轮补的桩：`POST /user/{id}/followers → {"id":59252845}`、`__EXP → errors.unauthorized`），
然后按矩阵覆盖：

```
未关注渲染 / 已关注(服务端)渲染 / 账本命中渲染 / 账本过期回落 /
点关注=POST+写账本+refreshBookInfo / 未登录点关注给🔒 / token失效给🔒 /
未登录整行不渲染 / 自己的内容那一档 / 合集页(playlist.user)也能识别 /
usehtml 六约束（开头<usehtml>、最后<是</usehtml>、onclick无裸<与&&、可 new Function 编译）
```

### 9.3 真机分场景矩阵（`eval_js`，唯一能验关系态与登录态的地方）
