## 1 ★对照实验：唯一可靠的逆向方法

### 1.1 手法一 · 官方 App 同一接口逐字节对照

用抓包拿到官方 App 的请求与响应，然后用 `send_request` 重放 URL、**只改一个变量**：

```python
# 同一 URL、同一 key、同一 readcontextid，只改 Cookie
A 带 transmode=chinese              → 7 639 B  纯中文正文
B 不带 transmode（只有 translang）  → 82 664 B 越南语原文 + 逐词对照标签
```

**响应体差异本身就是答案**，不需要读官方 JS。

### 1.2 手法二 · 单变量对照

一次只改一个键（Cookie / 头 / 参数），其余保持不变。变量多了就分不清是谁的作用。

### 1.3 三条纪律

1. ★**控制变量**：两次请求之间不要插入任何其它请求（会话类接口尤其敏感）。
2. ★**先排除易变量**：URL、路径、方法、UA 都对照无误之后，再动 Cookie。
3. ★**看响应体，不看状态码**：200 也能返回错误页/对照版/0 字节。

### 1.4 「鉴别四步」空体故障排查（承接旧文档，仍然有效）

接口返回 **HTTP 200 + 0 字节** 时按顺序做，别跳步：

1. **先看同站其它接口通不通**。同域同栈「目录 900 章通 / 正文空」= 不存在任何封锁，直接否掉地域假设。
2. **抓「别人成功过」的请求样本**。同 URL 官方 App 能拿到完整 JSON ⇒ 空体是我这条链独有的。
3. **判客户端栈差异**。某些站只对真浏览器/WebView 栈的 XHR 返回 JSON，`java.get`/`java.ajax` 恒空体。
4. **前两步都排除后，才谈地域/线路**。注意「沙盒 vs 手机对照」时栈已经变了，结论无效，必须统一栈。

> ⚠️ 本次 STV 的教训补充：第 3 步容易**过度归因**。
> 我们曾据此断定「必须走 WebView 栈」，绕了一大圈；真相只是**路径少了一段**
> （官方发 `/?sajax=readchapter`，我们发 `/index.php?sajax=readchapter`）。
> → 判定栈差异前，**先把 URL 逐字符对齐**。

STV 实例：`chapterlist` 的顶层是

- `data` = 越南语章名

## 3 ★会话铸语义：一次铸错，后面全错

这是本次最贵的教训。

### 3.1 现象

同一套规则，正文有时中文、有时越南语对照版；目录名能中文化、正文却不行；
各种补洞（degloss / squeeze / 分段 / 排版）都上了，正文语言就是不对。

### 3.2 真相

决定输出语种的是**「发放 key 那次请求」的 Cookie**，不是后续读正文的 Cookie。

STV 实例：

```
官方 App 请求 grantcontext 的 Cookie：lang=zh; transmode=chinese; foreignlang=vi; readcontextid=…
我写的：                                   transmode=name;    foreignlang=vi     ← 抄错了
```

`transmode=name` 铸出来的会话就是越南语的，于是正文只能给对照版。

### 3.3 通用检查表

拿到「先申请票据、后凭票取数」这类接口（token / key / grant / sign / context）时：

- [ ] 官方 App 申请票据时的 **Cookie / 请求头**抄全了吗？**逐项对照**。
- [ ] 票据是否与后续请求的**会话**绑定？缓存里要不要一起存（如 `时间戳|会话|key`）。
- [ ] 换命名空间让旧票据作废（`stv9_` → `stv10_`），否则会一直命中之前铸错的票据。
- [ ] 怀疑时，**同时试两组票据 Cookie**，看返回语种/数据形态是否变化。

## 4 ★正文「一整段」的完整链路：三个关口

症状：规则明明输出了段落，阅读端仍是一整段。
**修「怎么切」是没用的**，要一关一关确认。

```
规则输出  ──净化链路──▶  清洗后的文本  ──渲染层──▶  屏幕
   关口一                    关口二                  关口三
```

### 4.1 关口一 · 规则输出对不对

在 App 内实跑（`eval_js` + 真实 jsoup）验证，别只信 harness：

```js
var d = Packages.org.jsoup.Jsoup.parse(raw);
d.select('p').size();        // 段落标签数
String(d.wholeText());       // 保留换行？
```

**App 内 jsoup 三件套必测**（本次全部实测）：

| 方法 | 行为 |
|---|---|
| `text()` | **规范化空白，把换行吃掉** |
| `wholeText()` | 保留原始空白与换行 ← 正文必须用这个 |
| `select('p')` | 正常 |

### 4.2 关口二 · 净化链路

上游 `HtmlFormatter.formatText`：

```kotlin
private val wrapHtmlRegex = "</?(?:div|p|br|hr|h\\d|article|dd|dl)[^>]*>"
.replace(wrapHtmlRegex, "\n")        // <p> 就是换行标记
.replace(indent1Regex, "\n　　")       // \s*\n+\s* → 换行 + 全角缩进
```

**按源码，`<p>` 是官方认的换行标记，净化不会「拍平」。**

★但**改版 App 会加步骤**。识别方法：debug 输出里出现**源码里没有的痕迹**
（本次是：正文标点被转成半角 `，`→`,` `。`→`.`，而上游源码根本没有标点转换这一步）。
看到这种痕迹就说明净化被改过，别再按上游源码模拟——会得到「明明对却不对」的结论。

绕过方式：`<usehtml>`。`BookContent.kt` 会先用 `useHtmlRegex` 把整块换成占位符、净化完再还原。

### 4.3 关口三 · 渲染层

绕开净化后交给 **TextView**，它**不给 `<p>` 任何垂直间距**，只有 `<br/>` 产生换行。

⇒ 最终形态：**`<usehtml>` + 段落纯文本 + 段间单个 `<br/>`，整块单行**。

```js
return '<usehtml>' + lines.join('<br/>') + '<br/></usehtml>';
```

**硬约束**：整块必须单行——阅读端按 `\n` 切 `contents` 数组逐段处理，含换行的 usehtml 块会被切碎。

★**不要 `<p>` + `<br/>` 双叠加**（本次叠加后段落间距大得夸张，是用户当面指出才改的）。

### 4.4 ★分段策略：站点的原生结构优先，别猜

> **本文档 4.4 节已于 2026-10-03 重大修订**，原「同时跑五种切法各算一个分数取最高分」的做法被证伪并废弃。
> 保留下文作为**反面案例**，它解释了为什么那套做法必然会崩。

不同来源站的分段方式可能完全不同（STV 实测四种）：

| 类型 | 特征 |
|---|---|
| 空行型 | `data` 开头只有一个 `<p>`（广告），正文全靠空行 |
| 标签型 A | 121 个 `<p>`，其中 119 个是 `</p><p>` **相邻、相邻间没有换行符** |
| 制表符型 | 单换行 + 制表符（越南语对照版） |
| ★标签型 B | 232 个 `<p idx="N">`，包在 `<article>` 里，**整篇零换行符**（对话体小说） |

#### 4.4.1 正确做法：原生结构即权威，先采信再谈猜测

**站点已经把段落结构给了你（`<p>` / `<article>` / `<br>` / `<div>`），那就是原生形态，直接照搬。
只有站点没给结构时，才轮到从空白字符去猜。**

```js
function parasByTags(d) {
  var L = [];
  try {
    var scope = d;                                   // 优先 <article> 包裹的正文区
    try { var art = d.select('article'); if (art.size() > 0) scope = art.get(0); } catch (ea) {}
    var ps = scope.select('p');
    if (ps.size() < 3) return null;                 // 块标签太少 → 当没给结构
    for (var i = 0; i < ps.size(); i++) pushLine(L, ps.get(i).wholeText());
  } catch (e) { return null; }
  return L.length >= 3 ? L : null;
}

function paras(d, html) {
  var tagged = parasByTags(d);      // ★权威信号优先，不与猜测候选竞争
  if (tagged != null) return tagged;
  /* ↓ 只有站点没给块结构，才退回猜空白 */
  ...
}
```

#### 4.4.2 ★★反面案例：打分 PK 把唯一正确的候选毙了（对话体小说专属）

《起手乘十？有BUG你是真卡啊》(fanqie/7526236974294764606) 用上面这个修法之前，
老的打分实现**实测把正确答案打成负分**：

| 样本 | `<p>` 数 | 换行符 | p-tags 得分 | 其它切法 | 结果 |
|---|---|---|---|---|---|
| 起手乘十 | 232 | **0** | **-80** | 全 -1 | **winner=None → 整篇一段** |
| 生化暴君 | 1 | 150 | -1 | segBlank=51 | 正常 |
| trxs | 121 | 4 | 92 | -1 | 正常 |

打分函数：`score = n - tiny*3 - …`，其中 `tiny` = 长度 < 12 字的段数。
起手乘十 n=232、avg=14.1、tiny=**104**（对话体小说短句极多）→ `232 - 104*3 = -80`。

**致命点在选择循环本身：**

```js
var best = null, bs = -1;
for (...) { var sc = segScore(cands[k]); if (sc > bs) { bs = sc; best = cands[k]; } }
if (best == null) return [整篇一坨];   // ← 兜底
```

`bs` 初值 `-1` ⇒ **候选的绝对分数必须 > -1 才可能被选中**。
任何带负分惩罚的评分函数，都会让「最优解」变成负数而**永远落选**，`best` 保持 `null`，掉进兜底。

为什么一直没暴露：只有「**对话体 + 全 `<p>` 块 + 零换行**」这一形态会被打崩。
生化暴君/trxs 的正确候选得分 51/92 都 > -1，正常。
★**对话体恰恰是短段惩罚杀得最狠、也最需要原生标签的一类。**

#### 4.4.3 由此得到的三条通用铁律

1. ★**打分 PK 的初值陷阱**：任何 `best=null, bs=-1, if(sc>bs)` 的择优写法，
   候选分数**必须大于初值**才能被选中。带负分惩罚项时要么把分数下限钳到 0，
   要么**根本不该在这种场景用打分**。
2. ★**权威信号与猜测候选不许放进同一个评分池**。站点给的块级标签是权威，
   换行/缩进/定长切割全是猜测。**权威优先，猜测兜底。**
3. ★**先抓包确认服务端原生形态，再决定要不要解析**。
   本例若先抓包，那套「五切法 + 打分」根本不必存在 —— 用户的原话：
   「最好直接用它的原生格式，不要在这里切切切的」。

> ⚠️ 顺带一条证据纪律：本次我一度宣称「官方 App 拿到的与我们逐字节同构」，
> 但那批抓包其实是**另外两本书**的样本，本书当时**并没有真源支撑**，
> 结论虽对、证据是用户在官方 App 打开后才补抓到的。
> ⇒ **说「与官方一致」之前，先确认抓包里的 bookid/章节ID 就是目标对象。**

## 5 ★测试方法论（harness）

本次 harness 自身翻车 **十几次**，每一条都是通用教训。

1. ★**必须用被测的真实函数**。harness 里复制一份简化桩 = 测试副本不是产物。
   正确做法：从源文件里 `pick(start, end)` 抽出真实函数，用 `new Function` 装配。
2. ★**不同分支要有各自用例，并断言「真的走到了那条分支」**。
   本次对照版用例一直调的是 `clean()`（而它恰好正确），`plain()` 里的 bug 一直没被抓到——**假绿**。
3. ★**反向对照断言**：故意把桩改成真实的坏行为，断言「结果确实变差」。
   例：把 jsoup 桩的 `text()` 改成会吃换行，断言段落数下降。
4. ★**负例验证闸门**：新增的构建闸门要**故意触发一次**确认它真的会拦（本次模拟删掉来源列表，闸门如期报 3 条 FAIL）。
5. **删除函数后 `grep -c` 必须为 0**，不能只看 `node --check`——
   残留的 `if (x) { removedFn(t); return y; }` **语法完全合法**，只有运行时才 ReferenceError。
6. **emoji 断言**：`charAt(0)` 只返回代理对高位码元，永远匹配不上；必须 `indexOf('🔒') === 0` 或写真实字面量。
7. **Python 改断言别用 `re.sub` 带 `\u` 转义**（会报 `bad escape`）；按行遍历整行替换更稳。
8. **闭包捕获**：`let m` 在 `while((m = re.exec()))` 里是函数级作用域，循环结束后所有闭包都读到 null → 用 `const g = mm[1]` 捕获。

## 6 ★交付纪律（今天踩了三次）

1. ★**上传与唤起必须串行**，且**只能用当次上传返回值里的 URL**。
   并行时凭印象写地址 → 404 → 导入器把错误页当书源解析 → **弹窗显示乱码**。
   （`importSourceUrl` 不校验 HTTP 状态码，`GET 404` 与 `GET 200` 在日志里一眼可辨。）
2. ★**确认导入状态直接查日志 + 回读特征，不要问用户**。
   `eval_js` 回读书源内特征（版本号 + 功能锚点），`get_http_logs` 确认 `GET <raw> -> 200`，两者满足即已落库。
3. **非 BMP 字符**：走文件通道（uguu/GitHub raw）安全；走 MCP `save_source` 会被传输层吞掉代理对。

## 7 ★「端到端做对了但用户还是不满意」的排查顺序

正文分段这二十几个版本，按这个顺序走能少绕十个版本。
★**2026-10-03 补充：关口一（规则输出）要排在最前，且要先数清「服务端到底给了什么结构」。**

0. **先确认用户在哪个 APP 里看到的**。「我能正常看到」若指官方 App，那是**对照基准**，不是故障现场。
   同一句「格式正确 / 看不到正文」在不同 App 里指向完全相反的结论 —— 先问清再动手。
1. 在 App 内**实跑规则**看原始输出（`eval_js` + 真实 jsoup），并**打印结构统计**：
   块标签数 / 换行符数 / 平均段长。★不要只问「输出对不对」，要问「服务端给了什么」。
2. 抓**同接口的官方 App 响应**逐字节对照，确认服务端返回什么。
   ★抓包列表要先用 **bookid / 章节ID 过滤**，确认样本就是目标对象，别拿别的书的流量下结论。
3. 看 debug 输出里有没有**意外的痕迹**（标点被转换、标签消失）→ 判断净化被改过。
4. 最后才怀疑渲染层，而**渲染层 debug 永远看不到**，只能真机确认。

> ★关口一内部的优先级（本轮教训）：
> **先信服务端原生结构 → 再考虑从空白猜 → 永远不要用打分 PK 在两者之间做选择。**

### 8.1 目录数据结构

```
按 -//- 分章，每章内按 -/- 分槽：
  [ 常量 , 章节ID , 章名 , 状态标记? ]
  data     = 越南语章名
  oridata  = 中文章名（★优先用这个）
  状态标记 = 空(免费) / vip(未解锁) / unvip(已解锁)
```

★目录章名**必须从 `oridata` 取**；正文请求的 `c` **必须是章节 ID**
（trxs 恰好等于序号所以用序号能通，fanqie 是雪花 ID，用序号直接返回 0 字节）。

### 8.2 正文语种

```
铸 key（grantcontext）时 Cookie：readcontextid=旧; lang=zh; transmode=chinese; foreignlang=vi
读正文      时 Cookie：readcontextid=新; lang=zh; transmode=chinese; foreignlang=vi
```

`translang=zh` 与正文语种**无关**（只管搜索/详情）。
若站点暂未译出中文，正文会是越南语对照版 `<i t='中文' v='越南语'>`，可用 `t` 属性还原兜底。

#### 正文分段形态（四种，实测自同一本书的不同章节/来源）

```
① 空行型   <p><span>@广告</span></p>正文\n\n段落\n\n段落      （生化暴君）
② 标签型A  121 个 </p><p>，相邻间无换行                          （时停斗罗/trxs）
③ 制表符型 \n\t + <i t='中' v='越'>  对照版
④ ★标签型B <p><span>@广告</span></p><header></header>
            <article><p idx="0">001</p><p idx="1">…</p>…</article><footer></footer>
            232 个块，整篇 0 换行                                （起手乘十）
```
★形态 ④ 是**对话体小说的典型形态**：段落短、密度高、零换行，
既让所有「按空白切」的猜测失效，又让「短段惩罚」把正确答案打成负分 —— 双重夹击。
⇒ 遇到形态 ④ 只能靠原生 `<p>` 块，任何基于空白或长度的启发式都会崩。

## 10 避坑清单 K1~K26

1. 对照官方 App 同一接口的响应原文，别在参数上盲试。
2. 解析响应先打印所有顶层字段。
3. 票据/会话类接口要连**申请时的 Cookie** 一起抄，并核对语义（本文第 3 章）。
4. 怀疑旧票据时换缓存命名空间，让它们一次性作废。
5. 正文取文本用 `wholeText()`，不要用 `text()`。
6. `<usehtml>` 必须配 `<br/>` 才能产生换行。
7. `<usehtml>` 整块单行，用户文本的尖括号/`&`/引号要转义。
8. 不要 `<p>` + `<br/>` 双叠加。
9. 上游源码里没有的步骤 = 改版加的，别按原版模拟。
10. ★分段策略：站点给了块级标签就直接采信（原生结构优先）；
    只有站点没给时才从空白字符猜。**不要用打分 PK 在「原生结构」和「猜测切法」之间做选择** ——
    打分带负分惩罚时会把正确候选打成负数而永远落选（详见 4.4）。
11. harness 必须用真实函数 + 分支覆盖 + 反向对照。
12. 删函数后 `grep -c` 确认为 0，`node --check` 不足以发现残留调用。
13. 上传与唤起串行，只用当次返回值 URL。
14. 确认导入查日志 + 回读特征，不问用户。
15. `charAt(0)` 匹配 emoji 无效，用 `indexOf` 或真实字面量。
16. 循环里的闭包变量要用局部 `const` 捕获。
17. URL 选项：两个 JSON 对象会 NPE，要合并成单个。
18. 片段的 `#fragment` 不发给服务器，可安全携带备用参数（也不会干扰章节去重）。
19. 服务端给的计数字段（如 `unvip`）是最好的解析结果交叉校验数——方向反了立刻能发现。
20. 目录解码优先用「更长的数字槽」，但**先确认编号槽是紧邻章名左槽的那个**。
21. ★**打分 PK 的初值陷阱**：`best=null, bs=-1, if(sc>bs)` 要求候选分数 > 初值；
    负分惩罚项会让「最优解」永远选不上，`best=null` 静默掉进兜底分支。
22. ★**权威信号与猜测候选不许同池**：原生块级标签 vs 空白猜测，前者优先，后者兜底。
23. ★**说「与官方一致」之前先核对抓包样本**的 bookid/章节ID 就是目标对象，
    别拿别的书的流量下结论（本次因此一度无据宣称）。
24. ★**先问清用户在哪个 APP 里看到的行为**。「格式正确 / 看不到正文」在不同 App 里
    指向完全相反的结论，官方 App 能正常读恰恰是**对照基准**而不是故障现场。
25. ★**本地构建树可能比 App 旧整代**：改之前必须逐字段 md5 对账，
    否则「只改一个字段」会静默把其余字段整体回退（详见第 11 章）。
26. ★**服务端给的就叫原生**（不是「原声」）：用户原话「最好直接用它的原生格式」，
    指服务端返回的原始段落结构，不是音质意义上的原声。

## 11 ★多版本书源：本地树与 App 不同步的同步方法

多轮迭代的书源，本地 `js/` 片段目录很可能**落后 App 里已导入的版本整代**
（本次本地 content 19 667 B vs App 23 318 B，且 toc/init/explore/loginUrl 全都不同）。

**此时绝不能「改本地再 save_source」** —— 那是整体替换语义，会把其余字段静默回退成旧版。

### 11.1 正确姿势：让 App 自己吐原文，走文件通道回来

```
App eval_js  →  base64 编码字段 → uguu.se multipart 上传 → 沙盒 urllib 拉回 → md5 逐字段对账
```

```js
function b64(s){
  var bytes = new Packages.java.lang.String(String(s))
      .getBytes(Packages.java.nio.charset.Charset.forName('UTF-8'));
  return String(Packages.android.util.Base64.encodeToString(bytes, 2));   // 2 = NO_WRAP
}
function upload(fname, b64body) {
  var body = '--' + B + CRLF
    + 'Content-Disposition: form-data; name="files[]"; filename="' + fname + '"' + CRLF
    + 'Content-Type: text/plain; charset=utf-8' + CRLF + CRLF
    + b64body + CRLF + '--' + B + '--' + CRLF;
  var opt = ',' + JSON.stringify({ method:'POST', body: body, timeout:90000,
      headers: { 'Content-Type': 'multipart/form-data; boundary=' + B } });
  return String(java.ajax('https://uguu.se/upload.php' + opt));
}
```

### 11.2 为什么必须 base64 —— 不要裸传大段 JS

★**MCP 传输层会在内容出现 `</script>` 时提前截断**。本次正文规则正好内嵌了一段
`'<html>...<script>' + STVPRE + ...` 的 HTML 骨架，裸传直接变成语法错误。

⇒ **一律 base64 后传**（纯 ASCII，无引号/尖括号/换行），沙盒侧解码回原文再对账。

### 11.3 同步完成的验收闸门

```python
# 每个字段都要和 App 内 md5 逐一比对，全绿才允许动手改
EXP = {'ruleContent.content': 'e968fcb…', 'ruleToc.chapterList': 'a0244789…', …}
assert md5(local) == EXP[k]   # 12/12 PASS 才能开始改
```

构建脚本里保留同样的闸门（`build.py` 的 `KEEP` 字典），
断言**除目标字段外其余字段零漂移**。

### 11.4 本轮踩到的传输/环境小坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 裸传含 `</script>` 的 JS | Rhino 报「不允许的字符」 | base64 后再传 |
| `java.lang.String` | `undefined 的属性 String` | `java` 变量遮蔽了包名，写 `Packages.java.lang.String` |
| 手工拼 multipart | `No input file(s)` | body 里的 `"` 会打断 JSON，必须 `JSON.stringify` 构造选项 |
| 大文件上传 75 KB | 沙盒侧超时 | `nohup` 后台跑 + 轮询日志 |
| `node --check <(...)` | `ENOENT /proc/…/pipe` | 沙盒不接受进程替换，先落 `/tmp/x.js` |
| header 字段送进 node | JSON 不是 JS，误报语法错 | header/非 JS 字段要排除在 node 校验外 |
| Rhino `String.length` | 与 Python 码点数不等 | 只比 **md5**，不比长度（emoji 会差） |

### 11.5 ★测试桩会自己骗你（本次又犯一次）

手工在 eval_js 里拼一段"只包含待测函数"的桩时，**漏掉的常量/依赖会让行为失真**，
从而误报"有回归"。本次就一度误判「生化暴君从 75 段掉到 1 段」。

★**正解 = 从 App 内已保存的真实规则里抽取函数来装配**，不要手抄常量：

```js
var rule = String(source.getContentRule().content);   // 取真实规则原文
function ex(src, sig){ /* 括号配平，从 'function name(' 起截到 d==0 */ }
var deps = ['unesc','esc','isAd','pushLine','segBlank','parasByTags','paras','toHtml','render'];
// 逐个 ex(rule,'function '+deps[i]+'(') 拼起来再 eval
```

★**判定"是否回归"必须双跑**：新旧两版 × 同一批真源样本。只跑新版看到异常就下结论，
会把桩的问题当成代码的问题。已保存的响应样本（`real_*.json`）就是为这个准备的。
